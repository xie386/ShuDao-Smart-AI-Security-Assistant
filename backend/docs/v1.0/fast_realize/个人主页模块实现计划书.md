## 一、业务目标

在「蜀道安全助手」增加**个人主页**，登录用户可自助维护：

1. **修改用户名**（username，唯一）
2. **修改密码**（旧密码校验 + bcrypt 重哈希）
3. **上传头像**（复用人脸/图片上传白名单机制）
4. **填写个人邮箱**（email）
5. *显示用户的知识贡献(只显示通过的,可以复用"知识贡献"模块的显示路由)*
6. *显示用户的上报贡献(三种用户都有),整改贡献(只有安全员或者管理员会有),审批整改贡献(管理员独有),可以复用"隐患上报"模块的隐患列表展示路由,但在前端显示上要做页面美观适配调整,不要直接套用*

前端入口：右上角用户信息区新增「个人主页」入口（点击进 `#/profile` 单页）。

> 第 5、6 条为个人主页的**贡献聚合展示**（见 E 步「贡献记录区」）。后端复用现有列表接口（带 `mine=true` 过滤），仅隐患展示需给 `list_hazards` 加 `rectified_by` / `reviewed_by` 两个可选过滤参数（不改表、不加表）。

## 二、关键约束（来自现状调研）

| 现状 | 影响 |
|---|---|
| `users` 表只有 `id/username/hashed_password/role/real_name/created_at`，**无 email / avatar** | 按 P3 铁律「**勿改表结构**」，本模块**不碰 users 表**，email/avatar 落到新建的 `user_profiles` 一对一表 |
| 密码哈希 `security.hash_password(plain)` / `verify_password(plain, hashed)`（bcrypt，库直用，无 passlib） | 改密直接复用，无需新依赖 |
| 文件上传 `utils/files.py: validate_and_save()` 白名单 `jpg/jpeg/png/webp` + MIME 双校验 + ≤10MB + uuid 重命名 → `uploads/`，返回 `/uploads/<uuid>.<ext>` | **头像上传直接复用该函数**（同白名单），落盘后即静态可访问，无需新存储逻辑 |
| 认证 `get_current_user` 依赖返回 `{id, role}` | 个人主页所有写操作都用它取当前用户，保证「只能改自己」 |
| 前端 hash 路由 `#/<page>`，`/me` 已返回 UserOut（含 username/role/real_name） | profile 页加载时先拉 `/me` + 新增 `/me/profile` 拿 email/avatar |

**设计铁律**：不改 `users` 表、不改 `auth.py` 登录逻辑、不引入新依赖（bcrypt 已全局装）。

## 三、数据层（新建 1 表，users 零改动）

`schema.sql` 末尾追加 `user_profiles`（P3 铁律豁免：这是**新增**表，不是改旧表）：

```sql
CREATE TABLE IF NOT EXISTS `user_profiles` (
  `id` int NOT NULL AUTO_INCREMENT,
  `user_id` int NOT NULL,
  `email` varchar(128) DEFAULT NULL,
  `avatar` varchar(255) DEFAULT NULL,        -- 头像 URL（/uploads/<uuid>.<ext>），NULL=用默认头像
  `updated_at` datetime NOT NULL DEFAULT (now()),
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_user_profiles_user` (`user_id`),   -- 一对一
  CONSTRAINT `user_profiles_ibfk_1` FOREIGN KEY (`user_id`) REFERENCES `users` (`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
```

- 执行：`scripts/db_verify.py` 已能跑；本表走 ALTER/建表脚本（与 exams/kb_contrib 同范式）
- ORM：`backend/src/models/user_profile.py` → `UserProfile`（Mapped，user_id 唯一）
- `models/__init__.py` 导出；`db_verify.py` 扩展校验（对齐列）

**为何不用 users 加列**：P3 明确「数据表结构以 schema.sql 为准，代码不 create_all、不改表」。新增 `user_profiles` 是**加表不是改表**，严格守约；且头像/邮箱属「个人扩展信息」，与认证核心字段（username/password/role）解耦，独立表更合理。

## 四、后端实现（A–E）

### A. 数据模型与校验
- `models/user_profile.py`：`UserProfile(id, user_id, email, avatar, updated_at)`
- `schemas/user_profile.py`：
  - `ProfileOut(user_id, email, avatar)`
  - `UsernameUpdate(username: str = min_length(2, max_length=64))`
  - `PasswordUpdate(old_password: str, new_password: str = min_length(6))`
  - `EmailUpdate(email: str = EmailStr 或正则校验，可空)`
  - `AvatarUpdate(avatar: str)` —— 由上传接口返回 URL 后回填（不在本 schema 直接收文件）

### B. 头像上传（复用 uploads 机制）
- 在 `routers/uploads.py` 新增 `POST /api/uploads/avatar`：
  ```python
  @router.post("/avatar", status_code=201, summary="上传个人头像（复用图片白名单）")
  def upload_avatar(file: UploadFile = File(...), user: dict = Depends(get_current_user)):
      url = validate_and_save(file)          # 复用 jpg/jpeg/png/webp + ≤10MB + uuid
      return ImageUploadResponse(url=url)     # 返回 /uploads/xxx.jpg
  ```
- 前端拿到 URL 后调 `AvatarUpdate` 写入 `user_profiles.avatar`
- **不改 `validate_and_save`**（白名单已覆盖头像格式）；若需单独限制头像 ≤2MB，可加可选参数，但本计划复用现有 10MB 上限（保持简单）

### C. 个人资料读写服务 `services/user_profile_service.py`
| 方法 | 逻辑 |
|---|---|
| `get_or_create(db, user_id)` | 取 profile，无则建空行（首次访问个人主页自动初始化） |
| `update_username(db, user_id, username)` | 查重（`username` 唯一约束）→ 更新 users.username；返回冲突 409 |
| `update_password(db, user_id, old, new)` | `verify_password(old, users.hashed_password)` 失败 → 401；`hash_password(new)` 更新 |
| `update_email(db, user_id, email)` | 校验格式（空或合法邮箱）→ 写 profile.email |
| `update_avatar(db, user_id, url)` | 写 profile.avatar |
| `get_profile(db, user_id)` | 合并 users（username/role/real_name）+ profile（email/avatar） |

**安全**：所有方法强制 `user_id == 当前登录用户`，无越权风险（管理员也不能改他人，保持「个人主页=自助」语义；如需 admin 代改另议）。

### D. 路由 `routers/user_profile.py`（前缀 `/api/me`）
- `GET  /api/me/profile` → 当前用户完整资料（username/role/real_name/email/avatar）
- `PATCH /api/me/username` → 改用户名（查重）
- `PATCH /api/me/password` → 改密码（旧密码校验）
- `PATCH /api/me/email` → 填/改邮箱
- `PATCH /api/me/avatar` → 绑头像 URL（文件先走 `/api/uploads/avatar`）
- 全部 `Depends(get_current_user)`；`/me` 已在 auth.py 有，本路由独立 prefix 避免冲突
- `main.py` 挂载 `user_profile.router`

### E. 前端「个人主页」页 `#/profile`
- 右上角用户区加「👤 个人主页」链接（点击 `location.hash='#/profile'`）
- 页面结构（川蜀红设计系统，uiverse 003/004 组件重着色）：
  1. **头像区**：`<img>` 显示当前头像（无则默认「蜀」字圆形占位）；「上传头像」按钮 → `<input type=file>` → `POST /api/uploads/avatar` → 拿 URL → `PATCH /api/me/avatar` → 刷新头像
  2. **用户名**：input 显示当前 username + 「保存」按钮 → `PATCH /api/me/username`
  3. **密码**：旧密码 / 新密码 input + 「修改」→ `PATCH /api/me/password`（前端不回显，改后清空）
  4. **邮箱**：input + 「保存」→ `PATCH /api/me/email`
  5. 角色/真实姓名：只读展示（`/me` 返回）
- 加载：`loadProfile()` 先 `GET /api/me` 拿 username/role/real_name`，再 `GET /api/me/profile` 拿 email/avatar`（合并渲染）
- 消息联动（可选增强）：改密/改用户名成功 toast 提示；不做消息模块通知（属自助操作，无他人需知会）

#### 贡献记录区（批注第 5、6 条，聚合展示——复用现有路由，前端美观适配）

页面下半部分分两个卡片区，分别拉取并展示当前用户的贡献：

**① 知识贡献（只显示已通过的）**
- 接口：`GET /api/knowledge-contrib?mine=true&status_filter=已入库`（后端零改动，K02 已支持）
- 展示：卡片/紧凑列表，列 = 标题 / 类别 / 入库时间 / 查看详情（复用 K03 详情弹窗样式，但适配为 profile 内嵌卡片，不直接套用隐患列表）
- 空态：「暂无已入库的知识贡献」

**② 隐患贡献（按角色分三类，复用 H02 列表接口 + 新增过滤参数）**
- 我上报的（三种用户都有）：`GET /api/hazards?mine=true`
- 我整改的（安全员/管理员会有）：`GET /api/hazards?rectified_by={me}` ⚠️ 需后端给 `list_hazards` 加 `rectified_by` 过滤（见 F 步）
- 我审批的（管理员独有）：`GET /api/hazards?reviewed_by={me}` ⚠️ 需后端加 `reviewed_by` 过滤
- 前端用**三个 tab**（上报/整改/审批）切换，每个 tab 内用隐患列表的精简版（标题/等级/状态/时间），**做页面美化适配**（川蜀红卡片，不直接套用隐患管理页的表格样式）
- 角色适配：普通员工只显示「我上报的」tab；安全员 + 管理员显示「我整改的」；仅管理员显示「我审批的」
- 点击条目可复用 H03 详情弹窗（只读查看）

> 设计要点：批注明确要求「复用路由但前端美观适配、不要直接套用」——故 profile 内用**卡片网格/tab** 重新组织，而非直接 iframe 或原表格搬移。

### F. 隐患列表过滤扩展（支撑「我整改的 / 我审批的」）
- `routers/hazards.py` 的 `list_hazards` 新增两个**可选** Query 参数：
  ```python
  rectified_by: Optional[int] = Query(default=None, description="按整改人过滤（H05 rectify_by）")
  reviewed_by:  Optional[int] = Query(default=None, description="按审批人过滤（H04 assign_by / H06 review_by）")
  ```
- `HazardService.list_hazards` 内部按这两个参数追加 `where`（无值则忽略，零影响现有调用）
- **不新增表、不改表结构**：`hazards` 表已有 reporter_id / assign_by / rectify_by / review_by 等列（H01–H06 流程字段），仅暴露过滤入口
- 需确认 Hazard 模型字段名（reporter_id / rectify_by / review_by 等），执行时对齐实际列名

## 八、关键决策记录

1. **user_profiles 独立表 vs users 加列**：选独立表，严格守 P3「勿改表」铁律；一对一 + user_id 唯一约束，逻辑等价加列但零侵入。
2. **头像复用 uploads 机制**：白名单 jpg/jpeg/png/webp 完全覆盖头像场景，避免重复造轮子；URL 存 profile.avatar，静态托管已具备。
3. **密码改密复用 security 模块**：bcrypt 哈希/校验直调，不碰登录 jwt 签发。
4. **用户名查重**：username 唯一约束，冲突返回 409（前端提示「该用户名已被占用」）。
5. **贡献聚合展示（批注第 5、6 条）**：个人主页下半部分展示「知识贡献（只通过）」+「隐患贡献（上报/整改/审批三类，按角色）」，**复用现有列表路由**（`/api/knowledge-contrib?mine=true&status_filter=已入库`、`/api/hazards?mine=true/rectified_by/reviewed_by`），前端用 tab + 川蜀红卡片**美化适配、不直接套用原表格**；隐患需给 `list_hazards` 加 `rectified_by` / `reviewed_by` 两个可选过滤参数（零影响现有调用，不改表）。
