## 00 账号隔离性前置检查

> 状态：**已完成**（实现与真机验证均已收口，实测见 `Done/00-账号隔离性前置检查·实现记录.md`）

### ① 应对什么问题

**现象**：v2.0 开工前的账号隔离性回归检查中，三大模块的**接口层**隔离全部正确，但**产物文件层**存在隔离缺口——他人（甚至未登录访客）可以直接下载别人生成的 PPT 与试卷导出文件；PPT 产物还会因同名而互相覆盖。

**证据**（实测，可复跑；取证方法见 `research/00-账号隔离性前置检查.md` §二、§九）：

| 编号 | 现象 | 证据（实测响应 / 代码位置） |
|---|---|---|
| ISO-1 | PPT 产物文件名只由主题决定，落全局命名空间 | `src/services/ppt_service.py:153-154`；`ppt_tasks` 表 user 17 有「安全生产法要点」3 条（id=8 已完成、id=9/10 草稿），共用同一 `dest` |
| ISO-2 | `/ppt-files/*` 静态无鉴权，主题名可猜 | 无 token GET `/ppt-files/高处作业安全.pptx` → `200`，content-length `16247776`；带他人 token 同样 `200` |
| ISO-3 | 试卷导出有两条并行的无鉴权通道 | 无 token GET `/exam-files/paper_d0fd10a7c52c.md` → `200`（9660 字节）；`/uploads/exam/paper_d0fd10a7c52c.docx` → `200`（39807 字节）；`src/main.py:123,141` |
| ISO-4 | 用户上传的 PPT 模板对所有账号可见可用 | `src/services/ppt_template_service.py:88-102`（按裁定 3，属**有意设计**，不修） |
| ISO-5 | `routers/exam.py` docstring 写 6 个端点，实际 5 个 | `src/routers/exam.py:3-9` |

**接口层无需修复的部分**（实测通过，避免重复排查）：会话列表/消息/删除/点赞（401/403/404 全对，`chat_service.py:31,43,60,72,119`）；PPT 任务列表与详情/改大纲/删除/生成（403，`ppt_service.py:195-203,228-234`）；试卷列表/详情/导出（404，`exam_service.py:78,88`）；知识贡献详情越权（403，`knowledge_contrib_service.py:192`）。

### ② 功能

做完之后：

1. **PPT 只能本人下载**：其他人（含未登录访客）拿不到别人的讲义文件，越权请求被拒。
2. **同主题不再互相覆盖**：两个账号（或同账号两个任务）用同一个主题生成 PPT，各自持有一份，内容不串；删自己的任务不会误删别人的产物。
3. **下载名可读**：保存下来是「高处作业安全.pptx」这种业务名，不会看到内部编号。
4. **试卷同样只能本人下载**，且只剩一个取用入口。
5. **历史产物照常能下**：v1.0 期生成的 PPT 与试卷不需要重新生成。
6. **用户体验不变**：列表、生成、导出按钮的交互与位置不动，只是底层改走带鉴权的下载通道。

**(2) PPT 下载端点** — `src/routers/ppt.py` 新增 + `ppt_service.py` 新增 `download_path()`

@router.get("/{task_id}/download", summary="P07 下载 PPT（仅本人）")

                        media_type="application/vnd.openxmlformats-officedocument.presentationml.presentation")

`download_path()` 校验顺序（与 `_get_owned` 同范式）：
1. `_get_owned(db, user_id, task_id)` → 不存在 404、非本人 403
2. `status != 已完成 or not file_path` → 400「PPT 尚未生成」
3. `p = (PPT_FILES_DIR / Path(task.file_path).name).resolve()` —— **只取 basename**，天然免疫 `..` 穿越
4. `PPT_FILES_DIR.resolve() not in p.parents` → 404
5. 文件不存在 → 404「产物文件已丢失，请重新生成」
6. 返回 `(p, f"{task.topic}.pptx")` —— 下载名用主题，不暴露内部前缀

## 01 AI 助手模块升级

> 状态：**已完成**（2026-10-23 收官，含 A08 预处理审计）。实测见 `Done/01-AI助手模块升级·实现记录.md`；全量测评按裁定 1 延后；待跑清单见该文档 §五。

### ① 应对什么问题

**现象一：现有的「逐字同问」检索缓存，在实际对话里几乎不会被触发，等于没生效。**

- 现状机制：`src/routers/chat.py:41-48` 的检索块缓存以 `md5(question.strip())` 为 key（`_QA_CACHE_TTL = 10 * 60`），**只有与历史提问逐字相同（裁剪首尾空白后）才命中**；命中时才跳过 RAG 检索、复用它缓存的 `context` + `sources`。
- 现实交互形态：用户的真实路径是「根据上一个问题往下追问」或「直接跳到别的问题」——追问常是省略主语的短句（「那高度呢？」「这个要审批吗？」），跳题则换主题换措辞。任何一字、标点、语序、句式差异都会落到未命中分支，走完整检索。
- 直接后果：缓存收益被限制在极窄场景（本库日志里能看到的完全同句，主要来自「快捷提问」按钮：`conversations` 表中同一问句「脚手架搭设完成后需要检查什么？」出现两条，id 51 / 52）；真正的多轮追问完全不享受缓存，Redis 在这条链路上近乎空转。
- 附带问题：缓存是**按问题字面**存的，不是**按会话**存的。同一会话里已经检索过的高处作业父块，下一轮追问即使语义相关也拿不到，只能从头再检索一遍。

**现象二：用户习惯用疑问句，而疑问句式本身会拖累检索效果。**

- 用户在问答里更常输入「高处作业有哪些安全要求？」这类完整疑问句，而不是「高处作业安全要求」这种陈述式检索语。
- 疑问句带来的口语化虚词、句式倒装、指代（「它」「这个」）会稀释 BM25 的词项权重、也让稠密向量的语义中心偏移，检索效果打折。
- 当前链路把用户原话**直接**送进 `hybrid_retrieve(question)`（`chat.py:107`），没有任何预处理环节。
- 这一点是**用户判断**，具体折扣幅度要在调研期用评测集量化（口径：`scripts/eval_qa.py`，红线 ALL@10 ≥ 0.80）。

**红线（继承 v1.0，本大点不得突破）**：任何检索行为改动都必须过全量评测，ALL@10 ≥ 0.80 方可合并（口径见 `research/00-账号隔离性前置检查.md` §八 与 `../文件存放规则.md` 的检索指标约定）。

### ② 功能

做完之后，用户能感觉到的变化：

1. **追问不再重复「翻书」**：一个会话里，第一个问题（或停止聊天超过缓存时限后的最新一个）走完整向量检索；之后的追问先看这个会话已经检索到的内容够不够回答——够就直接回答（省掉整段检索时间），不够就只补检索「缺的那部分」，而不是把整个问题重新检索一遍。
2. **问题会被自动「说清楚」再送去检索**：口语化疑问句先被改写成检索友好的陈述句，并结合上下文补全省略的主语与细节（具体改写策略在调研期定），改写结果对用户可见或可追溯。
3. **缓存改成按会话，不再要求逐字相同**：换个问法追问、或把问题拆成两问，都能复用同一会话已有的检索结果。
4. **回答明显变快**：会话首问（含超时后首问）控制在 60 秒内，后续追问落到 15~20 秒量级；界面上给出本次是「完整检索 / 增量补检 / 命中缓存」以及耗时。
5. **可以自己选精度**：默认走半精度（快），想要更高准确性时，在 AI 助手页打开「高精度检索」开关，该轮改用全精度重排。
6. **答案准确性不下降**：改写与增量补检都要抽样核对，引用来源照旧可追溯。

**(2) 重排：fp16 默认 + 运行时可切 fp32** — `src/ai/reranker.py:27-52`

```python
@property
def model(self):
    if self._model is None or self._dtype != self._want_dtype():
        self._load()
    return self._model

def _want_dtype(self) -> str:
    """请求级开关优先，其次配置；仅 cuda 生效（CPU 无 fp16 加速意义）。"""
    want = "fp32" if self._force_fp32 else settings.RERANKER_DTYPE
    return want if settings.RERANKER_DEVICE == "cuda" else "fp32"

def _load(self):
    import torch
    from sentence_transformers import CrossEncoder
    if self._model is not None:          # 切换精度前必须卸载，否则显存不够（实测 fp32 会占满 3.57GB）
        del self._model
        self._model = None
        if torch.cuda.is_available():
            torch.cuda.empty_cache()
    kwargs = {"torch_dtype": torch.float16} if self._want_dtype() == "fp16" else {}
    self._model = CrossEncoder(settings.RERANKER_MODEL_PATH,
                               device=settings.RERANKER_DEVICE, model_kwargs=kwargs)
    self._dtype = self._want_dtype()

def set_high_precision(self, on: bool) -> None:
    """由请求的 high_precision 调用；切换代价 = 重新加载一次模型（fp16≈4s / fp32≈24s）。"""
    self._force_fp32 = bool(on)

def rerank(self, query, docs, top_k=None):
    scores = self.model.predict([[query, d] for d in docs],
                                batch_size=settings.RERANKER_BATCH_SIZE,
                                show_progress_bar=False)
    ...  # 其余不变
```

要点：`set_high_precision` 必须在**检索前**调用并加锁（`threading.Lock`），避免两个并发请求来回卸载/重载；精度切换只在请求显式打开时发生，默认路径不触发重载。

**(4) 问题预处理（所有路径必做，与 Redis 是否可用无关）** — 新文件 `src/ai/query_preprocess.py` + `prompts.yml` 新场景 `query_preprocess`

**四类动作：a / b / d 必做，c 由 Agent 按准则判断**

| 动作 | 说明 | 是否必做 | 无 Redis / 首问时 |
|---|---|---|---|
| a 陈述句化 | 疑问句/口语句 → 检索友好陈述句 | **必做** | 照做 |
| b 语义专业化 | 口语词 → 知识库的书文/规范用词（可多角度扩写） | **必做** | 照做 |
| c 多主题拆分 | 一题含**不同实体/不同主题**时拆成多个子查询 | **可选**，由 Agent 判断 | 照做（判断依据不变） |
| d 剔除已检索项 | 会话里已检索/已引用的内容不再重复检索 | **必做**（无可剔除则跳过） | **有 Redis**：按缓存块摘要剔除；**无 Redis**：按上一轮答案 `refs` 的 `doc#chapter` 剔除 |

**c) 的判定准则（写给 Agent，也写给实现）**：拆分本身等于多发一次检索，**时长近乎翻倍**，所以默认不拆。

| 情形 | 例子 | 处理 |
|---|---|---|
| **同一实体的两个方面** | 「高处作业的防护要求 + 检查要点」「安全带的选型 + 报废标准」 | **不拆**：合成一条检索式（同一文档块里大概率同时覆盖） |
| **不同实体 / 不同主题** | 「去外地怎么选择衣物和规划路线」「脚手架验收 + 塔吊司机持证要求」 | **拆**：分别检索（文献中很少把两个差别大的主题写进同一个块，一起检效果会打折） |
| 上限 | — | 最多 **2** 个子查询；更多的合并进最主要的那条，避免时长成倍 |

预处理只给**建议**（输出 `split` 与 `reason`），最终是否真的拆由 Agent 决定；Agent 不采纳时就只用 `declarative` 做单条检索（省一半时间）。

输入（三处来源，缺一不可）：

1. 原话；
2. `history` 最近 3 轮（各截 120 字）；
3. 「已检索过什么」的摘要 —— **有 Redis 用缓存块摘要，没有则用 DB 里上轮答案的 `refs`**（同一字段、两种来源，预处理逻辑不分支）。

输出（JSON）：

```json
{"declarative": "高处作业安全带高挂低用的具体要求",
 "subqueries": ["高处作业安全带高挂低用要求", "安全带使用规范 检验周期"],
 "split": true,
 "covered_dropped": ["氧气瓶使用方法"],
 "reason": "原问题含两个可分开检索的点，且氧气瓶部分上轮已覆盖"}
```

- 兜底：LLM 失败/超时 → 退回 `rag._keyword_split(question)`（零 LLM，已有实现）；此时 a/b 直接用原话，c 走关键词切分，d 跳过。
- 规则快路径：已是陈述句、≤ 30 字、不含指代词、且会话里没有可剔除项 → 跳过 LLM（省 2s）。
- **不得**因为「有 Redis」或「没有 Redis」而省掉任何一类动作。

## 02 PPT 工坊升级

> 状态：**已完成（2026-10-24）**。实现记录与逐文件带读见 `Done/02-PPT工坊升级·实现记录.md`、`Done/02-PPT工坊升级·逐文件带读.md`。
> 来源：`research/02-PPT工坊升级.md` 话题 1–6（含百度接口取证、产物体检、本机能力实测、素材源可达性实测）；取舍结论见 `../Verdict/02-PPT工坊升级.md`。

### ① 应对什么问题

**现象一：百度 PPT LLM 的额度是"全项目共享"，不是"每用户每天 10 次"。**

- 只有一个密钥，来自 `.env`（`src/ai/ppt_baidu.py:95,114`、`src/core/config.py:46-49`）；请求体里没有任何"谁在用"的字段（`ppt_baidu.py:102-112`）；全仓无按用户/按天计数、无密钥池。
- 一个部署 = 一个 key = 一份额度 → 任何一个人点到第 N 次，其他人当天就没得用；这与"每个员工一个账号"的产品形态直接冲突。
- 用户已核实：该接口**已转为付费**（原"每日 10 次免费"政策结束），故本大点**整体移除百度实现**（裁定 1）。

**现象二：百度返回的是"整套成品"，我们只控制输入，控制不了版本与版式。**

- 官方文档：`data.pptx_url` = 「pptx 下载链接」，成品为完整演示文稿（话题 1 证据 A）；本机三份百度产物 15.9–17.4 MB、27–35 页、28–40 张内嵌图片，而大纲只有 4–6 章节 —— 页数、配图、分页全由百度决定（话题 1 证据 B）。
- 三份产物的 `theme1.xml` 主题色**完全相同**（accent1 `#78A8C9`），因为三个界面模板标签都映射到同一个 `tpl_id=102322`（`ppt_baidu.py:29-33` 的两行 TODO 从未补）（话题 2 证据 A/B）。
- 还抓到一次**内容串台**：task8 主题"安全生产法要点"，产物封面与正文却是"隧道施工安全"（与 task6 产物逐页文字一致），而代码把 `query_id/chat_id` 硬编码为 1（`ppt_baidu.py:103-104`），官方文档明确这两个字段有上下文依赖（话题 1.5）。

**现象三：现有"降级链路"质量过低，不能直接当默认链路。**

- 固定 `封面 + 目录 + N 内容页 + 结尾`，5 章节时只有 **8 页 / 40 KB / 0 张图**（`ppt_local.py`，实测）；
- 要点硬截断 `points[:5]`（`ppt_local.py:108`），超过的静默丢弃；
- 目录页 6 章节时纵向溢出页外（`ppt_local.py:86-96`，1.8+5×1.05+0.85=7.9in > 7.5in）；
- 内置三套模板在本地通道**完全一样**（只有一套深蓝+金）。

**现象四：当前 PPT 工坊只是"形式上的 Agent"。**

- P01 是**一次** `llm_client.chat()` 出大纲（`ppt_service.py:81-91`）；全流程无工具、无循环、无自检；
- P03 是固定二分支（百度黑盒 / 本地固定渲染），没有决策；
- 中间态只有 `status` 四态与 `outline` 文本，没有步骤级产物可查。

**现象五：没有账号沙箱。**

- 成品平铺在 `ppt_files/`（`u{uid}_t{tid}_{主题}.pptx`，实测 4 个文件 50 MB）；用户模板在 `knowledge_src/ppt_model/` 且**全账号共享**；无"用户素材/中间产物"目录。参照 `deep_search_pro/utils/paths.py` 的教训：数据散在多个根、各模块各拼一次路径，出过"写进 A、读的是 B"的事故。

**现象六：没有进度、没有可读日志。**

- `POST /api/ppt/{id}/generate` 同步阻塞（百度 20–60 s），`ppt_tasks` 只有 `status`（无 progress/stage/updated_at），前端 `await` 后弹 `alert`（`index.html:1840`）；日志只有自由文本，无法回答"卡在哪一步、第几页、为什么重试"。

**红线（本大点不得突破）**

1. 账号隔离与下载鉴权（00 大点）不得回归：非本人访问仍是 404/403，产物不出账号沙箱；
2. **不改 `database/schema.sql`**（表结构由 P3 管理）：进度、中间态用 Redis + 磁盘承载；
3. 现有 PPT/试卷/AI 助手功能不因移除百度而丢入口（PPT 必须仍有"能出片"的默认路径）；
4. Agent 的每一次文件写入都必须落在本账号 sandbox 内，路径不得由模型自由拼。

### ② 功能

做完之后，用户能感觉到的变化：

1. **不再受"全公司一天 10 次"限制**：默认链路是本地 Agent 生成，点几次都不会因为别人用完了而失败；百度相关入口、文案、配置全部消失。
2. **生成过程可见**：点"生成"后出现进度条（阶段名 + 页进度），并实时滚出"正在检索 / 正在选图 / 第 3 页排版 / 第 3 页自检未通过，正在修"这类工作日志；关掉页面再回来也能看到当前进度。
3. **产物质量明显提升**：封面/目录/章节页/内容页/结束页齐全，图文混排（不再是纯文字 + 金线），每页有来源标注，末页有"图片来源与署名"。
4. **可以提要求**：主题 + 详细要求（可直接传 .md）、页数、每页字数、以及"内容超了要不要允许超页超字数"。
5. **模板由自己提供**：上传自己的 .pptx 作为母版；没有模板时用内置简洁版式兜底，也能出片。
6. **自己的工作区自己管**：每个账号一个沙箱目录，能看到本次下载的图片、逐页截图、中间大纲；用完可一键清理（成品可保留）。
7. **内容有依据**：大纲与要点优先来自企业知识库（复用 AI 助手的预处理 + RAG），检索不足时才由 Agent 联网补充，来源可追。
8. **可选直连 PPT LLM（预留位）**：如果以后接入别的付费 PPT LLM，只需填一段配置、打开开关，不需要改业务代码（当前无实现，默认关闭）。

#### 3.2 总体流程与阶段划分（进度权重）

| 阶段 | 内容 | 进度权重 | 产出 |
|---|---|---|---|
| S0 | 主题预处理（复用 `query_preprocess.preprocess`） | 3% | 检索式、子查询、拆分建议 |
| S1 | 知识库检索（复用 `rag.retrieve_queries` + `format_context`） | 7% | 带来源的素材块 |
| S2 | 充分性判定（复用 `sufficiency.judge`） | 5% | 够/不够 + 缺口查询 |
| S3 | 缺口补检（**最多 1 次**） | 10% | 补充素材 |
| S4 | 大纲策划（标题/副标题/章节/每页要点/配图意图），受页数与字数约束 | 15% | `drafts/outline.json` |
| S5 | 素材采集（Openverse 图片；用户模板副本） | 10% | `images/*`、`images/sources.json`、`templates/*` |
| S6 | 逐页制作 + 自检修复（每页：渲染 → 审图 → 修补，最多 2 轮） | 40%（按页均分） | `out/{task}.pptx`、`shots/page-N.png` |

#### 3.3 账号沙箱与"路径唯一事实源"

新建 `src/core/paths.py`（仿 `deep_search_pro/utils/paths.py` 的归口模式）——**只给路径、不建目录、不写文件**，落盘显式 `ensure_dir()`：

```
user_data/ppt/{user_id}/
    templates/            本次使用的模板副本（从共享模板库复制或用户上传）
    images/               下载的图片
    images/sources.json   每张图的 license / creator / attribution / 原始 URL
    shots/                逐页截图 PNG
    drafts/               outline.json / pages.json / plan.json
    out/                  u{user_id}_t{task_id}_{主题}.pptx
    logs/{task_id}.jsonl  结构化工作日志
```

安全约束（写进实现，必须有单测）：

- 目录名只由 `int(user_id)` 与 `int(task_id)` 拼；**任何来自模型/用户的字符串只做 `basename` 处理**，禁止 `..`、`/`、`\`、盘符；
- `safe_join(root, name)`：`(root / name).resolve()` 必须仍在 `root` 内，否则拒绝；
- 图片/模板下载有类型白名单（png/jpg/jpeg/svg→仅图标用、pptx）、体积上限（图片 ≤8 MB、模板 ≤20 MB 沿用）、超时与重试上限；
- 清理端点只允许删 `templates/ images/ shots/ drafts/ logs/`（`out/` 单独开关），且路径必须通过 `safe_join`。

历史产物兼容：旧 `ppt_files/*.pptx` 仍可下载（`download_path` 先查 `user_data/ppt/{uid}/out/`，未命中再按 basename 回退到 `ppt_files/`，两条路径都做根目录校验）；不迁移历史文件。

#### 3.4 Agent 编排形态（混合式，不让模型自由跑）

**代码负责"走哪些阶段"，Agent 负责"每一页写什么、怎么排"**：

```
run(task_id, spec)                    # src/ai/ppt_agent.py，生成器，逐步 yield 事件
  S0-S3  预处理/检索/判定/补检        # 复用 01 大点已有函数
  S4     plan = llm.plan_outline(...) # 一次结构化输出（JSON），校验 sections/pages
  S5     for each page: agent.pick_images(page)   # Openverse
  S6     for each page:                            # 逐页闭环
            agent.compose(page) -> officecli batch 命令数组
            apply(batch)                            # 唯一写者：OfficeCLI
            shot = render(page)                     # officecli view screenshot
            verdict = vision.review(shot, page)     # AGNES 审图
            if not ok and fix_round < 2: agent.fix(...) ; continue
  S7-S8  收尾 + 落盘
```

为什么不用"纯自由 agent"：草案的 (2)→(7) 是**确定性流水线**，把阶段交给模型自由选会造成三类问题——① 阶段漏做（跳过充分性判定）；② 成本不可控（每阶段都可能多轮）；③ 进度条无法映射。混合式下进度条天然对齐 S0–S8，Agent 的不确定性被限制在"单页内"。

工具清单（`src/ai/ppt_tools.py`，全部受沙箱与上限约束）：

| 工具 | 签名 | 作用 | 限制 |
|---|---|---|---|
| `kb_search` | `(query: str) -> str` | 复用 `rag.retrieve_queries` + `format_context` | 单次 ≤ 6 块；不写盘 |
| `image_search` | `(query_en: str, n: int) -> list[dict]` | Openverse 检索 + 下载到 `images/` | n ≤ 8；超时 20 s；失败返回空并记日志；无图时页面走"图标/形状"版式 |
| `ppt_apply` | `(commands: list[dict]) -> str` | 转成 `officecli batch` 参数执行 | 命令白名单（add/set/remove/move/swap）；路径必须 `/slide[N]/...`；一次 ≤ 40 条 |
| `ppt_render` | `(page: int) -> str` | `officecli view <f> screenshot --page N -o shots/page-N.png` | 返回图片路径 |
| `ppt_inspect` | `(page: int) -> str` | `officecli view <f> issues --type content,format` | 返回低对比度/坏引用等结构化结果 |
| `fs_list` / `fs_read` | `(rel: str)` | 列出/读取沙箱内文件 | 只读；`safe_join` 校验；文本 ≤ 20 KB |
| `vision_review` | `(png: str, page_spec: dict) -> dict` | AGNES 看图判定：文字溢出/遮挡/对比度/要点缺失 | 每页 ≤ 2 次；`max_tokens ≥ 600`（见 3.5 的坑） |

#### 3.5 多模态配置段（AGNES 默认，可扩展）

`src/core/config.py` 新增独立段（不动主模型 `DEEPSEEK_*` / 降级 `AGNES_*`）：

```
PPT_VISION_PROVIDER=agnes                 # 预留多实现（用户后续会接别的视觉模型）
PPT_VISION_BASE_URL=https://apihub.agnes-ai.com/v1

```

实现：`src/ai/vision_agent.py` —— 独立的 `ChatOpenAI`（OpenAI 兼容），只做"看图判定"，不参与文本生成；`reasoning_content` 一律丢弃、只读 `message.content`（实测 `max_tokens=40` 时 `finish_reason=length` 且 `content` 为空，`content` 与 `reasoning_content` 必须分开处理）。

#### 3.6 逐页制作与自检

每页固定闭环（**OfficeCLI 是唯一写入者**）：

```
officecli open   out/xxx.pptx                     # 常驻，反复改同一文件
officecli batch  out/xxx.pptx --commands '[ ... ]'  # 加文本框/图片/形状/页码
officecli save   out/xxx.pptx                     # 落盘（或等 resident 自动 flush）
officecli view   out/xxx.pptx screenshot --page N -o shots/page-N.png
（AGNES 读 shots/page-N.png → 判定 ok / 需要修 + 原因）
officecli batch  ...（修补，最多 2 轮）
officecli close  out/xxx.pptx
```

审图提示词要判定四件事：① 文字是否溢出文本框/被裁切；② 图片是否与文字重叠遮挡；③ 前景/背景对比是否过低（也可用 `officecli view issues --type format` 的 `low_contrast` 交叉验证）；④ 本页要点是否与大纲一致（数量/顺序）。判定结果结构化：`{"ok": bool, "problems": [...], "fix_hints": [...]}`。

#### 3.7 素材：图库接入（Unsplash 默认 / Openverse 备选）

- 检索：用户的主题是中文 → 先由 LLM 生成**英文关键词**（3–5 个），再按 `PPT_IMAGE_PROVIDER` 查图：
  - `unsplash`（默认，裁定 13）：`GET https://api.unsplash.com/search/photos?query=...&per_page=N&orientation=landscape`，头 `Authorization: Client-ID <UNSPLASH_ACCESS_KEY>`；取 `urls.regular`、`user.name`、`links.html`、`links.download_location`；
  - `openverse`（备选）：`GET https://api.openverse.org/v1/images/?q=...&license=cc0,pdm,by&page_size=...`；
- 授权：返回体自带授权字段（Unsplash：`unsplash license` + 摄影师名 + `links.html`；Openverse：`license/creator/attribution`），逐条落 `images/sources.json`，末页"图片来源与授权"按此渲染；两类都必须带署名；
- **可达性实测**：Openverse 本机 0/4 成功（超时），Unsplash 4/5（~1.8 s）、图片可下载 → 默认用 Unsplash；两者都必须：超时 30 s、重试 1 次、失败即降级（该页改用形状版式），**不允许因图片失败让整单失败**；Unsplash Demo 配额 50 次/小时，`x-ratelimit-remaining ≤ 3` 告警、401/403/429 直接降级；
- 图标兜底：Iconify API（`https://api.iconify.design/tabler.json?icons=...`，实测 200）与 jsDelivr（`lucide-static`，实测 200）取 SVG，MIT/Apache 无授权风险；
- 每页图片数上限 2 张、单图 ≤8 MB、总下载 ≤20 张，超出即停。

## 03 意图识别（回答前门禁）

> 状态：**已完成（2026-10-24）**。裁定见 `Verdict/03-意图识别.md`（裁定 1–8），调研见 `research/03-意图识别.md`，实现与真机实测见 `Done/03-意图识别·实现记录.md`、`Done/03-意图识别·逐文件带读.md`。

### ① 应对什么问题

**现象**：用户问"日常/元问题"，系统当成知识题去检索。

- 2026-10-24 实例：问「不用检索,你现在有自我维护和丰富知识库的能力吗」——这是**对助手能力/边界的询问**（且显式说不用检索），
  但 `src/routers/chat.py` 的 `_prepare()` 起手就 `query_preprocess.preprocess()`，随后按 `full` 无条件检索，用户看到"我把闲聊拿去查资料了"。
- 同一次还叠加了环境故障：`retrieve_queries` 抛 `OSError: [Errno 22] Invalid argument: '.env'`（盘掉线→CWD 失效），
  而检索段**没有兜底** → ASGI 500、SSE 断流、整轮回答丢失（本大点一并修掉）。

**要解决的**：① 回答前判「闲聊 / 知识问答」；② 闲聊跳过预处理与检索直答；③ 显式"不用检索"优先；④ 判定失败保守走知识问答；⑤ 检索失败降级而不是整轮失败；⑥ 判定与降级都可审计。

### ② 功能（用户视角）

| 场景 | 现在的表现 | 升级后 |
|---|---|---|
| 「你是谁 / 在吗 / 谢谢 / 你能上传什么」 | 走预处理 + 全量检索，5~45s，可能答非所问 | 判定 `chat` → **1s 内出首字**，状态行显示"闲聊（未检索）"，不出来源条 |
| 「不用检索，你现在有自我维护知识库的能力吗」 | 同上（还被当知识题） | 提示词识别"不用检索" → 走闲聊直答（由裁定 1 的提示词承担，无代码规则） |
| 「第一问」「那…呢」（指代追问） | 靠检索碰运气 | 判定输入带**上一轮问题 + 上一轮回答前 200 字** → 落 `knowledge`，走补检链路 |
| 「高处作业几米算高处」 | 正常检索 | 不变（判定 `knowledge`） |

| 想临时回到旧行为 | —— | `CHAT_INTENT_ENABLED=false` 一键回到 01 收官版本 |

### ③ 实现功能的技术方案

#### 3.1 数据流

```
POST /api/chat（SSE）
  └─ intent.detect(question, history)                    [新增，1 次 LLM，≤8s]
       输入：当前问题 + 上一轮 user 问题全文 + 上一轮 assistant 回答前 200 字（总 ≤600 字）
       输出：{label: chat|knowledge, reason, ms, model, degraded?}
       ├─ chat  ──► mode="chat"
       │              ├─ 跳过 query_preprocess / retrieve_queries / chat_agent
       │              ├─ llm_client.chat_stream(chat_assistant 提示 + 最近 3 轮，不注入资料)
       │              ├─ references=[]、不 _merge_sources()、不写 conv_rag_cache
       │              └─ user 消息 refs.intent 落库 → meta{intent,intent_ms,sources=0}
       ├─ knowledge / 判定失败（→ knowledge）──► 既有 _prepare()
       │              ├─ preprocess（01 现状）
       │              ├─ 检索四态 full/cache/incremental/context
       │              └─ 检索段 try/except → 失败则 context="" + degraded{kind:"retrieval"}
       └─ CHAT_INTENT_ENABLED=false ──► 完全跳过 detect（等于 01 收官行为）
```

#### 3.3 关键实现点

1. **判定只调一次**：`llm_client.primary_chat_model`（复用单例，不新建客户端），`temperature=0`、`max_tokens=80`、`timeout=CHAT_INTENT_TIMEOUT`；首调建连 7.45s 实测值 → 超时按裁定 4 回退，不会挂死整轮。
2. **解析容错**：`re.search(r'"(?:intent)"\s*:\s*"(chat|knowledge)"', out)`；命中即取；`chat`/`knowledge` 之外一律 `knowledge + degraded`。
3. **历史注入**：`_history_hint()` 取最后 1 条 user + 紧随的 assistant（取前 200 字），拼成"上一轮：问题 / 回答摘要"，总长截到 600。
4. **闲聊 system**：`chat_assistant` 提示明确"你未被注入知识库资料；涉及法规/作业规程等业务问题时，引导用户直接提问以获得有依据的回答"，防止闲聊路径被用来套知识答案。
5. **检索降级**：包住 `retrieve_queries` / `retrieve_more` / `get_vectorstore()`；异常只 `WARNING` 一行（类型 + 首 120 字），**不透传敏感信息**；`context=""` 时给 system 追加降级说明。
6. **缓存隔离**：闲聊轮不 `put_blocks`、不 `touch`；知识轮行为不变。
7. **审计兼容**：闲聊轮 `refs = {"intent": {...}}`（无 `preprocessed`）；`build_rounds()` 用 `intent` 也生成一条 round，`sources=0`。

## 04 知识贡献升级 + Agent 知识贡献渠道

> 状态：**已完成（2026-10-26）**。裁定见 `Verdict/04-知识贡献升级.md`（裁定 1–13），现状与实测见 `research/04-知识贡献升级.md`（§1–§9），实现与真机验证见 `Done/04-知识贡献升级·实现记录.md`、`Done/04-知识贡献升级·逐文件带读.md`。

### ① 应对什么问题

**（1）模块本身完整但"冷"且与助手不通。** 全库仅 2 条贡献（1 条入库 14 块、1 条测试垃圾），714 个普通用户几乎没人用；贡献入库后助手**能检索到**，但引用显示内部 id `contrib_1`、点「查看原件」必然失败（`kb/doc` 只放行 `knowledge_src` 四类）；分不清官方源与用户贡献；助手也无法把"资料不足"反馈给贡献模块。

**（2）没有非人类用户通道。** 认证只有"用户名+密码→JWT"、角色只有人类岗位；提交只收 multipart 文件；`timeline.operator_id` 外键指向 `users` —— Agent 没有身份，contributor 与审计都说不清。

**（3）现有格式与治理不支撑"把文件变成可用知识"。** 只支持 md/txt/docx/pdf；`python-docx` 只读段落**丢表格**；PDF 只取文本层；没有 `.html`；清洗后门槛 300 字、无查重、无版本。

**（4）用户已定的产品形态**（2026-10-25 草案 + 2026-10-26 两轮确认）：通过审核的贡献**落进 `knowledge_src` 四类**（前端政策文件可搜、引用可点开）；**Agent 自行网搜、自行总结成 md** 再走人审；接入 **MinerU CLI** 解决表格；贡献 **≥1000 字**；同名/同标题由管理员以"标题重复"驳回；**本期不做下架**；方法论放 `team/Methodology/`、实体不入库只推 `.example`。

### ③ 实现功能的技术方案

#### 3.1 数据流

```
【人工贡献】
POST /api/knowledge-contrib (md/txt/docx/pdf/html ≤10MB)
  → 解析文本（原样存 DB）→ 待审核 → 通知 admin
  → admin: 预筛(AI) + 原件预览(GET /{id}/file) + 查重红灯 + 转换预览
  → 审核通过:
       kb_convert.to_markdown(file)         # MinerU 优先，失败兜底
       → kb_govern.clean_text → quality_check(≥1000 字)
       → contrib_store.plan_target()        # 归一化文件名 + 双重查重
       → 写 knowledge_src/{type}/.tmp_{uuid}.md
       → knowledge.upsert_file(...)         # doc=stem, source=相对路径, metadata{contrib_id,origin}
       → rename 成最终名 → DB: 已入库 / md_path / chunk_count / convert_by → 通知

【Agent 贡献】
回答结束（异步）→ 判定"知识库资料不足"（与 Redis 缓存不足区分）
  → agent_runs 建任务 → 读 Methodology.md（只在工具内注入）
  → Playwright 按方法论搜集（硬边界：禁 file/内网/本机端口；限额：站点≤3/页≤8/总≤8MB/≤600s）
  → LLM 总结成 md（首行标题 + `> Agent 贡献（模型） · 来源 URL…`）
  → 提交待审核（source_kind=agent, source_agent_id, origin_urls）
  → 与人工贡献共用审核流（裁定 8：无自动入库）
```

#### 3.3 关键实现点

1. **MinerU 调用**：`uv tool install mineru` 独立环境；`KB_MINERU_CMD` 默认 `mineru`；PDF 必带 `--pages all`、`--tier basic`（表格模型），docx 走 `--tier flash` 原生解析；输出只取 md；超时/非零 → 兜底并记 `converted_by=fallback`。
2. **绝不装进后端解释器**：实测 dry-run 会把 `starlette 0.52.1→1.10.0`、`pydantic→2.14.1`，直接破坏 FastAPI。
3. **文件名归一化**：保留中文、去扩展名与非法字符、截断 60 字；同名时不做自动加后缀（会绕过"标题重复"判定），而是**直接报冲突**让管理员驳回。
4. **查重两路**：目录同名文件 + 标题集合（`kb/list` 全量 + DB 已入库标题），任一命中即红灯。
5. **单文件入库**：`doc=stem`、`source=knowledge_src/{type}/{stem}.md`（相对路径，反斜杠归一）、metadata 加 `contrib_id`/`origin`；**不能**再写 `user_contrib`（否则 `kb/doc` 打开失败）。
6. **回滚顺序**：临时文件 → 入库成功 → rename → 更新 DB；失败删临时文件、状态不变。
7. **Agent 硬边界**：URL 校验（scheme 白名单 http/https；禁 `file`、`localhost`、`127.*`、`10.*`、`172.16-31.*`、`192.168.*`、`::1`），`KB_FETCH_DENY_HOSTS` 可加；越界记 `agent_runs.status=rejected`。
8. **方法论注入范围**：只进 scout 的提示词；**不进**主问答 system prompt（保 01/03 时延与判定口径，裁定 9）。
9. **异步触发**：`chat.py` 落库后用后台线程 + 幂等键（conversation_id + 问题哈希）避免重复采集；失败只记日志，不影响已回答的内容。
10. **旧块清理**：`--dry-run` 默认，输出将删的 doc/块数；`--apply` 才 `collection.delete(where={"doc": ...})`。
