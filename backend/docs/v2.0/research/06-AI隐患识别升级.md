## ① 圈不准：彻查结论

### 1.1 现场素材

| 项 | 值 |
|---|---|
| 原图 | `37514008b0464dd9a78c54664c8bee85.jpg`，**4096×3072**，2.0 MB |
| 项目画框产出 | `035a6e7983cd49ab81a229e1862935a9_boxes.png`，**19.7 MB** |
| 送模型尺寸 | 等比缩放到长边 **1024 → 1024×768**，`_scale=(4.0, 4.0)` |

### 1.2 三组对照实验

| 实验 | 方法 | 结果 |
|---|---|---|
| **A 合成对照** | 画 1024×768 纯色块（红/绿/蓝，位置已知），问模型要框 | IoU **0.98 / 0.94 / 0.94** —— 模型坐标约定正确（就是送它那张图的像素系），我们的缩放与 `×scale` 还原数学无问题 |
| **B 重复性** | 同一张真图连问 3 次 | 返回条数 **3 / 5 / 4**，条序会变，`location` 有时 `null`；同一物体三次框的 y1 = 365 / 382 / 360（1024 系） |
| **C 坐标口径** | 同一张图要求输出 0~1 归一化，再换算回 1024 系 | 与像素口径**几乎一致**（木板 `[0,368,334,471]` vs `[0,365,315,470]`）→ 不是格式/单位问题 |
| **D 绘图脚本** | 用**人工真值坐标**调 `draw_hazard_boxes(**原图坐标**)` | 4/4 框落在正确位置 → 脚本坐标逻辑正确 |

### 1.3 与人工真值的偏差（1024 系，×4 = 原图）

| 目标 | 模型框 | 人工真值 | IoU | Δy1（1024） | Δy1（原图） |
|---|---|---|---|---|---|
| 木板 + 白盒 | `[0,365,315,470]` | `[11,410,294,480]` | 0.47 | **-45** | -180 px |
| 中间长木板 | `[380,450,835,768]` | `[389,539,846,765]` | 0.68 | **-89** | -356 px |
| 黑色波纹管 | `[540,560,1024,670]` | `[737,567,1024,655]` | 0.47 | -7 | -28 px |
| 围挡杂草带 | `[0,300,1024,450]` | `[0,348,1024,450]` | 0.68 | **-48** | -192 px |

**规律**：框整体「**往上抬、往外扩**」，会把沟渠、地面、围挡带进框内；`波纹管` 左边界比真值多 197 px（1024 系），把沟渠当成了管子。

### 1.4 结论（三段论）

1. **不是绘图脚本的坐标错误**：合成对照 IoU≈0.95、归一化口径一致、人工真值能画准，三点互证。
2. **渲染参数写死是“看不见/字小”的直接原因**：`boxes.py` 里 `BOX_WIDTH = 4`、`_font(20)` 是固定像素——4096 宽图上字只占 **0.49%**，缩到 700 px 预览约 **3.4 px**；4 px 线缩到预览 1.4 px，几乎透明。观感上就像“框飘在别处”。
3. **模型本体的定位能力偏松 + 系统性上偏**：同图三次结果条数/顺序/坐标都变，框普遍比真值高 28~356 px 且偏大。这是本次调研发现的**主要质量瓶颈**，靠调缩放参数解决不了。

### 1.5 对“重叠”的修正（用户 2026-11-05 指正）

> 原调研曾建议“只给物类画框、场景类不画”，理由之一是框重叠不好看。**该结论作废**。
> 实际现场必然出现多个「物」类隐患框重叠（例如木板压在波纹管上），**重叠必须照画**：
> - 重叠不是缺陷，是“同一区域多风险”的真实表达；
> - 半透明填充天然让重叠区颜色叠加变深，反而强化“这里风险集中”的信息；
> - 视觉混乱通过**筛选/聚焦**（见 ②）而不是“少画框”来解决。

## ② 可读性与筛选交互

### 2.1 渲染实测（同一批真值坐标，4096×3072 原图）

| 变体 | 耗时 | 体积 |
|---|---|---|
| v0 现状：4 px 线 / 20 px 字 / 无填充 / **PNG** | 1.24 s | **19.73 MB** |
| v1 自适应：8 px 线 / 64 px 字 / 无填充 / **JPG q90** | 0.23 s | **2.49 MB** |
| v2 同上 + 同色透明填充 **18%** | 0.23 s | 2.48 MB |
| v3 同上 + 填充 **28%** | 0.23 s | 2.50 MB |

- 渲染开销可忽略（0.23 s），体积从 19.7 MB 降到 **2.5 MB**（8 倍），纯属输出格式问题；
- **填充透明度**：18% 在明亮场景（白木板）偏淡；28% 既醒目又不遮细节。建议默认 **25%**，悬停/选中 **50%**；
- 线宽/字号建议按图宽自适应：`lw = max(4, W/512)`（4096 → 8 px）、`label = max(20, W/64)`（→ 64 px），标签加 90% 不透明底色保证可读。

### 2.2 交互需求（用户提出）

1. 框内加**同色半透明填充**（玻璃效果）→ 已实测可行；
2. 解释栏支持**筛选**：只看某类别 / 只看某等级；
3. 点解释栏某条 → 图上对应框**高亮**，其余**淡化或隐藏**。

### 2.3 关键架构发现：现在没法“只显示某条”

当前实现是**服务端把框烘焙进 PNG**（`draw_hazard_boxes` → `<原图名>_boxes.png`），前端只拿到一张静态图。
一旦要“按条件显示/隐藏/高亮”，烘焙图就不够用了——隐藏某条只能重画一张（每切一次筛选项 = 一次请求 + 2.5 MB 传输）。

**可选方案对比**：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A（推荐）前端 SVG 叠加** | 接口已有 `analysis.hazards[].location`；前端在 `<img>` 上盖一层 `<svg viewBox="0 0 原图宽 高">`，用 `<rect fill-opacity>` + `<text>` 绘制 | 筛选/高亮**零请求**、可动画、可无障碍；图片用原图即可；重叠天然叠加 | 前端要做一层渲染逻辑；导出时仍需服务端图 |
| B 服务端按条件重渲染 | 每次筛选传 level/category 参数重画 | 前端简单 | 每次 0.23 s + 2.5 MB；交互卡顿，筛选无法做悬停预览 |
| C 烘焙图 + 遮罩变暗 | 只把非选中项“盖一层灰” | 改动最小 | 无法真正隐藏某条（像素已固化），筛选语义做不到 |
| D Canvas 重绘 | 前端 Canvas 自绘 | 性能好 | 与 A 等价但代码更多，可访问性差 |

**结论（2026-11-05 拍板）**：走 **A**（前端 SVG 叠加）。服务端 `boxes.png` 保留，仅用于「上报后存档 / 下载」场景，输出格式改 JPG。

**数据契约（A 方案）**：接口返回已够用，无需改造——`analysis.hazards[]` 里已有 `level / category / description / suggestion / location`；原图宽高由前端 `img.naturalWidth/naturalHeight` 取（或后端补 `image_width/image_height` 更稳）。**注意**：现有 `location` 是**原图坐标**（后端已按 `_scale` 还原），前端 `viewBox` 直接用原图宽高即可，不需要再乘比例。

### 2.4 交互设计草案

```
解释栏顶部： [全部] [等级: 重大|较大|一般|轻微] [类别: 人的不安全行为|物的不安全状态|环境的不安全因素|管理缺陷]
解释栏每张卡片： 点击 → 聚焦该条（图上对应框 50% 填充 + 4px 描边 + 标签常显；其余框 8% 填充/淡化）
                 再次点击 → 取消聚焦
悬停卡片 → 图上对应框轻微放大描边（不改变其它框）
图上悬停某框 → 对应卡片高亮并滚动到可视区（双向联动）
```

细节约束：
- **框与卡片用 `hazard_index` 绑定**，不依赖数组顺序（模型每次返回顺序会变，见 §1.2-B）；
- 重叠时绘制顺序 = 等级优先级（重大 > 较大 > 一般 > 轻微），选中项提到最上层（SVG 内 `appendChild` 重排）；
- 标签避让：同一 y 带内的多个标签水平错开（避免重叠成黑块）；
- “隐藏”与“淡化”都要有：筛选=真隐藏；聚焦=淡化，避免页面跳变；
- 颜色（**已由 `Verdict/06` 裁定 1 定稿**）：**色相 = 类别，明度 = 等级**；边框加白色 1~2 px 外描边；边框粗细随等级递增（重大 12 px / 较大 9 / 一般 7 / 轻微 6），色板唯一事实源见裁定 1。


### 2.5 拍板结果（2026-11-05）

| 议题 | 结论 | 裁定 |
|---|---|---|
| 框色主维度 | **类别定色相、等级定明度**（4 类别 × 4 级深浅，白色外描边） | 裁定 1 |
| 聚焦时其余框 | **淡化到 6~8%**（不隐藏） | 裁定 2 |
| 标签 | **默认只显示序号**，悬停/聚焦才展开文字 | 裁定 3 |
| 渲染与保存 | 上报前**前端 SVG** 渲染；上报时**后端烘焙**并落盘 | 裁定 4 |
| 暗背景可见性 | 白色外描边 + 边框粗细随等级递增（设计约束，已并入裁定 1） | — |
| 标签越界 | 自动内收/翻转（设计约束，已并入裁定 3） | — |

### 2.6 原型验证（可运行的静态页，非项目代码）

用 SVG 叠加写了一个最小原型（原图 + `<svg>` + 筛选 chips + 卡片联动），三种状态截图：

| 状态 | 观感 |
|---|---|
| 全显示 | 4 个框带半透明填充，**两块木板与杂草带重叠处自然加深**，标签（64px + 同色描边）可读 |
| 聚焦第 3 条（长木板） | 选中框填充 50% + 14px 描边，其余框淡到 6%，卡片同步变暗并加描边 —— 一眼能看出选的是哪块 |
| 类别筛选=管理缺陷 | 图上只剩杂草带，列表只剩 1 条；但**灰底（深色杂草）上 22% 填充几乎看不见** |

原型暴露的两个新问题（要在定方案时收进设计）：

1. **暗背景可见性**：同一 22~28% 透明度，在浅色木板区域很清楚，在深色杂草/阴影区几乎不可见。
   → 需要「白色 1~2 px 外描边 + 同色内描边」双层描边，或按区域平均亮度自适应提高填充（30~35%）；
2. **标签越界**：位于图左边缘（x=0）的框，标签文字被裁掉一截。
   → 标签自动内收（`x1 < 标签宽/2` 时右移），y 方向同理。

## ③ 圈隐患后的图片：全业务可视（新调研）

### 3.1 现状取证（代码级）

| 环节 | 现状 | 结论 |
|---|---|---|
| 图片上传 | `POST /api/uploads/image` → 落盘 `uploads/`，返回 `/uploads/xxx.jpg` | 只有**原图**入库 |
| AI 识别 | `POST /api/vision/hazard` 生成 `<uuid>_boxes.png`（标注图），**只在响应里返回** `boxes_url` | 标注图**从未落库**，刷新即失联 |
| 上报 H01 | 前端提交 `image_urls = [原图 URL...]`（`index.html:1376`） | 隐患记录里只有原图 |
| 详情 H03 | `GET /api/hazards/{id}` **没有任何权限校验**（任何登录用户可看） | 不是"权限不让看"，而是**标注图没存** |
| 列表 H02 | `HazardOut.image_urls` 原样返回 | 列表也没有标注图 |
| 详情前端 | 只渲染 `image_urls` 与 `rectify_images`（`index.html:1396-1398`） | 管理员/安全员只能看到原图 |
| 静态托管 | `/uploads` 是 `StaticFiles` 匿名挂载 | **知道 URL 即无需登录可访问**（既有风险，本次一并评估） |

**根因一句话**：现在没有任何字段承载「AI 标注图」，也没有字段承载「隐患坐标/分析结论」。上报者之所以"能看见"，只是因为他在**同一次会话**里还没刷新页面。

### 3.2 目标

上报者、管理员（审核/派单/验收）、被指派责任人（安全员）在**列表、详情、整改、验收、导出**任一面都能看到同一份「原图 + 标注图」，且标注图与上报时所见一致。

### 3.3 存储方案对比（约束：不改 `schema.sql` 既有表）

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 塞进 `hazards.image_urls` | 把标注图 URL 追加进同一 JSON 数组 | 零 DDL、详情页现有渲染自动生效 | 原图/标注图混在一个数组里，无法区分；**坐标与分析 JSON 无处存**，前端筛选/复核做不到 |
| **B 新增表 `hazard_ai_analysis`（推荐）** | `hazard_id / model / raw_json / boxes_json / annotated_url / generated_by / created_at`；`boxes_json` 存 hazards（含 location/level/category） | 不动既有表；坐标可复用（前端 SVG 复核、二次筛选、后续训练集）；审计留痕 | 需要迁移脚本建表；H03 要 join |
| C 给 `hazards` 加列 | 加 `ai_analysis JSON` | 查询简单 | **违反「不改 schema.sql 主表」铁律**（04 已多次强调） |
| D 只存标注图 | 存图不存坐标 | 最简单 | 管理员只能看死图，无法筛选/复核；模型换版后无法重画 |

### 3.4 标注图由谁画（决定 4：上报前前端渲染、上报后保存）

| 方式 | 说明 | 评价 |
|---|---|---|
| **① 后端烘焙（推荐）** | 上报请求带 `boxes_json` + 样式参数；后端用 PIL 按**与前端 SVG 同一张配色表**画图，存 JPG（≈2.5 MB） | 图质稳定、可压缩、无需前端 4000px canvas；复用并改造现有 `boxes.py`（加填充/自适应字号/双层描边）；前后端共用一个样式配置模块即可保持一致 |
| ② 前端 canvas 导出 | `html-to-image` / 手写 canvas 合成后上传 | 所见即所得；但字体渲染差异、超大图内存、导出体积不受控 |
| ③ 只存坐标，谁看谁画 | 详情页也走 SVG 叠加 | 零存储；但导出/打印/推送（消息卡片、PPT）场景没有图 |

**推荐**：预览用 ①（前端的 SVG）+ 保存用 ①（后端烘焙），样式参数集中在一处；③ 作为详情页的"可交互复核"增强（有坐标时优先 SVG，缺图时退回静态图）。

### 3.5 接口与数据改动草案（B + ①）

```
新增表（迁移脚本，不动 schema.sql 既有表）：
  hazard_ai_analysis(
    id, hazard_id FK, model, boxes_json MEDIUMTEXT, raw_json MEDIUMTEXT,
    annotated_url VARCHAR(255), generated_by VARCHAR(16), created_at

```

### 3.6 权限与越权（既有问题，一并评估）

- `/uploads/*` 目前**匿名可读**：只要拿到 URL（例如截图外泄、日志、前端源码），未登录也能看图。
- 三条可选路线：① 维持现状（内网自用可接受，写进安全说明）；② 改为带签名的临时 URL（`/api/files?token=`）；③ 走鉴权代理（`/api/hazards/{id}/image/{idx}`，校验当前用户是否与隐患相关）。
- 建议：本期先做 ③ 的**最小版**——为标注图/原图提供带隐患 id 的鉴权入口，静态 `uploads` 继续保留（兼容旧数据），并在文档里明确"旧 URL 仍可访问"。

## ④ 知识库联动：隐患识别 Agent 化（新调研）

### 4.1 需求（用户 2026-11-05）

1. 隐患识别从「API 工作流」改成 **Agent**（下文称"隐患识别 agent"）；
2. agent 找到隐患点后，**复用 AI 问答的 RAG 链路**检索该隐患的处理知识，用它来写解释列表每条下面的「建议」，不再由视觉模型直接编；
3. 若检索发现知识库缺料，**复用 AI 问答的网搜链路**（04 的 `agent_scout` + 人工审核入库）；
4. 网搜总结出的知识文档同样走管理员审核，通过后进 `knowledge_src` 四类目录。

### 4.2 现状可复用资产（代码级）

| 能力 | 现有实现 | 复用方式 |
|---|---|---|
| 混合检索 | `src/ai/rag.py: retrieve_queries(queries)` → 块（含 `doc/chapter/source/rerank_score`） | 直接调用；实测见 4.3 |
| 查询改写/预处理 | `query_preprocess` + `sufficiency`（01 大点） | 可用作"隐患描述 → 检索式" |
| 网搜补料 | `agent_scout.run_sync()`（60s 同步，04 v1.4）/ `kick_off()`（异步） | 缺口时二选一 |
| 贡献入库 | `agent_contrib_service.submit_agent` + 管理员审核 → `knowledge_src/` | 直接复用 |
| 会话缓存 | `conv_rag_cache`（Redis，滑 TTL） | 隐患识别按"图 hash"缓存可选 |

### 4.3 真实检索实测（4 条隐患，本机真跑）

| 隐患描述 | 命中块 | 耗时（温） | Top1 相关度 | 可用性判断 |
|---|---|---|---|---|
| 木板/纸盒散落未定置 | 4 | — | **0.916**（`shd-proc-check-202507` 「11.材料堆放：分类存放整齐，有标识，并有现场规划图」）；0.874（「现场材料堆码凌乱…」） | **可直接支撑建议** |
| 波纹管裸露未埋地/防护 | 4 | 2.7s | **0.877**（`shd-proc-check-202405` 「5.电缆敷设规定：直埋电缆埋深≥0.7m、上下铺 5cm 细砂、上覆硬质保护层；架空需绝缘子固定」） | **强相关，能给出可执行做法** |
| 围挡底部杂草/杂物堆积 | 4 | 1.3s | 0.613（「1、文明施工…材料堆码凌乱」）；其余 0.25/0.23 | **弱相关**：只到"文明施工"层面，无"清理频次/责任"条款 |
| 沟渠边缘无防护/无警示 | 4 | 1.0s | 0.542（事故整改措施）；0.493（高处作业）；0.467（事故原因） | **覆盖不足**：讲的是高处/洞口，不是沟渠临边 |

> 首条查询耗时 156.9s 是**冷启动**（加载 bge 嵌入 + BM25 语料 + 重排模型）；服务端已有 `warmup`，温态每查询 1~3s。

**结论**：
- 对"物"类常见隐患（材料堆放、电缆敷设），RAG **能给出条款级建议**（还有文件名与章节可引用）；
- 对"环境/管理"类（杂草、沟渠临边），知识库确实偏薄 —— 这正是"缺口 → 网搜补料 → 人审入库"该发挥作用的场景；
- 冷/温差异巨大：**必须在服务启动时预热**（已有），且 agent 侧要设单查询超时（建议 8s）。

### 4.4 Agent 架构三选一

| 方案 | 流程 | 时延（温） | 优点 | 缺点 |
|---|---|---|---|---|
| **A 全 Agent（LLM 自主循环）** | 视觉 → 把 hazards 交给 LangChain agent → agent 自己决定调 `search_kb` 几次、改写查询、必要时 `report_gap` → 输出最终 JSON | 视觉 10~30s + 4~8 次工具往返 ≈ **20~40s** | 灵活、能自主改写查询、天然"agent 化" | 时延与成本不可控；同图两次结果可能不同（复现性差）；调试难 |
| **B 混合编排（推荐）** | 视觉（确定性）→ 每条隐患构造 1 条检索式（可复用 `query_preprocess`）→ **并发** RAG → 一次 LLM 汇总（每条建议 + 引用）→ 缺口判定 → 缺口走补料 | 视觉 10~30s + 并发检索 2~3s + 汇总 5~8s ≈ **20~40s** | 结构确定、引用稳定、可测试；缺口判定有明确阈值 | "Agent 味"弱一些，需要在文档里讲清"确定性编排 + 工具化"的理由 |
| **C 只注入检索结果** | 视觉 → 检索 → 把块拼进 prompt，模型自由写建议 | 同上 | 改动最小 | 无法保证每条建议有引用；无法触发补料；等于没 agent 化 |

**推荐 B**，并把外层包装成"隐患识别 Agent"（工具集：`search_kb` / `report_knowledge_gap`；编排器负责并发与预算）。理由：这类任务**步骤是确定的**（先看图、再查每条、再汇总），让 LLM 决定"查几次"只会带来抖动；而"Agent"的实质是**有工具、能补料、有边界**，B 全都有。

### 4.5 缺口判定与补料策略

- **阈值**：Top1 `rerank_score < 0.65` 或命中 0 块 → 判定"依据不足"（实测：有料 0.88~0.92，无料 0.54~0.61，0.65 落在空档）；
- **补料方式**（需拍板）：
  - 同步（`run_sync`，60s）：识别总时延可能到 90~100s；
  - 异步（`kick_off`）：识别结果先返回，该条建议标注「依据不足，已提交后台补充」，审通过后下次识别可用；
- **回执**：复用 04 的三态回执（submitted / insufficient / failed），避免"假上报"。

### 4.6 输出契约（建议）

```json
{"hazards": [{
   "index": 1, "level": "一般", "category": "物的不安全状态", "location": [..],
   "description": "现场地面散落两块木板及一个白色纸盒…",
   "suggestion": "材料分类存放并设置标识（依据《…》11.材料堆放）",
   "refs": [{"doc": "shd-proc-check-202507", "chapter": "11.材料堆放", "score": 0.916}],
   "grounded": true,            // false = 该条知识库无依据（缺口）
   "gap_note": "知识库缺少沟渠临边防护条款，已提交补充"
}]}
```

- `grounded=false` 时，前端「建议」小字旁显示黄色提示"知识库暂无依据，已提交补充"；
- `refs` 供前端做角标/悬浮引用（与问答页的引用样式一致）；
- 视觉模型的 `detected/summary` 与坐标保持原样，不改。

### 4.7 待拍板（下一条）

1. 缺口补料用**同步（60s 阻塞）**还是**异步（先出结果，后台补）**？
2. 「建议」是否**必须带引用**（无依据就不写，只提示"暂无依据"），还是允许"通用建议 + 标注未引用"？
3. 架构选 **A 全 Agent** 还是 **B 混合编排**（推荐）？

### 4.8 验收口径草案

1. 对"材料堆放""电缆敷设"这类有料的隐患，建议必须能追到 `doc#chapter`，且人工抽查 10 条中 ≥8 条"照做即可"；
2. 对无料隐患（杂草/沟渠），必须出现 `grounded=false` + 缺口提示，不得编造条款号；
3. 温态总时延 ≤ 40s（视觉 + 并发检索 + 汇总），单查询超时 8s，超时降级为"无依据"；
4. 缺口补料走 04 的同一人工审核流，审核通过后**同一条隐患重新识别能命中新知识**；
5. 同图两次识别：`level/category/description` 允许模型抖动，但 `grounded/refs` 必须一致（同一知识库、同一查询，结果应稳定）；
6. 视觉链路（坐标、框、等级）与本文档 ①②③ 的裁定不冲突。

## ⑤ 验收口径（渲染与交互）

1. 4096×3072 图上：线宽 ≥ 8 px、标签 ≥ 64 px，缩到 1500 px 预览仍清晰可读；
2. `boxes` 输出从 PNG 改 JPG，单张 ≤ 3 MB（现状 19.7 MB）；
3. 框内同色填充默认 25%，重叠区颜色自然加深（不做去重、不做裁剪）；
4. 前端 SVG 叠加与后端 `location` 坐标一致（同一张图，SVG 框与烘焙图框逐像素对齐）；
5. 解释栏筛选（等级/类别）与聚焦高亮：切换无请求、无闪烁，响应 < 50 ms；
6. 卡片 ↔ 框双向联动；框与卡片用索引绑定，模型换顺序不错位；
7. 场景类（沟渠/杂草）框保留，但与物类框视觉可区分（标签前缀/图标）；
8. 无 AI 结果或 `location=null` 时，卡片正常显示、图上不画框，且不报错。
