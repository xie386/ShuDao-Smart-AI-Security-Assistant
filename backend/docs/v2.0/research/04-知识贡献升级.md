## 1. 模块设计（代码事实）

### 1.1 链路

```
POST /api/knowledge-contrib（multipart：title / doc_type / intro + file）
  → 扩展名白名单 .md/.markdown/.txt/.docx/.pdf，≤10MB，正文解析后 ≥50 字
  → 存盘 uploads/kb_contrib/{uuid}{ext}
  → content = 解析出的全文（md/txt 双编码、docx 用 python-docx、pdf 用 pymupdf）
  → knowledge_contributions（status=待审核）+ timeline「提交」
  → 通知全部 admin（Redis 队列，Redis 不可用则降级不阻塞）
GET  /api/knowledge-contrib              列表（admin 看全部可筛状态；其他人只看自己）
GET  /api/knowledge-contrib/{id}         详情（本人或 admin）+ /timeline
POST /api/knowledge-contrib/{id}/review-preview   AI 预筛（仅 admin，不写库）
POST /api/knowledge-contrib/{id}/review          审核（仅 admin）
  ├ 通过：kb_govern.clean_text + quality_check（正文≥300 字 / 重复段落≤40% / 乱码≤5%）
  │        → SPLITTERS[doc_type] 分块（doc="contrib_{id}"、source="user_contrib"）
  │        → knowledge.upsert_chunks（稳定 ID 增量写，不重建）
  │        → status=已入库、chunk_count=n、review_by/review_note
  └ 驳回：status=已驳回 + review_note
  → 通知贡献者
GET  /api/knowledge-contrib/review-standard       判定标准原文（docs/v1.0/施工安全领域文件鉴别判定标准.md，已核实存在）
```

### 1.2 数据模型

| 表 | 字段 | 缺什么 |
|---|---|---|
| `knowledge_contributions` | id / title / content(MEDIUMTEXT) / file_intro / file_path / doc_type(laws·procedures·plans·cases) / contributor_id / status(待审核·已入库·已驳回) / review_note / review_by / chunk_count / created_at / updated_at | 无版本号、无有效期、无来源系统/Agent 标识、无内容指纹（去重键）、无下架状态、无适用区域 |
| `knowledge_contrib_timeline` | id / contrib_id / action / operator_id(FK users) / note / created_at | `operator_id` 只能指向人类用户；无"触发方"（人 / Agent / 定时任务）区分 |

### 1.6 支持贡献什么文件（代码事实）

**白名单三件套**（`src/services/knowledge_contrib_service.py`）：

| 项 | 值 | 位置 |
|---|---|---|
| 扩展名 | `.md` / `.markdown` / `.txt` / `.docx` / `.pdf` | `_ALLOWED_EXTS`（L42） |
| 大小 | ≤ **10 MB**（读流截断到 10MB+1 判断，不看 Content-Length） | `_MAX_FILE_BYTES`（L43）+ `submit()` L102 |
| 解析后正文 | ≥ **50 字**（过短视为空壳/碎片） | `_CONTENT_MIN`（L40）+ L116 |

**前端**：`<input type="file" accept=".md,.markdown,.txt,.docx,.pdf">`；表单三项必填——标题（2–128 字）、知识类别（四选一）、文件简介（2–500 字，上传者手写，审核员要读它）。

**知识类别（doc_type）只有四类**：`laws` 法规/制度、`procedures` 操作规程、`plans` 应急预案、`cases` 事故案例。

**解析器实际能力**（`_extract_file_text`，L48-70）：

| 扩展名 | 怎么解析 | 上限/坑 |
|---|---|---|
| `.md` / `.markdown` / `.txt` | 按 `utf-8` → `gbk` → `utf-8(errors=ignore)` 依次读文本 | 双编码兜底，但 GB18030 生僻字仍可能丢 |
| `.docx` | `python-docx`：**只取段落文本**（`Document(...).paragraphs` 逐段取 `p.text` 后拼接） | **不读表格、不读页眉页脚、不读文本框** —— 表格型规程会大量丢内容 |
| `.pdf` | `pymupdf` 逐页 `page.get_text()` | **只取文本层**：扫描件/图片 PDF 解析为空 → 撞 50 字门槛被拒 |

**明确不支持**：`.doc`（旧 Word）、`.xlsx/.csv`、`.pptx`、图片/扫描件 OCR、`.htm/.html` 文件本体、压缩包、epub。

**存哪**：原文件 `uploads/kb_contrib/{uuid}{ext}`（保留扩展名便于审核员下载）；全文存 `knowledge_contributions.content`（MEDIUMTEXT）。

> 一句话：**能贡献的是"有文本层的单文档"——5 个扩展名、3 种解析器（纯文本 / Word 2007+ 段落 / PDF 文本层）**。最常见的"看着支持其实进不来"是**扫描版 PDF**和**旧版 .doc**；最容易"进去了但缺内容"的是**表格型 docx**。

### 1.7 清洗规范处理流程（`kb_govern`）

**执行时机：只在「审核通过」那一刻跑**（`review()` 的 approved 分支）。提交时不洗、存原文；AI 预筛（`review-preview`）用的是**未清洗原文**的前 3000 字——两处口径不同（见 §1.7.4）。

#### 1.7.1 第一步：`clean_text()` —— 五步清洗

| 步 | 做什么 | 细节 |
|---|---|---|
| ① HTML 剥离 | 正则 `<\w+...>` 命中就用 BeautifulSoup `get_text("\n")` | 兜用户把网页源码粘进 txt/md |
| ② 控制字符 | 删 `\x00-\x08 \x0b \x0c \x0e-\x1f \x7f` 和 `\ufffd`（替换符=乱码常见形态） | 保留 `\n \t` |
| ③ 逐行净化 | 空白压缩（连续空白→单空格）→ 空行丢弃 → **噪声行剔除** | 噪声表：`_NOISE_LINES` 30 个词（首页/收藏/打印/字号/无障碍/备案号/版权所有/主办单位/当前位置/来源：/点击数/更新时间/上一篇/下一篇/扫一扫…）+ `_EXACT_NOISE` 8 个整行词（简/繁/EN/邮箱/默认/超大/登录/注册）；另外"≤30 字且以 … / ... / ··· 结尾"的行也丢（导航截断） |
| ④ 相邻重复行去重 | 只去掉**紧邻**完全相同的行 | 分页页头/复制粘贴重复 |
| ⑤ 重新拼接 | `"\n".join(lines)` | 返回清洗后全文 |

#### 1.7.2 第二步：`quality_check()` —— 四项硬指标

| 检查项 | 阈值 | 不通过后果 |
|---|---|---|
| 有效字数 | **< 300 字 → 拒绝**（`_MIN_HARD`）；300–2000 允许但标 `short=True`（审核界面写"偏短"）；≥2000 正常（`_MIN_NORMAL`） | 422「有效正文仅 N 字（低于碎片阈值 300 字）」 |
| HTML 残留 | 清洗后仍有成对标签 → 拒 | 422「存在 HTML 标签残留」 |
| 重复段落 | 按行统计 `重复率 = (行数 - 去重行数)/行数`，**>40% 拒** | 422「重复段落比例 X%（超过上限 40%）」 |
| 乱码比例 | CJK 兼容区/私用区/替换字符（`\uE000-F8FF \uF900-FAFF \ufff0-FFFF`）占比 **>5% 拒** | 422「乱码字符比例 X%」 |

> **与判定标准的口径差（重要）**：`docs/v1.0/施工安全领域文件鉴别判定标准.md` §5 写的是「有效正文 **≥2000 字符**」，代码对**用户主动上传**改成了分档：<300 硬拒、300–2000 放行但标注。模块注释里写明了理由（标准针对批量网页采集，用户上传的单条通知/规程几百字也可能是完整知识）。**如需严格 2000 硬门槛，只改 `_MIN_HARD` 一处**。

#### 1.7.3 第三步：达标之后才落库

```
clean_text → quality_check(ok) → SPLITTERS[doc_type] 分块（doc=contrib_{id}、source=user_contrib）
→ knowledge.upsert_chunks（稳定 ID 增量写）
→ status=已入库、chunk_count=n、review_note/时间线写「清洗治理后 N 字（偏短）」
```

不达标：**拒绝入库**、贡献状态仍是「待审核」（管理员可再沟通补充后再审），不写向量库。

#### 1.7.4 实测（2026-10-24，库里唯一一条已入库贡献）

| 样本 | 原始 | 清洗后 | 结果 |
|---|---|---|---|
| contrib #1（建设部 1998 通知，md） | 1722 字 | 1644 字（删 78 字 / **-4.5%**） | `ok=True`、`short=True`（偏短）、重复率 0、乱码 0 → 入库 **14 块** |
| 合成 HTML 粘帖文本（1080 字，含"首页/收藏/打印"+ 重复段） | 1080 字 | **159 字** | `ok=False`：碎片（<300）+ 重复段落 95% |

#### 1.7.5 现状缺口（事实，不含结论）

1. **判定标准 §5 的另两条没有代码校验**：「标题规范」（纯"DB""@相关人员"这类无意义标题要人工复核）、「时效性」（现行有效 / 非征求意见稿 / 未废止）—— 全靠管理员人工看。
2. **解析层静默丢内容**：docx 表格、页眉页脚、文本框；扫描 PDF 无文本层。只有"解析后 ≥50 字"这一道兜底，表格漏读不会被发现。
3. **两套清洗规则并存**：官方 `knowledge_src` 走 `scripts/govern_html.py`（`NOISE_WORDS` 全表 + 站点特定噪声，如"安全管理网""粤公网安备"），用户贡献走 `kb_govern._NOISE_LINES`（精选子集）—— 词表不同步。
4. **预筛与清洗口径不同**：`review-preview`（AI 预筛）看的是**未清洗**内容，可能判"通过"；真正审核通过时却被清洗卡住（历史上没出问题，因为预筛只判"是否属安全领域"，不判质量）。
5. **清洗不落审计**：`clean_text` 前后的差异没有留档（只记最终字数与块数），无法回溯"某段被当噪声删掉了"。

## 2. 与 AI 助手「不通」的具体位置

先说准确的那一半：**检索侧其实是通的** —— 贡献入库后写进同一个 `safety_kb` 集合，`retrieve_queries` 会命中 `source="user_contrib"` 的块。问题在"通了但用户看不见、也不能反向流动"：

| # | 断点 | 证据（file:line） |
|---|---|---|
| 1 | 引用标签显示内部命名空间 `contrib_1`，不是文件标题 | `knowledge_contrib_service.review()`：`doc=f"contrib_{contrib_id}"`；`rag.format_context()` 用 `meta["doc"]` 当标签 |
| 2 | 点「查看原件」必然失败：`GET /api/kb/doc` 只放行 `knowledge_src/{laws,procedures,plans,cases}/**.md`，而贡献的 `source="user_contrib"` | `src/routers/kb.py::read_kb_doc` 的前缀校验；前端 `openKbDoc(s.source, s.doc_type)` |
| 3 | 无法区分"官方源 / 用户贡献"：前端只按 `doc_type` 四类上色，没有可信度或来源角标 | 前端 `TYPE_META`（法规蓝/规程紫/预案橙/案例绿） |
| 4 | 助手不知道"这一轮资料没覆盖"：无命中或检索降级时只对用户说一句，不落库、不进贡献池 | `routers/chat.py` 的 `RETRIEVAL_DEGRADED_NOTE`（03 刚加） |
| 5 | 没有"从对话沉淀知识"入口：好答案无法一键转贡献草稿 | 提交端点只接受 `UploadFile = File(...)` |
| 6 | 贡献"何时能被问答检索到"用户看不到：`chunk_count` 只作为数字展示 | 前端贡献列表 |

## 3. 非人类用户（Agent）渠道：缺什么

| # | 缺口 | 证据 |
|---|---|---|
| 1 | 认证只有"用户名+密码→JWT"，无 API Key / 服务账号 / 机器凭证 | `src/core/security.py`（`HTTPBearer` + JWT，`sub`+`role`） |
| 2 | 角色枚举只有 `admin / safety_officer / employee` | `src/models/user.py` |
| 3 | 提交只收 multipart 文件：Agent 产出的结构化文本/对话沉淀没有文件 | `routers/knowledge_contrib.py::submit_contrib`（`file: UploadFile = File(...)` 必填） |
| 4 | 审计无法标识 Agent：`timeline.operator_id` → `users.id`，Agent 无 user 行 | `models/knowledge_contrib.py::KnowledgeContribTimeline` |
| 5 | 审核 100% 人工（`require_roles("admin")`），AI 只能预筛；无"低风险自动入库"分级 | `knowledge_contrib_service.review()` |
| 6 | 无去重/修订/下架：同一文档再贡献 = 新 `contrib_{id}` = 新命名空间（`upsert_chunks` 的 ID 含 doc），旧块仍在库；法规废止也只能手工删 Chroma | `knowledge.py::_chunk_id`（`doc_type|doc|chapter|article_no|child前64字`） |
| 7 | 通知只有"待审→admin / 结果→贡献者"两类事件，Agent 渠道没有事件位 | `notification_service.TYPE_KB_CONTRIB` |

## 4. 可复用的资产（04 不必重建）

1. **状态机 + 时间线范式**：`hazard_service` → `knowledge_contrib_service` 已经把"待审→通过/驳回 + timeline + 通知"跑通。
2. **质量门槛**：`kb_govern.clean_text / quality_check`（碎片/重复/乱码三关）可直接用作 Agent 提交的第一道过滤。
3. **AI 预筛**：`knowledge_review_agent` + 判定标准原文，Agent 提交同样可以先过一遍"是否属施工安全领域"。
4. **分块器**：四类 `SPLITTERS` + `upsert_chunks` 稳定 ID 增量写，Agent 提交只要给 `doc_type` 就能复用同一套切分。
5. **检索侧**：`retrieve_queries` 已能命中 `user_contrib`，Agent 提交入库后**无需改 RAG 即可被问答引用**（但引用展示要修，见 §2）。
6. **前端**：贡献页表单/列表/详情/审核弹窗/AI 预筛按钮都在，改造面主要在"字段 + 来源角标 + 详情预览"。

## 5. 调研待补（下一轮取证）

1. **贡献 vs 官方重复度**：现有 1 条已入库贡献与 816 份官方源是否有内容重叠（可用子块文本哈希比对）——决定"去重"是必须还是可选。
2. **助手侧缺口样本**：最近 200 轮问答里"检索 0 命中 / 降级 / 被判资料不足"的比例与问题类型，作为"缺口回收"的输入量级。
3. **Agent 提交的真实来源**：项目里有哪些 Agent 会产出知识（PPT Agent 的检索要点、审核预筛的结论、对话沉淀），各自产物形态与体积。
4. **权限边界**：非人类账号能否看到/检索知识库全量（等价 employee 还是更高）、能否触发审核动作。
5. **法规有效期数据可得性**：`knowledge_src` 的法规 md 是否带"实施日期/废止日期"字段（抽样 20 份），决定有效期字段是"能自动填"还是"人工填"。
6. **前端阅读器改造面**：`openKbDoc` 目前只认 `knowledge_src` 路径，评估改为"贡献详情页"的最小改动。

## 6. 风险与前置约束

- **不得改 `users` 表既有字段含义**（00/01 已定"尽量不动 users"），Agent 身份若需要新字段，只能加列或新增表。
- 官方知识源链路（`knowledge_src` 816 份、`collect_kb.py` 等采集脚本）**不能被信任边界改动污染**：用户/Agent 贡献必须保持独立命名空间（`contrib_*`），否则官方重跑会覆盖或误删。
- 问答时延口径（01：首问 ≤60s、追问 15~20s）不能被"缺口回收"这类附加动作拖慢——它必须是异步/事后。
- 贡献审核是**人的管理职责**，AI 只能辅助；自动入库若要开，必须限定"可信 Agent + 低风险类型 + 可回滚"。

## 7. 草案（用户 2026-10-24《知识贡献链路升级与Agent贡献渠道开发》）可行性评估

> 本节只写"哪些能做到、哪些有坑、每处坑的实测依据"，不含裁定；取舍进 `Verdict/04`。

### 7.1 逐条评估

#### ① 贡献入库 `knowledge_src` 四类 + 前端可查

**可行**：`/api/kb/list` 扫四类目录下全部 `.md/.txt`；`/api/kb/doc` 读原文并按 md 渲染；两侧白名单都是 `laws/procedures/plans/cases`。贡献文件写进对应目录后，**首页"政策文件"立刻可搜、引用可点开**。但有 7 个必须先处理的事实：

| # | 坑 | 依据 |
|---|---|---|
| 1 | **"前缀小字"不能放在标题之前** —— `_first_title()` 取"第一行非空行"，放前面会让首页列表标题变成前缀 | `routers/kb.py::_first_title`（L62-74） |
| 2 | **文件名冲突**：同名文件直接覆盖；`/list` 的 `name` 就是文件名 | `routers/kb.py` L43-45 |
| 3 | **全量重建会跳过 <2000 字节的文件** —— 清洗后 300–2000 字的短贡献（简报/通知）重建后从 RAG 里消失，DB 仍显示"已入库" | `knowledge.py::build_from_dir`（`if size < 2000: continue`） |
| 4 | **重建需先清空集合**（治理后文本变化 → 稳定 ID 变化），脚本本身没有 `--clear`，清空靠另外操作 | `scripts/collect_kb.py` 头部注释 |
| 5 | **旧块迁移**：现贡献入库是 `doc=contrib_{id}` / `source=user_contrib`；改成 `doc=文件名` / `source=knowledge_src/...` 后，旧 `contrib_1`（14 块）仍在库里 → 必须显式删除，否则一份文档两份块 | `knowledge_contrib_service.review()`；`_stable_id` 含 `doc` |
| 6 | **source 必须写相对路径**（`knowledge_src/laws/x.md`）。实测官方块的 source 是相对路径 + 反斜杠，`kb.py` 已做 `\`→`/` 归一，绝对路径会被前缀校验挡下 | Chroma 官方块 meta 实测；`read_kb_doc` L89-100 |
| 7 | **`knowledge_src/` 在 `.gitignore` 里**（`backend/knowledge_src/`），贡献原件不随仓库走；DB `content` + `uploads/kb_contrib/`（也被忽略）是唯一副本 → 换机/重建即丢。若要"可重建"，需 DB 为准的回填脚本 | `.gitignore` L35 / L38 |

**补充事实**：分类目录一旦官方+贡献混住，`crawl_*`/`collect_kb` 无法从目录区分来源 —— 建议 metadata 增 `origin`（official / user / agent），否则将来"只重采官方源"没有依据。

#### ② 上传支持 `.html`

**可行且简单**：后端白名单加 `.html/.htm`、前端 `accept` 同步；解析用已装的 `bs4`（`kb_govern.clean_text` 已经在用）+ `markdownify`。实测把含 h1/表格/列表的 HTML 转 md：**0.18s，h1/表格/列表全部保留**。
**但**：`markdownify` 目前**不在 `requirements.txt`**（该文件连 `pymupdf`/`python-docx`/`bs4`/`playwright` 都没列，属既有缺口），04 要顺手补，否则换机器跑不起来。

#### ③ `.txt/.html → .md`

- `.txt`：改名 + 加 H1 标题即可，**无结构可补**（纯文本没有标题层级信息）——草案"简单复制改后缀"对 txt 成立。
- `.html`：**不能只改后缀**，必须转换（上面实测方案），转完还要过 `kb_govern`。

#### ④ `.docx/.pdf → .md`：MinerU 能否"简单复现"

**MinerU 的设计原理**（网络检索 + 项目内既有《知识贡献模块MinerU集成计划书》v2 复核）：`pipeline` 后端是 **5 个模型的串联流水线** —— 版面分析（doclayout-yolo）→ OCR（PP-OCR 系列）→ 表格结构识别（RapidTable）→ 公式识别（UniMER）→ 阅读顺序（layoutreader）；另有 hybrid / VLM 后端（需 6–8GB+ 显存，本机 RTX3050 4GB 只能跑 pipeline，且建议 CPU）。**这不是"规则可复现"的东西**：精度来自模型，不来自代码结构。

**但草案的诉求（把 docx/pdf 变成 md）不必等于 MinerU**。本机实测（2026-10-24）：

| 场景 | 方案 | 实测结果 | 结论 |
|---|---|---|---|
| 文本层 PDF 的**标题层级** | `pymupdf` `get_text("dict")` 取每行 span 字号 | 字号分布 20/15/11/10pt 清晰分层（H1/章节/正文/表头） | 可做启发式分级 |
| 文本层 PDF 的**表格** | `page.find_tables()` | 命中 1 个表，抽出 2 行（合并表头会合并行，需容错） | 可用，简单表够用 |
| **DOCX（含表格）** | `python-docx` 按 body 顺序遍历段落+表格，标题样式→`#`、表格→md 表 | **0.024s**，标题层级+表格全部保留 | 现有"只读段落"丢表格的问题直接解决 |
| **HTML** | `markdownify` | 0.18s，h1/表格/列表保留 | 可用 |
| **扫描件 PDF（无文本层）** | 无 OCR 就无解 | pymupdf 抽不到字（现有 50 字门槛会拒） | 只有 MinerU/OCR 能做 |

**评估结论（候选路径，非裁定）**：

- **路径 A（轻量内置转换）**：新增 `kb_convert.py`，md 直通 / txt 加标题 / html→md（markdownify）/ docx→md（段落+表格+标题样式）/ pdf 文本层→md（字号分级 + find_tables）。零新模型、毫秒级、无需装 mineru；覆盖"有人上传的电子文档"绝大多数场景。
- **路径 B（MinerU 可选后端）**：仅当 A 判定"无文本层/抽取字符过少"时才调 mineru CLI（子进程 + 180s 超时 + 失败降级），装不装都能跑；对应既有计划书 v2 的落地方式。
- **路径 C（纯 MinerU）**：所有 pdf/docx 都走 mineru —— 解析变 30–180s、装包风险（torch 依赖/模型 1–2GB），与"减少外部依赖"的目标相反。

### 7.2 审核流程（草案 (0)/(0.5)/(2)/(3)）

现有能力已覆盖"待审 → 通过/驳回 → 通知 → 入库 → 时间线"，草案新增两件事：

### 7.5 风险排序（按"会静默出错"的程度）

1. **贡献文件的可重建性与来源可区分性**（2000 字节跳过 / 重建清空 / 无 origin 字段）——出错时用户看到"已入库"但问答检索不到。
2. **旧 `contrib_1` 遗留块迁移**——不删就出现同一份文档两份块，引用重复。
3. **Agent 身份缺失**——工具能写库却说不清谁写的，审计与追责断链。
4. **时延/并发**——把网搜塞进回答链路会直接破坏 01 的口径。
5. **搜索源无 key**——方案落地时才发现"网搜"没有可用入口。

### 7.6 待定决策点（进 `Verdict/04` 用）

1. 贡献文件命名（标题/`{slug}_{id}`）与目录写入时机（审核通过时 vs 入库后）。
2. 是否给 metadata 增 `origin`（official/user/agent）与 `contrib_id`——引用角标与"可区分来源"依赖它。
3. 转换路径 A / A+B / C 的取舍；扫描件不可解析时的用户提示文案。
4. 短贡献（<2000 字节）是否在重建时豁免；重建后 DB `chunk_count` 如何校准。
5. `Methodology/`、`case.md` 的存放位置与格式（JSONL vs `&`）。
6. Agent 身份模型与权限（能否自动入库 / 是否必须人工审核）。
7. "网搜"入口：搜索 API / 站点白名单 / 浏览器，三者是否并存与降级顺序。
8. 旧 `contrib_1` 迁移脚本是否随 04 一起做（删旧块 + 按新命名重入）。

### 8.2 条目 1：贡献迁入 `knowledge_src/四类`

**可行性**：可行，且是前端改动最少的做法 —— `GET /api/kb/list`（首页政策文件）与 `GET /api/kb/doc`（引用原件阅读器）都只扫 `knowledge_src/{laws,procedures,plans,cases}/*.md|txt`，贡献写进去后**前端零改造即可见**。

**必须配套的 6 处护栏**：

| # | 护栏 | 为什么必须 |
|---|---|---|
| 1 | 文件名 `contrib_{id}_{safe_title}.md` | 避免同名覆盖；`doc` 取文件名 stem，引用标签可读；可从文件名反查 contrib_id |
| 2 | **改 `build_from_dir` 的 2000 字节跳过**（改可配置 / 贡献走单独函数） | 现在 `size < 2000` 直接 `continue`（`knowledge.py`）→ **短贡献静默不入库**，用户以为成功 |
| 3 | **`clean_empty_kb.py` 排除 `contrib_*`** | 该脚本会删除正文 <300 字的 md；贡献正文常在 300 字上下，一次清理就没了 |
| 4 | 首行必须是 `# 标题` | `kb._first_title()` 取首个 `#` 行；若首行是 front-matter `---`，列表标题会变成 `---` |
| 5 | 入库改用"单文件入库"函数（对齐 `build_from_dir` 的 metadata 口径） | 现状贡献是 `doc=contrib_{id}`、`source=user_contrib`；迁入后必须变成 `doc=stem`、`source=knowledge_src/...`，否则 `kb/doc` 仍打不开 |
| 6 | 失败回滚 | 先写临时文件 → 入库成功再落最终名；否则会出现"文件在、库里没有"的长期不一致 |

**正文前缀怎么写**：
- 第 1 行 `# {标题}`；第 2 行 `> 用户推荐 · 贡献 #12 · 审核通过 2026-10-25`（Agent 则 `> Agent 贡献（deepseek-v4-flash） · ...`）；
- **不要用 front-matter**：会破坏 `_first_title`，且清洗/分块会把 `---` 当正文；
- 更可靠的"角标"来自 **Chroma metadata**（`contrib_id`、`source_kind=user|agent`），前端按 metadata 上色，不依赖正文文字。

**修订/下架**（草案未写，必须定）：`chromadb 1.5.9` 的 `collection.delete(where={"doc": stem})` 可用 → 修订 = 删旧块 + 换文件 + 重新入库；下架 = 删文件 + 删块 + 状态置"已下架"（需扩状态枚举）。

**迁移影响**：库里已有 `contrib_1`（14 块）属旧命名空间；新模式上线后要么删除、要么保留（会与新文件块重复）。建议一次性清理。

### 8.3 条目 2：格式支持与转换

现状：`_ALLOWED_EXTS = {md,markdown,txt,docx,pdf}`；三种解析器（文本 / docx 段落 / pdf 文本层）**都不产出 md**。

| 格式 | 建议实现 | 成本 | 实测依据 |
|---|---|---|---|
| `.txt` | 改名 + 首行补 `# 标题` | 极低 | 现有解析已能读 |
| `.html` | `markdownify(html, heading_style="ATX")`，先删 `<script>/<style>/<title>` | 低（库已装） | 实测：标题/加粗/列表/表格都成 md，`<script>` 被剔除 |
| `.docx` | `python-docx` 按 `document.element.body` 交错遍历 `p`/`tbl`：段落成行、Heading 样式转 `#`、表格转 md 表格 | 中（约 100 行） | 两份真实 docx：53/132 段、body 元素 54/141，可交错遍历 |
| `.pdf`（文本层） | `pymupdf`：`get_text("dict")` 按字号分布定标题（峰值字号=正文，>1.15× 判标题）、按页首尾重复行去页眉页脚、`page.find_tables()` 转 md 表格 | 中（200–300 行） | 3 份报告：60/107/39 页、2.8–7.2 万字；字号峰值 15.0/16.0/14.1、标题 20.8/22.0；`find_tables` 可用（这 3 份无表格） |
| `.pdf`（扫描件） | `get_text()` 为空 → **明确拒绝并提示"需要可复制文本的 PDF"**；OCR 只作可选后端 | 高 | 现有 9 份 PDF **全部有文本层**（0 份扫描件） |

**MinerU 复现评估（结论：不划算）**
- 原理：多阶段流水线 —— 版面分析（DocLayout-YOLO / LayoutLMv3）→ OCR（PaddleOCR）→ 公式检测与识别（YOLO + UniMERNet）→ 表格结构还原（RapidTable / SLANet / StructEqTable）→ 阅读顺序重排（MNLR）→ 拼 Markdown。
- 代价：权重数百 MB~GB、首次下载、显存需求、依赖链长（`mineru`/`magic-pdf` 均未安装）。
- 判断：它解决的是"扫描件 + 复杂版式 + 公式/表格"。本语料 9/9 文本层、无公式、表格少 → pymupdf 轻量管线覆盖 ~90%。建议 MinerU 只做"可选后端 adapter"（配置开关 + CLI 调用），不进主路径。

### 8.4 条目 3：Agent 贡献渠道

**3.1 `Methodology.md` + `cases.md`**

**3.2 聊天工具（网搜 + 提交）—— 建议改设计**

| 问题 | 事实 | 影响 |
|---|---|---|
| 浏览器能力 | 服务端没有 Hermes 的 `ui_browser`；要用就得加 Playwright/Chromium | 生产多一套二进制依赖 |
| 反爬现实 | 项目内实测：VCG 403、1ppt 反爬、Openverse 首次 200 后连续超时 | 成功率不可控 |
| 时延口径 | 01 定：首问 ≤60s、追问 15~20s；Agent 现在只有 1 次工具预算（`retrieve_more`，`calls>=1` 硬拦） | 第 2 个工具会打架或拖慢 |
| 触发信号 | "知识库资料少"（全量检索后仍不足）≠ "redis 缓存少"（会话缓存不足） | 信号源不明会每轮误触发 |
| 合规 | 外网资料有版权/时效问题，入库必须人审 | 不能自动入库 |

**建议三步（由稳到激进）**：
1. **缺口登记（必做，成本低）**：回答结束后异步判断"检索无命中 / 补检后仍 insufficient"→ 写 `knowledge_gaps`（问题、缺口子查询、往返次数、conversation_id），管理端出"待补知识清单"。
2. **管理员一键采集（推荐）**：管理员在缺口清单点"采集"→ 后台任务抓取（HTTP/Playwright）→ 走贡献审核（AI 预筛 + 人审）。Agent 不直接写库。
3. **Agent 自动提交（最后再考虑）**：服务账号 + 自动提交，仍需审核，且限"可信来源白名单"。

**3.3 Agent 身份（草案缺）**
- 三种可选：① `users` 加 `user_type=agent` + 新角色（改表，与"尽量不动 users"冲突）；② 新建 `agent_clients(api_key_hash, name, model, owner_user_id, scopes)`（不动 users）；③ 复用发起人 JWT + 贡献表加 `source_kind/source_agent`（最轻，但审计只能到人）。
- 推荐 ② + 贡献表加 `source_kind`(user/agent) / `source_agent_id`；`timeline.operator_id` 保持人类，新增 `actor_kind`。

### 9.2 MinerU 接入的三条硬事实（实测，2026-10-26）

**① 绝对不能装进 `C:\python` 全局环境。**
`uv pip install --dry-run mineru --python C:/python/python.exe` 的解析结果显示它会**降/升级后端核心依赖**：

| 包 | 现状 | MinerU 要求 |
|---|---|---|
| `starlette` | 0.52.1 | **1.10.0**（FastAPI 直接依赖，破坏性升级） |
| `pydantic` | 2.12.3 | 2.14.1 |
| `pydantic-core` | 2.41.4 | 2.50.1 |
| `typing-inspection` | 0.4.2 | 0.4.4 |

→ 结论：**用 `uv tool install mineru`（独立工具 venv）或单独 venv 安装，项目只以子进程调用 CLI**（对齐 OfficeCLI 的做法：配置路径 + 超时 + 失败兜底），绝不 import。

**② MinerU 4.x 支持 DOCX 原生解析，且 Office 格式固定走 Flash（不加载模型）：**
- 输入支持：PDF / 图片 / DOCX / PPTX / XLSX / OFD / EPUB / HTML / MHTML / CSV / RTF 等；
- **Office（docx 等）固定走本地 Flash 原生解析，整本解析，不占推理模型** → 恰好解决 docx 表格；
- PDF 可选四档：flash（原生文本）/ basic（ONNX 小模型 + 表格/公式）/ standard（小模型 + VLM）/ advanced；
- **PDF 默认只解析前 10 页**，必须显式 `--pages all`（否则 60 页的调查报告只进前 10 页，静默丢内容）；
- Windows + CPU 环境自动选 ONNX/CPU 小模型 + llama.cpp VLM；表格模型（SLANet/UNet）可在 CPU 跑，`MINERU_TABLE_DEVICE=cpu` 可固定。

**③ CLI 形态**：`mineru parse <input> -o <out>` / `mineru-kit parse <input> -o <out> --tier flash`；非 PDF 输入不接受 `--pages`。

### 9.3 这条口径带来的连带变化

1. **"至少 1000 字"让两个历史坑自然消失**：`build_from_dir` 跳过 <2000 **字节**、`clean_empty_kb` 删除 <300 **字** —— 1000 个汉字 ≈ 3000 字节 > 2000，且远大于 300。**唯一残留风险**：正文以 ASCII 为主时 1000 字可能不足 2000 字节（中文安全文档里罕见），可在方案里把"跳过阈值"按 `contrib_` 前缀豁免一次做扎实。
2. **文件名 = 最终 md 文件名** → 写入 `knowledge_src/{type}/` 前必须做**双重查重**：① 同目录同名文件；② md 首行标题与已有文档标题（含 DB 里已入库贡献）重复。命中即由管理员以"标题重复"驳回。
3. **不做下架** → 本期不做"删除已入库贡献 / 撤回 md"；但"修订"也应视为下期（同标题会被拒，天然不产生覆盖）。
4. **Agent 网搜的产物**要走同一套审核流：Agent 搜集 → 总结成 md（带来源 URL 清单）→ 提交 `待审核` → 管理员通过才写盘入库。
5. **方法论迁移后**：路径不再受 `.gitignore` 影响（`knowledge_src/` 被忽略，根目录不被忽略）→ 方法论可随仓库分发；需同步改 `_REVIEW_STANDARD` 之外的读取点，并新增 admin 读写端点。

### 9.5 Playwright 自由浏览的安全边界（实现时必须写死）

1. **域名策略两层**：方法论的"黑名单"是**软**约束（供 Agent 参考）；代码层再加**硬**约束（禁 `file://`/内网 IP/本机端口，防止 SSRF；可配 `KB_FETCH_DENY_HOSTS`）。
2. **抓取限额**：单次任务的站点数、页面数、单页体积、总下载字节、总时长都要封顶（方法论写入"超时/超限即换源"）。
3. **落盘只留证据**：下载的原件存 `uploads/kb_contrib/agent/{task_id}/`，md 里保留来源 URL + 抓取时间；**不把 HTML 原样入库**，先过转换 + `kb_govern` 清洗。
4. **一律人审**：Agent 产物进 `待审核`，管理员看到"来源 URL 清单 + Agent 模型 + 方法论版本号"，通过后才写 `knowledge_src`。
5. **可回放**：每次 Agent 采集写一条 `agent_runs` 记录（任务、问题缺口、访问过的 URL、结论、产物 md、审核结果），作为方法论更新的数据来源，也便于追责。
