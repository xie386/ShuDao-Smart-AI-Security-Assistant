| 项 | 内容 |

## 2. 现状取证（代码事实）

### 2.1 回答链没有意图门禁

`src/routers/chat.py`：

| 位置 | 事实 |
|---|---|
| `_prepare()` 第 104-106 行 | **第一个动作**是 `query_preprocess.preprocess(question, history, covered)`，注释写明"所有路径必做" |
| 第 113-153 行 | 之后按四态分支：`cache`（追问且判定足够）/ `incremental`（只补缺口）/ `context`（无 Redis + 有历史）/ `full`（首问/过期/退化首问，用预处理的子查询全量检索） |
| 第 152 行 | `full` 分支无条件 `retrieve_queries(pre["subqueries"])`，**无 try/except** |
| 第 194 行 | `event_stream()` 里 `prepared = _prepare(...)` 同样没有兜底 → 异常直接冒到 ASGI，SSE 断流 |

结论：**没有"闲聊"这个分支**，也没有任何意图分类；`mode` 的四态全部以"要检索"为前提。

### 2.2 提示词场景里没有意图分类

`prompt/prompts.yml` 现有 13 个场景：`safety_qa / ppt_outline / ppt_outline_md / ppt_content / hazard_vision / query_rewrite / exam_templates / exam_paper_gen / knowledge_review / query_preprocess / sufficiency_judge / safety_agent / safety_agent_user`。
没有"闲聊 / 意图判定"场景，也没有任何"不检索直答"的 system 提示。

### 2.3 现有可复用的机制

| 机制 | 位置 | 与本任务的关系 |
|---|---|---|
| 规则快路径 | `query_preprocess._looks_declarative()`：已是陈述句 + 短 + 无指代 + 无可剔除项 → 不调模型 | 同款思路可直接用于意图判定（省一次 LLM） |
| 预处理结果落库 | `chat_messages.references` 里的 `{"preprocessed": {...}}`（裁定 5，复用现有字段） | 意图判定结果可并列写入 `{"intent": {...}}`，不动表结构 |
| A08 审计 | `src/services/preprocess_audit.py` + `GET /api/conversations/{id}/preprocess-audit` + 前端 🔎 | 闲聊轮没有预处理结果，需要让审计展示"判定为闲聊、未检索" |
| 会话 RAG 缓存 | `src/services/conv_rag_cache.py`（TTL 600 滑动） | 闲聊**不能** `put_blocks/touch`，否则污染追问时的 covered |
| 时延基线 | 01 实测：首问 20.8~45.2s（≤60s 达标）、追问 15.0~22.0s | 意图判定新增开销必须落在噪声内（规则 0ms / 一次 LLM ~1~2s） |

### 2.4 本次失败的直接原因（与本任务相邻）

- 预处理内部 LLM 调用失败 → 已按设计退回原话（这层是好的）；
- 随后 `retrieve_queries` 失败 → **没有降级** → 500。
- 失败根因是 `.env` 打不开：`langchain_chroma` 构造时会 `chromadb.config.Settings()`，pydantic-settings **用相对路径**读 `.env`；那一刻进程 CWD 在 D 盘上而 D 盘掉线 → `Errno 22`。
- 说明：即使加了意图门禁，"知识问答"这条路的检索异常仍会把整轮回答打掉（属健壮性问题，是否并入本大点由 ③ 方案定）。

## 3. 候选判定方式

| 方案 | 做法 | 时延 | 误判特征 | 维护成本 |
|---|---|---|---|---|
| **A 规则快路径** | 关键词/正则 + 领域实体词典：寒暄/身份/能力/致谢/情绪 → `chat`；命中安全实体（高处/动火/隐患/作业票/法规名…）→ `knowledge`；其余不定 | ≈0ms | 规则覆盖不到的表述会漏判（落回知识问答 → 多查一次） | 词表要维护，但可脚本化 |
| **B 单次 LLM 二分类** | 新增 `chat_intent` 场景，输入问题 +（可选）上一轮主题，输出 `{intent, reason}` | +~1s/轮（实测中位 0.98s，见 §10） | 受模型波动影响；对"元问题/能力询问"通常判得准 | 低（改提示词），但每轮多一次调用成本 |
| **C 混合：规则先判，模糊落 LLM** | 规则命中明确信号（显式免检索、纯寒暄、含领域实体）直接定；都不命中 → 调 B | 0ms 或 +1~2s | 兼顾准确与成本；需要定义"明确信号"边界 | 中（两套逻辑 + 边界表） |
| **D 交给 Agent 自查** | 让现有 `chat_agent` 在 system 里自判 | 省不了检索（Agent 起手就要上下文） | 不可控 | 低但效果差 |

补充事实：01 已把"预处理"做成所有路径必做，若在它**之前**插入判定，顺序是 `意图 → 预处理 → 检索`；判定为闲聊时后两步都不执行。

## 5. 误判代价

| 误判方向 | 后果 | 可接受度 |
|---|---|---|
| 知识题误判为闲聊 | 不检索直接答 → 可能编造/无依据，且**没有来源标签** | 不可接受（安全领域答错代价高） |
| 闲聊误判为知识题 | 多一次预处理 + 一次检索（首问 ~5-45s）→ 慢，但答案通常仍可用 | 可接受（现状就是全这样） |
| 混合问题（前半闲聊 + 后半知识） | 若整句判闲聊 → 丢知识诉求；若整句判知识 → 慢但答得上 | 倾向后者 |

推论：判定兜底应偏保守（默认 `knowledge`），规则层只做"高置信度的闲聊"判定。

## 6. 与既有机制的耦合点

1. **会话缓存**：闲聊不写 `conv_rag_cache`；同时也不应把上一轮的块摘要当作 `covered` 传给下次判定（保持"闲聊不影响检索状态"）。
2. **审计（A08）**：`refs` 里现在只写 `preprocessed`；闲聊轮需并列写 `intent`，`preprocess_audit.build_rounds()` 与前端 🔎 都要兼容"没有预处理"的轮次。
3. **history**：闲聊轮仍要进 `chat_messages`（否则上下文断裂），但 `build_history()` 不应把闲聊内容当作"检索式"注入。
4. **meta / 状态行**：`mode` 需要新增 `chat` 一档；前端 `MODE_LABEL` 增加"闲聊（未检索）"。
5. **Agent 化**：闲聊不走 `chat_agent`（工具无意义），直连 `llm_client.chat_stream`。

## 7. 验证设计（供 ③ 方案引用）

**样本集**（建议 24 条，人工标注 + 记录预期路径）：

| 类别 | 条数 | 示例 |
|---|---|---|
| 纯闲聊 | 8 | 「在吗」「谢谢」「你是谁」「你能干什么」「你比别的助手强在哪」「今天好累」 |
| 显式免检索 | 4 | 「不用检索，你刚才说的方法对不对」「别查资料，凭经验说说高处作业最怕什么」 |
| 知识问答 | 8 | 「高处作业几米算高处」「动火作业审批流程」「脚手架验收要点」 |
| 混合 | 4 | 「你是谁？顺便说下临边防护要求」 |

**指标**：

1. 闲聊/显式免检索的**判定准确率 ≥ 90%**，且**0 条**知识题被判成闲聊（硬约束）；
2. 闲聊首字时延 **≤ 5s**（不含模型冷启动）；
3. 知识问答链路**无回归**：抽 4 条跑，检索与回答结构与 01 基线一致（来源标签仍在）；
4. 闲聊轮**不产生** `shudao:rag:conv:*` 写入（Redis 里可验证）。

**跑法**：`scripts/` 下加探针脚本（复用 01 的 `probe_chat_e2e.py` 思路），逐条记录 `intent/mode/首字时延/是否命中来源`。

## 8. 已知风险与外部依赖

- **模型抖动**：B/C 方案依赖一次 LLM 调用；网络抖动时会退化为"保守走知识问答"（需要显式日志与 meta 标记）。
- **D 盘/网络不稳**（2026-10-24 实测两次掉线）：`.env` 相对路径读取、Chroma 初始化都会炸；与意图判定无关，但会让"验证"不可复现，需要在设置判定开关时留环境开关。
- **规则词表腐化**：法规名称/术语会更新，需要一条"从知识库元数据重新生成词表"的脚本，否则半年后漏判上升。

## 10. 实测补充（2026-10-24 下午，真实环境）

### 10.1 意图分类 LLM 抽样（DeepSeek 主模型，`temperature=0`）

| 提问 | 期望 | 判定 | 耗时 | 模型给的理由 |
|---|---|---|---|---|
| 在吗 | chat | chat | 7.45s（首调建连） | 问候寒暄 |
| 你是谁 | chat | chat | 0.96s | 询问助手身份 |
| 谢谢 | chat | chat | 0.57s | 表达感谢属闲聊 |
| 你能上传什么格式的模板 | chat | chat | 0.75s | 询问助手能力用法 |
| 不用检索,你现在有自我维护和丰富知识库的能力吗 | chat | chat | 0.92s | 询问助手自身能力 |
| 你刚才说的方法可靠吗 | chat | chat | 0.77s | 询问助手回答可靠性 |
| 高处作业几米算高处 | knowledge | knowledge | 1.04s | 高处作业定义属业务 |
| 动火作业审批要谁签字 | knowledge | knowledge | 1.21s | 动火作业审批属业务规程 |
| 脚手架验收要点 | knowledge | knowledge | 1.01s | 脚手架验收业务问题 |
| 你是谁？顺便说下临边防护要求 | knowledge | knowledge | 1.01s | 含临边防护业务问题 |
| **第一问** | knowledge | **chat（MISS）** | 1.21s | 未含业务知识诉求 |

**结论**：① 单次 LLM 二分类约 **1s**，落在 01 追问基线（15~20s）的噪声内；② 混合句按"含业务诉求即 knowledge"的提示词能正确归并；
③ **无上下文的指代句会误判**，判定输入必须带"上一轮问题/当前主题"。

### 10.2 真实流量分布（近 60 条 user 消息）

- 知识题 58 条（高处作业/安全带/脚手架/动火/有限空间/临时用电/塔吊/监护人职责…）；
- 闲聊 1 条（本次触发需求的那条）；
- 不可判 4 条（"第一问""第二问"，属测试残留）。

**结论**：真实流量里闲聊占比极低，但**每条知识的检索成本高**（首问 5~45s），一旦闲聊进来浪费明显；同时说明"误判成闲聊"的风险主要在**元问题与指代句**，而不是业务提问。

### 10.3 规则层可用的词素材（草稿验证）

- 显式免检索：`不用检索 / 别检索 / 不要检索 / 不用查 / 别查 / 不需要资料 / 不用知识库 / 凭经验`；
- 助手元问题：`你是谁 / 你叫什么 / 你能做什么 / 你能干什么 / 你会什么 / 你支持 / 你的 / 你比 / 你刚才 / 在吗 / 谢谢 / 感谢 / 你好 / 再见`；
- 业务实体（草稿 24 词，仅作种子）：高处、动火、隐患、整改、作业票、脚手架、安全带、临边、洞口、有限空间、临时用电、应急预案、演练、事故、法规、条例、标准、规程、防护、吊装、危大、特种作业、消防、职业健康。
- 用这套草稿跑 60 条真实提问：**0 条业务题被误判**（"高空作业""塔吊""监护人职责"虽没命中词表，但按 `unknown→knowledge` 兜底落到正确分支）。
