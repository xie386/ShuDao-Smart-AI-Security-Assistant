## 一、用户口述（逐字留档）

### 1.1 首轮（2026-10-23）

> 推翻原先的按照同样问题(而且是严格每个字都要一样)触发 redis 缓存块热启动时加速检索的设计，在实际应用中用户几乎不可能几乎一字不差的一直问一个问题，更多是根据会话的第一个问题的主题向下追问或者直接跳到其他问题，所以按照完全相同问题的链路在实际应用几乎不可能触发，另外，在实际问答中，用户更喜欢用疑问句，而不是陈述句，而疑问句本身句式会对检索效果大打折扣，预期更正设计是按照会话缓存检索块并且升级检索方式：首先 AI 助手要处理用户的问题，如果用户的问题用了不适宜的句式，需要进行问题预处理，转成陈述句，增添细节和适配转化等(具体转化方案在调研期说查找)，然后是除了一个会话的第一个问题或者停止聊天一段时间后(过了缓存时间)的最新问题，直接开始向量检索，其他问题，AI 助手先取缓存块的内容，判断是否够回答用户问题，不够再向量检索还需要的信息而不是检索整个问题需要的所有信息

### 1.2 草案（桌面 `草案.md` 要点逐字）

> 1. 首先当前 AI 助手模块的架构有一定问题,虽然引入了 langchain 架构包,但不是严格的 Agent,更像是一个连接 AI API 接口的工作流,升级后的 AI 助手的功能需求可能需要正式地把 AI 助手模块变成一个 Agent
> 2. 向量检索按照会话 ID 储存在 redis 服务中,redis 服务未开时退化方案见 5
> 3. redis 过时机制,检索块缓存不再是简单的超时清理,因为极有可能出现用户长时间提问超过缓存时间的情况,要变成更加智能的超时清理机制:某次 AI 助手完成回答后 10 分钟内用户不再问问题就清掉缓存,如果十分钟内用户继续追问,刷新重置计时为 10 分钟,**注意 AI 助手生成答案和回答期间不能消耗这个计时**
> 4. 在 redis 开启情况下:
> (0) AI 助手接收问题的预处理:最基本的非陈述句句式转陈述句,还有"语义适配化"，
> 例一：问「什么情况容易感冒」→ 步骤 1「容易感冒的情况」→ 步骤 2 把「流感期换季期易感冒行为」+「预防感冒方法」一起抛给检索任务（语义专业化适配，知识库多是书文领域专业化的，需要有转专业化的能力和多角度尝试的问询）
> 例二：问「去外地怎么选择衣物和规划路线」→ 步骤 1「外地旅游衣物选择方案和路线规划技巧」→ 步骤 2 把「外地旅游衣物选择方案」+「外地旅游路线规划技巧」分别检索（文献中很少有衣物和路线两个差别大的点出现在一个文档块里，一起检索效果会大打折扣；与例一行为上都是问两遍，但目的不同：例一是多问法尝试，例二是拆开更容易得到答案）
> 例三：问「潜水套装使用方式」（上一个问题是「氧气瓶使用方法」）→ 处理后把「潜水镜使用方式」「潜水服使用方式」分别检索（因为上一个问题已经拿到氧气瓶使用方法，故不再搜）
> 上面只是医学 Agent 和旅游规划 Agent 的检索方案例子，具体该项目的 AI 助手问题预处理怎么做需要网搜资料调研
> (1) 会话的第一个（或者超时清理后的第一个）问题：AI 助手预处理问题中的所有需要检索的信息后做整体检索
> (2) 后续追问问题 AI 助手先取 redis 检索结果和上下文信息判断是否需要更多信息,需要的话把需要的信息进行检索,而不是整体重新检索（这个设计实现后也就是说 redis 服务中一个会话就要存储不止一个检索块了）
> (3) 超过 10 分钟没有继续问,清空 redis 中的检索块
> 5. redis 服务未开,退化情况下：(0) 同 4；(1) 同 4；(2) 后续追问问题 AI 助手先上下文信息判断是否需要更多信息,需要的话把需要的信息进行检索,而不是整体重新检索
>
> 对 Hermes 待回答调研问题的回答：Q1 = LLM 判定；Q2 = 见上文（10 分钟）；Q3 = 见上文，主要是 LLM 判断还需要哪些信息，做问题预处理，把需要的信息里筛掉已经检索到的，只给检索任务布置未检索到的；Q4 = 拟父块（后续 bug 维护与优化期灵活评估调整）；Q5 = history 存用户原话和 AI 助手预处理后的样子

### 1.3 第二轮裁定口径（2026-10-23，逐字留档）

> 1. 重排归入 01 大点，调研重排瓶颈问题与解决方法，我个人认为会话第一问（超时后第一问）的时长在控制 60s 是可以接受的，只要能够达到速到逐渐变快（15s-20s 内）效果即可；2. 确定 Agent 化；3. 一开始缓存父块的本意是降低问题被分成多问题分别提问的频率（多次提问意味多倍耗时），但既然草案 4(0) 的一半已经存在且父块体量过大，拟改为子块缓存

拆成三条可执行口径：

| # | 口径 | 对草案的修订 |
|---|---|---|
| P1 | **重排优化纳入大点 01**，目标延迟：会话首问（含超时后首问）≤ 60s，后续追问落到 **15~20s** 量级 | 原草案未含重排；现在它成为 01 的一部分（§4.4 实测它是 56s 的唯一来源） |
| P2 | **确定 Agent 化**（即 §七 的 R2：`create_agent` + 检索工具 + 中间件承载缓存/判定） | 草案 1 由「可能需要」升为「确定要做」 |
| P3 | **缓存块从父块改为子块**（原 Q4 的「拟父块」作废） | 依据：父块 p50 117,312 字符（§4.3），原样缓存会把上下文顶爆；且原意是降低「一个问题被拆成多次提问」的频率，子块同样能达到该目的而体量可控 |

### 1.4 第三轮口径（2026-10-23，逐字留档）

> 1 和 2 都无误，但是第 3 点 redis 挂掉问题，草案提到了不是完整检索，是只回顾上下文总结缺失信息（redis 存活时回顾上下文和 redis 内检索块总结缺失信息）

即退化路径的口径：**Redis 不可用时不做整题全量重检**，而是
- Redis 存活：判定输入 = 会话上下文 + Redis 内的检索块
- Redis 不可用：判定输入 = **只有会话上下文**（最近若干轮问答 + 上轮答案已引用的来源），据此总结缺什么，只补缺的部分

## 四、实测取证（2026-10-23，只读，单问题抽样）

### 4.1 Redis 实况

```
ping: True（6380 在跑）
shudao:* 共 189 个 key —— 全部是 shudao:notify:<user_id>，rag_cache 前缀 0 个
```
**含义**：现有检索缓存一个都没在 Redis 里（当前实例）。要么曾被重启（TTL 只有 10 分钟），要么真实流量确实没走到写入分支。无论哪种，都印证口述判断：这条缓存链路没有形成收益。

### 4.2 单问题粒度：耗时与体量（进程内、含首次模型加载）

| 探针 | 耗时 | 产出 |
|---|---|---|
| Chroma 集合读取 | 5.40s | 17,797 块 |
| `query_rewrite("高处作业有哪些安全要求？")` | **18.25s** | 3 个子查询（「高处作业安全技术规范 临边洞口防护 安全带高挂低用要求」等） |
| `hybrid_retrieve(q, use_rewrite=False)` 冷启动 | **373.99s** | context **100,594 字符** / 4 个来源 |
| `hybrid_retrieve(q, use_rewrite=True)` 默认配置 | **128.79s** | context **226,471 字符** / 4 个来源 |
| 追问句「那高度呢？」（无会话上下文，独立检索） | **142.16s** | context 87,304 字符 / 4 个来源，首条来源「临边防护栏杆搭设要求」 |

三条含义：

1. **冷启动成本极高**（374s/次），但服务进程内模型与 BM25 常驻，实际每问只付「改写 + 检索」增量——**缓存要省的正是这两段**。
2. **上下文体量是隐藏大头**：默认配置下一题喂给模型的 `retrieved_context` 达 **226K 字符**（4 个父块）。若缓存块用父块原样存、原样复用，会把上下文直接顶爆——草案 Q4「拟父块」必须同时定「复用时怎么裁剪」。
3. **追问句在无上下文时被当真问题改写/检索**（142s），检索主题未必与上文相关——这就是「必须把会话上下文喂进预处理」的证据。

### 4.3 预热后的单次耗时（热进程）与父块体量

**预热成本**：BM25 语料构建（17,797 块分词）**178.20s**，进程内 `lru_cache` 只做一次。

**热态单次检索**（模型与语料均已常驻）：

| 问题 | 耗时 | context 字符 | 来源数 |
|---|---|---|---|
| 高处作业有哪些安全要求？（第 2 次） | **56.95s** | 100,594 | 4 |
| 同上（第 3 次） | **56.82s** | 100,594 | 4 |
| 安全带如何正确使用？ | 69.02s | 577 | 4 |
| 脚手架搭设完成后需要检查什么？ | **154.56s** | 209,330 | 4 |
| 发生火灾事故应如何应急处置？ | 42.25s | 4,857 | 4 |

**改写 LLM 热态耗时**：11.39s（首次）→ **1.88s**（第二次）。即 §4.2 里的 18.25s 是**冷启动**数字，热态只有约 2s。

**父块体量（关键发现）**：随机抽 200 块的 `metadata.parent_text` 长度
```
min = 2,768   p50 = 117,312   p90 = 117,312   max = 117,312
```
**大多数「父块」其实是整篇文档**（117K 字符 ≈ 6 万汉字），不是「章节」。这就是 context 动辄 100K~209K 字符的原因；也意味着草案 Q4「缓存父块」若原样存、原样复用，单次会向模型塞进数十万字符。

**排除法：40~155s 不是「每次重建 Chroma 客户端」造成的**

| 探针 | 耗时 |
|---|---|
| `get_vectorstore()` 构造第 1 次 | 63.13s |
| `get_vectorstore()` 构造第 2 次 | **0.02s** |
| 复用客户端的 `retriever.invoke` 第 1 次 | 2.61s |
| 复用客户端的 `retriever.invoke` 第 2 次 | 0.03s |
| `_dense_search`（现行实现）预热后 | **0.05s** |

即：第一次 63s 是模型/索引一次性加载；之后 dense 段已降到毫秒级，**57s 花在检索链路的其他环节**（候选构造、稀疏打分、重排、父块注入等）。分段归因见 §4.4。

### 4.4 分段归因（热进程逐段计时，同一问题）

| 整条 `hybrid_retrieve` 第 3 次 | **115.86s** | 退化到约 2 倍，提示资源层面不稳定（疑似 4GB 显存与 CPU 之间换页） |

**结论**：
1. 单次问答的检索延迟 **几乎全部来自 `src/ai/reranker.py` 的 CrossEncoder 重排**，与向量检索、BM25、融合、MMR 都无关。
2. **机制已确认（不是猜测）**：`bge-large-zh` 占 1.30GB + `bge-reranker-v2-m3`（fp32）占 2.27GB = **3.57GB 已分配，显存 free 归零**（总 4.29GB）。此时重排 n=4 → 6.02s、n=10 → 9.97s、n=30 → 39.71s；而**纯 CPU** 跑 n=30 是 50.40s，与线上观测的 56s 同量级——即「GPU 显存打满后实际按 CPU 速度在跑」。同一进程内连跑第 3 次翻倍（56s → 116s）也是这个抖动的表现。
3. 对本大点的直接意义：**缓存命中一跳就能省掉这 56~116s**，这就是「会话级缓存」的最大收益来源；同时「热态检索仍要 1 分钟」本身也解释了用户体感慢。
4. 与本大点的关系：按 2026-10-23 第二轮口径 P1（§1.3），**重排优化已纳入大点 01**，具体解法见 §5.5。

## 五、草案逐条对应的技术路径

### 5.1 Agent 化（草案 1）

**可行路径（LangChain 1.x 官方姿势）**

```python
from langchain.agents import create_agent
from langchain.tools import tool

@tool
def retrieve(query: str) -> str:
    """检索安全知识库，返回带 [来源: 文档#章节] 标注的父块文本。"""
    ctx, src = hybrid_retrieve(query, use_rewrite=False)   # 改写交给上层/Agent，检索层不重复改写
    return ctx

agent = create_agent(
    model=llm_client.chain,          # 复用现有 ChatOpenAI + with_fallbacks 降级链
    tools=[retrieve],
    system_prompt=<safety_qa 改造版>,
    checkpointer=<MemorySaver 或 RedisSaver>,
)
for chunk in agent.stream({"messages": [("user", q)]},
                          config={"configurable": {"thread_id": f"conv-{conv_id}"}},
                          stream_mode="messages"):
    ...  # 逐 token 拼现有 SSE 格式
```

| 问题 | 现状线索 |
|---|---|
| 工具集怎么定 | 至少 `retrieve(query)`；可选 `get_retrieved_blocks()`（读会话缓存）、`judge_sufficiency(question)`（也可作为中间件/结构化输出，而非工具） |
| 多轮状态存哪 | `thread_id = conv-{conversation_id}`；`MemorySaver` 只在单进程有效（重启丢、多 worker 不共享）；Redis 检查点需装 `langgraph-checkpoint-redis` |
| SSE 契约能否不变 | 能：`stream_mode="messages"` 的 `AIMessageChunk.text` 逐块映射到现有 `data: {"delta": ...}` |
| 延迟代价 | Agent 每轮一次 LLM 往返；本机实测 LLM 调用 **冷 18.25s / 热 1.88s**（§4.3）。热态下 2-3 轮尚可接受，但真正的延迟大头不在这里，而在检索链路本身（42~155s/次，见 §4.3）与上下文体量 |

**风险**：Agent 化把「延迟可控的固定工作流」换成「模型决定调几次工具」，与现场快速提问的场景冲突。是否值得，需要实测延迟对比（§八 E4）。

### 5.2 会话级检索块缓存（草案 2、3；缓存粒度按 P3 改为子块）

```
key   shudao:rag:conv:{conversation_id}
value {
  "blocks":   [ {chunk_id(文本哈希), doc, doc_type, chapter, article_no, source,
                 child_text, rerank_score, parent_ref} ... ],   # ← 子块，不是父块
  "queries":  [已执行过的检索子查询],
  "rewrites": [每轮 {original, rewritten[], ts}],
  "updated":  <epoch 秒>
}
TTL   600（滑动）
```

**为什么是子块（P3）**：父块 p50 = 117,312 字符（§4.3），缓存父块＝每轮往模型塞十几万字；子块 300~800 字符，体量可控，且命中后**可以跳过重排**（§4.4 的 56s 就在这里），这才是「逐步变快」的关键。父块只在**生成前**按命中的子块所属文档取一次（并裁剪），不放进缓存。

**滑动 TTL 的正确落点（对应草案 3「生成期间不消耗计时」）**

- 现在 `chat.py:74-80` 的 `setex` 在**检索完成后、生成开始前** → 生成时间会吃掉 TTL。
- 改法：在 SSE 生成器的 `finally`（回答落库那一步，`chat.py:132-142`）里 `setex`（写或刷新为 600）；生成多久都不影响计时起点。
- 追问命中缓存时同样刷新 TTL（语义 = 10 分钟无追问才清）。

**并发**：一条会话可能并发两个请求（接口允许），需要「最后写入者胜」或带版本号，避免块集合互相覆盖。

### 5.3 问题预处理（草案 4(0)）

按草案三个例子，预处理要输出**四类动作**，不是一个改写字符串：

| 动作 | 触发条件 | 例子 |
|---|---|---|
| A 句式规范化 | 非陈述句 / 口语 / 含指代 | 「什么情况容易感冒」→「容易感冒的情况」 |
| B 语义专业化 + 多角度扩写 | 知识库是书文/规范体 | 「容易感冒的情况」→「流感期换季期易感冒行为」+「预防感冒方法」 |
| C 多主题拆分 | 一题含两个语义差距大的主题 | 「怎么选择衣物和规划路线」→「衣物选择方案」+「路线规划技巧」 |
| D 剔除已检索项 | 会话上下文已拿到部分信息 | 上轮问过「氧气瓶使用方法」→ 本轮「潜水套装」只搜「潜水镜」「潜水服」 |

实现形态三种（代价不同）：① 纯 LLM 结构化输出（一次往返给全四类动作，本机 18s 量级是主要顾虑）；② 规则 + LLM 级联（明显句式走规则，复杂问题才调 LLM）；③ 并入 Agent 工具（自由度最高、可预测性最差）。

**已有资产可复用**：`query_rewrite` 场景与 `_keyword_split` 可作 B/C 动作的兜底。

### 5.4 「够不够」判定 + 缺口增量检索（草案 4(2)、Q1、Q3）

草案指定 Q1 = **LLM 判定**。落地形态建议「一次调用同时给判定与缺口」：

```json
{"sufficient": false,
 "missing": ["高处作业分级标准", "安全带高挂低用要求"],
 "queries": ["高处作业分级 坠落半径 标准", "安全带 高挂低用 要求"]}
```

- 输入：会话缓存块的**摘要视图**（doc + chapter + 首 200 字，避免把 226K 字符再塞一次）+ 预处理后的问题。
- 输出：`sufficient` 与缺口子查询；`true` → 直接生成；`false` → 按 `queries` 各跑 `hybrid_retrieve(use_rewrite=False)`，与缓存块按 `parent_text` 去重合并。
- 强约束（来自 §4.2 第 2 条）：**判定器输入必须摘要化**，否则判定这一步自己就把上下文顶爆。

### 5.5 重排优化（P1 新增，实测已找到解法）

#### 5.5.1 实测对照（同一批 30 个真实子块，长度 751~800 字符）

| 配置 | 显存占用 | n=4 | n=10 | n=30 |
|---|---|---|---|---|
| CUDA + **fp32**（现状） | 3.57GB（free 0.00GB） | 6.02s | 9.97s | **39.71s** |
| CUDA + **fp16** | 2.45GB | — | **1.00s** | **3.13s** |
| **CPU**（fp32） | — | — | 14.12s | 50.40s |

加载耗时：bge-large 47.42s、reranker fp32 24.16s、**reranker fp16 仅 4.24s**、CPU 版 2.89s。
显存账：总 4.29GB；bge-large 1.30GB → reranker fp32 再吃 2.27GB → free 归零 → 实际按 CPU 速度跑（CPU n=30 50.40s ≈ 线上 56s，互相印证）。

#### 5.5.2 解法（按性价比排序）

| # | 手段 | 实测/预期收益 | 对指标影响 | 落点 |
|---|---|---|---|---|
| S1 | **reranker 用 fp16 加载** | n=30：39.71s → **3.13s**（约 12.7×）；加载 24.16s → 4.24s | 排序分数差异需抽样核对（fp16 通常只影响小数位；用单题对比 top-4 是否一致） | `reranker.py:33-35` 增加 `model_kwargs={"torch_dtype": torch.float16}`（仅 cuda 时） |
| S2 | **显式 `batch_size`** | 现在 `predict()` 用默认 batch，fp16 下可再压一档 | 无 | `reranker.py:49` |
| S3 | **bge 嵌入也 fp16**（可选） | 显存 1.30GB → 约 0.65GB，给重排留余量，防抖动 | 向量一致性需抽样核对 | `embeddings.py:32-36` 的 `model_kwargs` 加 `torch_dtype` |
| S4 | **缓存命中直接跳过重排** | 追问省掉整段重排（3s/56s，视是否已修 S1） | 无（命中路径本来就不用重排） | 会话缓存 + Agent 工具层 |
| S5 | 降候选数（30 → 15） | 省一半重排 | **触碰指标红线**，必须全量评测 | 只在 S1-S3 仍不达标时考虑 |
| S6 | 换更轻的重排模型（如 base 版） | 显存与耗时都降 | **触碰指标红线**（v2-m3 是 ALL@10 0.83 的组成） | 同上 |

#### 5.5.3 预期延迟账（对照用户目标：首问 ≤ 60s、追问 15~20s）

| 阶段 | 现状 | 修 S1+S2 后（首问） | 命中缓存的追问 |
|---|---|---|---|
| 问题预处理/改写（LLM 热态） | ~1.9s | ~2s | ~2s（判定 + 补检决策） |
| dense + sparse + RRF | 0.33s | 0.33s | 0（命中） |
| **重排** | **39.7~56s** | **~3.1s** | 0（命中） |
| 缺口补检（如有） | — | — | 0~3.5s（仅在判定「不够」时） |
| LLM 生成（流式首字 + 生成） | 未单独计（见 §八 E4） | 未单独计 | 未单独计 |
| 合计（不含生成） | ~42~58s | **~5.5s** | ~2s |

结论：**S1 一项就能把首问从「约 1 分钟」压到 6 秒级**（不含生成），追问在缓存命中下只剩判定与生成——用户「首问 60s、追问 15~20s」的目标有充足余量。

#### 5.5.4 E6/E7 实测结果（2026-10-23，已执行）

**E6 · 排序一致性（同一问题、同一批 30 个真实子块 751~800 字符）**

| 项 | fp32 | fp16 |
|---|---|---|
| 重排耗时 n=30 | 36.40s | **3.16s** |
| top-4 | `[13, 18, 12, 23]` | `[13, 18, 12, 23]` |
| 分数 | 0.9897 / 0.9709 / 0.9671 / 0.9550 | 0.9897 / 0.9707 / 0.9673 / 0.9551 |

- **top-4 顺序一致 = True**，集合一致 = True，**全量 30 条排序一致 = True**
- 最大分差 **0.001615**（第 3 位 0.9671 vs 0.9673），对排序无影响

**E7 · fp16 稳定性（连跑 3 次 n=30）**

```
3.21s / 3.06s / 3.06s     抖动(最大/最小) = 1.05x
```
对比 fp32 时「56s → 116s」的 2 倍抖动：**抖动消失**。

**显存（fresh 进程）**：fp16 `allocated 2.45GB / reserved 2.63GB / device_free 0.73GB`（total 4.29GB）；fp32 为 allocated 3.57GB、device_free 0.00GB。即 fp16 留下约 0.7GB 余量，fp32 一点不剩。

**结论：S1（fp16）+ S2（显式 batch）可安全落地**——排序零变化、耗时降 11.5 倍、抖动消失。

#### 5.5.5 仍需在全量口径上确认的

1. **指标层面**：`eval_qa.py` 全量（用户口径 3~4 小时/次）需在实现期验收时跑，确认 ALL@10 仍 ≥ 0.80；调研期只做了单题排序一致性。
2. **长尾**：本次抽样是 30 条 751~800 字符的子块；若将来子块长度分布变化（如超长表格块），需重测一次 n=30 的耗时。
