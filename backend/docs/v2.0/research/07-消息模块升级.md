# 大点 07 · 消息模块升级 —— 现状调研

> 2026-11-05。**只做现状取证，不含裁定**（裁定待用户拍板后写入 `Verdict/07`）。
> 取证方式：读代码 + 连真实 Redis/MySQL 取数，所有数字均为本机实测。

---

## 一、结论摘要

消息模块本质是一段**「Redis 列表 + 只读不删」的临时通道**，不是消息中心：

| 维度 | 现状 | 一句话问题 |
|---|---|---|
| 存储 | 每用户一个 Redis list `shudao:notify:<uid>`，元素是 JSON 字符串 | **重启即全丢**（内置 Redis 无持久化）；无 TTL、无长度上限，靠 `allkeys-lru` 兜底 |
| 未读 | `unread = llen(key)` | 是"总条数"，**从不会减少**，前端却写「（N 未读）」 |
| 时间 | payload 只有 `message / hazard_id / type` | **没有时间戳**，前端渲染里也没有时间（`.notify-time` 样式写了但没用） |
| 接口 | `GET /api/notifications?limit=` + `DELETE /api/notifications` | 只能"看最新 50 条"和"全部清空"，**无已读、无单删、无分页、无筛选** |
| 前端 | 登录时刷一次角标；页面按 type 分组平铺 | 开着页面时**新消息不会提示**（要 F5） |
| 广播 | 每个隐患事件扇出给全体 admin（109 人）/ sfo（47 人） | 一个隐患走完生命周期 ≈ **536 条消息**；单个 admin 收件箱 ≈ 4 条/隐患 |

## 三、数据流

```
业务动作（H01/H04/H05/H06/K01/K05/Agent 补料）
        │  NotificationService.push(user_id, message, hazard_id?, msg_type)
        ▼
   RPUSH shudao:notify:<uid>  "{message, hazard_id, type}"      ← 无 TTL、无上限
        │
        │  GET /api/notifications?limit=50        DELETE /api/notifications
        ▼
   前端 loadNotifies()：按 type 分组 → 平铺渲染（无时间、无已读态）
   前端 loadNotifyCount()：只在登录后调用一次 → 角标「消息（N）」
```

## 四、接口契约（全量）

### `GET /api/notifications?limit=1..100`（默认 50）

```json
{"total": 37, "items": [{"message": "【接收上报】…", "hazard_id": 190, "type": "report"}], "unread": 37}
```

- `items` 取 `LRANGE key -limit -1` → **最早→最晚**，且**只给最后 limit 条**；
- `total` = `len(items)`（**被 limit 截断后的长度**，不是真实总数）；
- `unread` = `LLEN`（= 真实总数，与"是否读过"无关）；
- 无分页游标、无类型过滤、无搜索、无已读标记。

### `DELETE /api/notifications`

整键 `DEL`，**不可撤销、不能单删**。

## 六、存储与容量（真实配置）

```
redis_version   7.4.3
maxmemory       268435456 (256MB)
maxmemory-policy allkeys-lru     ← 内存吃紧时按 LRU 淘汰，通知键可能被静默淘汰
save            ""               ← 不落 RDB
appendonly      no               ← 不落 AOF
dbsize          0                ← 当前一个键都没有（上次重启后清空）
```

**三个后果**：

1. **重启即丢**：内置 Redis 是后端子进程（`redis_boot.stop()` 会结束它），而它既不 RDB 也不 AOF → 后端每重启一次，所有人消息清零；
2. **可能被淘汰**：`allkeys-lru` 是"所有键"共享策略 → 内存紧张时连 RAG 会话缓存、PPT 进度键一起淘汰；
3. **无上限**：`push` 不做 `LTRIM`，单用户列表只增不减（除非手动清空）。

## 八、缺陷清单（按严重度，均可复现）

### S1 · 功能性错误（用户能直接感知）

| # | 缺陷 | 证据 | 复现 |
|---|---|---|---|
| S1-1 | **重启即丢消息** | `redis_boot.py:165-166`（`--save "" --appendonly no`）+ `stop()` 结束子进程 | 收几条消息 → 重启后端 → `GET /api/notifications` 返回 0 条，但隐患时间线仍在 |
| S1-2 | **"未读"是假的** | `notifications.py:17` `unread = count() = LLEN` | 打开消息页后 `unread` 不变；只有「清空」才归零 |
| S1-3 | **消息没有时间** | payload 仅 3 个字段（`notification_service.py:32-33`） | 列表里分不出"5 分钟前"和"上周"的消息 |
| S1-4 | **管理岗消息洪泛** | 第 5/6/7 条触发点都发给全量 admin+sfo | 一个隐患验收后，每个 admin 收 2 条（验收结果 + 最终结果），叠加前面共 4 条 |

### S2 · 体验与契约问题

| # | 缺陷 | 证据 |
|---|---|---|
| S2-1 | 角标不刷新，必须 F5 | `loadNotifyCount()` 仅 1 处调用（登录后） |
| S2-2 | `total` 被 `limit` 截断，却当总数返回 | `notifications.py:16-17`；`limit` 默认 50，>50 条时永远显示 50 |
| S2-3 | 只能整体清空，**误清不可恢复** | `DELETE` → `DEL key` |
| S2-4 | 列表顺序是"最早→最晚"，分组后时间序更乱 | `LRANGE -limit -1` + 前端按 type 分组 |
| S2-5 | 收件人集合里可能含 `None` → 写入 `shudao:notify:None` | `hazard_service.py:297`：`{assignee, reporter} | set(managers) - {None}`，运算符优先级使 `- {None}` 只作用于右侧集合 |

### S3 · 架构与可维护性

| # | 缺陷 | 证据 |
|---|---|---|
| S3-1 | 无持久化/无归档，与"隐患时间线"存在两套真相 | `hazard_timeline` 有全量流转记录，消息重启后全丢 |
| S3-2 | 跳转依赖文案正则（「贡献 #id」） | 前端第 2080 行附近；文案调整即断链 |
| S3-3 | 无消息中心基本能力：分类筛选、搜索、分页、批量已读 | 接口层完全没有 |
| S3-4 | 无系统公告 / 无邮件·短信·企业微信渠道 / 无用户消息偏好 | 全项目无相关代码 |
| S3-5 | 测试只有 1 个"Redis 挂了不 500"的用例 | `tests/test_stats_notifications.py:42` |
| S3-6 | 类型常量与文案前缀 `【…】` 双轨维护（`TYPE_*` 与文本） | `notification_service.py:19-25` + 各 push 点 |

## 十一、待拍板（调研结论出来后再定）

1. **范围**：只修 S1（能用的消息）还是做到 C（可查可归档的站内信）？
2. **存储**：走 MySQL 表（持久、可回填、可对账）还是继续 Redis（快，但重启丢）？
3. **洪泛**：每个隐患是否还需要给 109 个 admin 全量推 4 条？改成"角色桶 + 按人已读"还是"只推相关人"？
4. **实时性**：30s 轮询够不够，还是要 SSE（复用聊天/PPT 那套）？
5. **历史**：要不要用 `hazard_timeline` 回填 190 条隐患的历史消息？
6. **渠道**：本期是否需要站外通知（邮件 / 企业微信）？

## 十二、验收口径草案（供定方案时细化）

1. 重启后端后，消息与未读数**不丢**；
2. 「未读」随阅读递减：进消息页可标已读，单条/批量都行；
3. 每条消息显示时间（相对 + 悬浮绝对）；
4. 角标在 30s 内（或实时）更新，无需 F5；
5. 列表支持分页（>50 条可翻页）与按类型筛选；
6. 单隐患消息数从 ≈533 条降到可解释的数量，并有统计口径；
7. 历史隐患可用时间线回填，回填后与 `hazard_timeline` 条数可对账。

## 十三、实测附录（本机跑过，不是推演）

### 13.1 未读语义 + limit 截断（`NotificationService` 直调）

```
push 5 条到 uid=999999
count() = 5
list_for(limit=3) -> 3 条，内容 ['测试消息 2','测试消息 3','测试消息 4']   ← 只给最后 3 条、升序
再次 count() = 5                                                          ← 读过也不变
```

结论：`unread` 就是 `LLEN`；`total` 就是 `len(截断后的 items)`。两个字段都不能当"未读数/总数"用。

### 13.2 `None` 键（`hazard_service.py:297` 的优先级隐患）

```
NotificationService.push(None, "孤立消息") 
EXISTS shudao:notify:None -> True
GET    shudao:notify:None -> ["{"message": "孤立消息", ...}"]
```

结论：只要某条隐患的 `assignee_id` 或 `reporter_id` 为 `None` 走进那个集合运算，就会生产一个**没人会读的孤儿键**（还会被 LRU 计入）。代码表达式 `{a, r} | set(managers) - {None}` 因 `-` 优先级高于 `|`，`- {None}` 只作用于右侧。

### 13.3 无持久化（磁盘侧证据）

```
$ redis-server --save "" --appendonly no      # redis_boot.py:165-166 的启动参数
$ ls tools/redis/data                        -> 无 data 目录
$ ls tools/redis/*.rdb tools/redis/appendonlydir -> 都没有
```

结论：不存在任何快照/AOF 文件，进程一退出（后端子进程随 `stop()` 结束）消息即丢。当前 `dbsize=0` 就是上一轮重启后的状态。

### 13.4 清理

测试键 `shudao:notify:999999`、`shudao:notify:None` 已删除，测试后 `scan_iter("shudao:notify:*")` 为 0 个。
