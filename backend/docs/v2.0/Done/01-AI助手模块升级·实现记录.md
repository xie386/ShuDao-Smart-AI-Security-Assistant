## 一、改了什么（问题 → 做法 → 结果）

| # | 改造前的问题（实测） | 做法 | 结果（实测） |
|---|---|---|---|
| 1 | 缓存 key = `md5(question.strip())`，逐字匹配；真实追问几乎不可能命中（chat.py 原 `_qa_cache_*`） | 换成**会话级子块缓存**：`shudao:rag:conv:{conversation_id}`，value = `blocks[]`（子块窗口文本 + 精简 metadata + rerank_score）/ `queries[]` / `rewrites[]`；TTL 600s **滑动**，在 SSE 生成结束的 `finally` 里 `touch()` | 一次会话 4 轮后缓存 8 块 / 16,005 字节 / TTL 590s；追问 `mode=cache` 时检索段 0ms（只剩判定） |
| 2 | 只缓存父块会把上下文顶爆（父块 p50 = 117,312 字符，4 块 ≈ 47 万字） | 缓存**子块**，且每个子块只存「父块中围绕它的窗口」（默认 `RAG_CONTEXT_BUDGET_CHARS/4` = 4000 字符） | 单会话缓存 value 16KB；喂模型的 context 8,305~12,800 字符（改造前同题 100,594~209,330） |
| 3 | 问题原样进检索，疑问句/口语化句式拉低召回；追问里的指代（「那安全带呢」）无法独立检索 | 新增**问题预处理公共步骤**（`query_preprocess.preprocess`）：a) 陈述句化 b) 语义专业化 c) 多主题拆分（**仅建议**，Agent 决定，上限 2 条）d) 剔除已检索项 | 实测原话「那安全带的具体要求呢？」→ 检索式「安全带的具体技术要求与使用规范（佩戴、栓挂高挂低用、检查与报废）」；`covered_dropped` 正常回填到 user 消息 `refs` |
| 4 | 追问一律整题重检索（多次检索 = 多倍耗时） | 追问先**判定充分性**（`sufficiency.judge`），够就只生成，不够只发**缺口子查询**（上限 2 条） | 4 组实测：`full / incremental / incremental / cache`；`incremental` 每轮只补 1 条子查询 |
| 5 | 检索是直连四步流水（稠密+稀疏→RRF→重排），模型不会自己补资料 | 改用 `langchain.agents.create_agent`，工具 `retrieve_more(queries)`，**整轮最多 1 次**（工具内部计数，确定性拒绝，不靠模型自觉）；异常回落 `llm_client.chat_stream`（含 agnes 降级链） | Agent 就绪日志正常；真实补检一次（冷启动进程内实测 `tool_calls=1`，回答引用了补检回来的条款）；正常答题 0 次调用（不拖时间） |
| 6 | 重排 fp32 把 4.29GB 显存打满，n=30 实测 39.71s，占整条检索 99% | 重排默认 **fp16**，请求体 `high_precision=true` 切 fp32；切精度先卸载旧模型再加载（加锁防并发来回重载）；前端加「高精度」开关（`localStorage.sd_high_precision`） | fp16 n=30 3.13s；真机 `fp16` 检索 2.4~6.4s、`fp32` 16.1~19.3s；meta 帧如实回报当前精度 |
| 7 | 首问冷启动：BM25 语料加载 159.8s + 建索引 17~18s ≈ 175s，远超「首问 ≤60s」 | 语料**只读 `documents`**（不再拉 2.2GB 的 `parent_text`）→ `bm25_corpus.pkl` 磁盘缓存（17.8MB，块数校验）；metadata 按 id 只回查稀疏命中的 ≤30 条；启动后后台 `warmup()` 预热；检索端 `_await_warmup()` 防「预热中提问」重复建索引 | 语料 5.8~8.0s、BM25 17~18s、embedding 7.3~8.1s、重排 3.6~3.9s，**预热总计 33.9~35.8s**；预热中提问从 93.9s 降到 34.5s；预热完成后首问检索 **2.4s**、全程 **20.8s** |

## 四、偏差与事故（如实记录）

1. **Agent 不用 checkpointer**（偏离裁定 2 的措辞）→ 已立裁定 9，理由：DB 才是唯一事实来源、避免双份上下文、避免单进程内存状态。
2. **first attempt 写出 2.2GB pickle**：第一版把 `metadatas`（含 `parent_text`）一起缓存，文件 2,200,987,776 字节、进程内存飙到 800MB+ 后崩溃（exit 139）。改为只读 `documents` + `ids`，缓存降到 17.8MB，并删除旧文件。→ 裁定 10。
3. **预热中提问导致重复建索引**：`lru_cache` 不防并发，实测首问检索 93.9s。加 `_await_warmup()` 后同场景 34.5s。
4. **meta 行被重渲染覆盖**：第一版把状态行 append 到回答气泡，`finally` 里 `loadConvs()/openConv()` 用 DB 消息重渲染气泡 → 状态行立即消失（Playwright 等到超时才发现）。改为输入区上方常驻 `#chat-meta`。
5. **退化模式首问被判成 `incremental`**：初版退化分支对所有轮次都先判定，导致「新会话第一问」也走缺口检索。已加 `ChatService.has_messages()` 识别首问，退回首问全量检索（重测 `mode=full`）。
6. **回归：判定标准文档路径**（本大点外部影响）：文档重组把 `施工安全领域文件鉴别判定标准.md` 移到 `docs/v1.0/` 后，`routers/knowledge_contrib.py` 的 `/api/knowledge-contrib/review-standard` 与 `tests/test_knowledge_contrib.py::test_doc_exists` 都指着旧路径（功能会 500/404）。已同步为 `docs/v1.0/…`，测试恢复通过。
7. **文档里两处笔误**：3.3 表首问 context 写成「83,67 字符」（实际 8,367）；`generate` 段耗时随答案长度波动（2,467 字 ≈ 24.6s、5,556 字 ≈ 67s），不是检索回归。
8. **`contextvars` 跨上下文 bug（用户真机发现，2026-10-23 21:16）**：日志 `Agent 生成失败，回落直连 LLM: <Token var='chat_agent_ctx' ...> was created in a different Context`。
   - 根因：初版用 `_CTX: ContextVar` 传「本轮运行上下文」，在 `stream_answer()` 里 `set()` / `finally reset(token)`；而 Starlette 用 `iterate_in_threadpool` 迭代**同步**生成器，每 `next()` 都在线程池的**新 context 副本**里执行 → `reset(token)` 必然抛 `different Context`，异常从 `finally` 冒出被 `chat.py` 的 `except` 兜住 → **Agent 路径在真实服务里从未生效**，回答一直是「直连 LLM」回落结果（所以速度看着还行，但工具补检、Agent 判定都没跑）。
   - 修复：运行上下文改由 **LangChain `config.configurable`** 传递（`stream_answer(..., config={"configurable": {_CTX_KEY: run_ctx}})`，工具内 `ensure_config()` 读取；`run_ctx` 是同一个 dict 对象，跨线程修改可见）。已加两条回归用例（`test_run_ctx_comes_from_langchain_config` / `test_chat_agent_does_not_use_contextvars`）。
   - 验证（模拟 Starlette 的逐次线程池迭代，`probe_agent_ctx_fix.py`）：
     ```
     [1] 工具直接调用 calls=1 new_blocks=4        # ensure_config 能读到 config 里的 run_ctx
     [2] 线程池逐次迭代 19.2s tokens=662 calls=1 new_blocks=4 error=None   # 不再抛 different Context，且流中真的调用了工具
     ```
   - 教训：**「功能看起来能用」不等于链路生效**——回落分支会把真实异常吞掉。凡是 `except` 回落的地方，验证时必须确认回落分支没被走到（看日志关键字「回落直连 LLM」）。
9. **追问的回答没有来源标签与点赞踩（用户真机发现，2026-10-23 21:33）**：首问正常、追问缺 refs/rate，但 DB 里追问那条 `references` 有 8 条来源（`check_conv_refs.py` 实测）——纯前端问题。
   - 根因：`refs` / `.rate-row` 只在 `renderMsg(m)` 里生成（即 `openConv()` 按 DB 重渲染时），流式气泡只有纯文本；`send()` 的 `finally` 只在 `!curConvId`（首问）时调 `openConv`，追问不调 → 追问气泡永远是裸文本。
   - 修复：`finally` 里改为「有回答就按 DB 重渲染当前会话」（`await openConv(curConvId)`）；为此把 `answer` 提到 `try` 外声明。注意 `#chat-meta` 在 `#chat-area` 之外，重渲染不会清掉本轮状态行。
   - 验证（真机 Playwright，走用户正在跑的后端）：`首问 来源标签=4 点赞踩=2 / 追问 来源标签=6 点赞踩=2`。
10. **Agent 补检的来源没进 `references`**：`refs_json` 原本在**生成之前**算好，导致补检命中块被回答引用却点不开。已改为生成后合并（新增 `_merge_sources()`，按 `doc+章节` 去重），日志同时打出「新增来源 N 条」。
