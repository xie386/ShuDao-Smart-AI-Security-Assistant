## 1. 一句话概括这次改动

**在"预处理 + 检索"之前加一道门：先问模型一句"这是闲聊还是问业务"，闲聊就直答、什么都不查；判定失败就当业务题继续（宁多查）；检索炸了就降级说清楚，不再让整轮 500。**

---

## 2. `prompt/prompts.yml`：两个新场景

### 2.1 `chat_intent`（分流）

- **只输出一行 JSON**：`{"intent":"chat|knowledge","reason":"≤12字"}`。为什么不让它输出自然语言？解析成本、以及"模型一闲聊就多写"的不可控性。
- 四条判定规则是按实测坑写的：
  1. 含业务诉求即 `knowledge`（混合句不拆）；
  2. **指代型追问**（「第一问」「那…呢」）必须结合【会话上一轮】判 `knowledge`——不带上下文时模型会判 chat（调研实测，这是唯一一条 MISS）；
  3. 明确"不用检索"→ `chat`，但同句另有业务问题仍 `knowledge`；
  4. 拿不准 → `knowledge`。
- 占位符只有 `{history}` 与 `{question}`：`render()` 是白名单替换，JSON 花括号不会被当占位符（`prompts.py` 顶部注释有说明）。

### 2.2 `chat_assistant`（闲聊直答）

- 明确写"**没有被注入知识库资料**"，并禁止编造条文/条款号/统计数字——这是防"绕过检索套法规答案"的软约束。
- 允许它讲清"不能自我学习、知识库由管理员维护"——这是用户本次问题的真实答案（"你有没有自我维护能力"）。
- 注入了【最近对话】（最近 3 轮），但不注入资料。

## 3. `src/ai/intent.py`：判定器（178 行）

| 位置 | 关键点 |
|---|---|
| `_model()` | **独立 `ChatOpenAI`**：构造级 `timeout=CHAT_INTENT_TIMEOUT`、`max_retries=0`、`max_tokens=80`。为什么不复用 `llm_client.chat`？它的超时是客户端级 60s，且试过 `model_copy(request_timeout=…)` **不生效**（0.001s 下请求照常成功）。判定必须"要么 8s 内给答案，要么保守回退"，不能拖 60s。 |
| `_parse()` | 三层容错：带引号 JSON → 裸词（模型只回 `chat`）→ 花括号里捞 JSON。都不行返回 `None`（→ 保守回退 + `degraded.why="unparsable"`）。 |
| `detect()` | **永不抛异常**。四种返回：正常判定、空问题、开关关闭（不调模型）、异常/不可解析（`degraded={kind:"intent", why:...}`）。 |
| `_parse` 之外的坑 | 判定输入截断：`hint` 超过 `CHAT_INTENT_MAX_HISTORY_CHARS` 时按**字符头截**（问题在前、回答在后），避免把上一轮问题整段切掉；`question` 只喂前 500 字。 |

**改错会怎样**：把 `detect()` 写成会抛异常 → `event_stream()` 第一行就炸，整轮 500（比改造前更糟）；把 `_model()` 换回 `llm_client.chat` → 网络抖一下判 60s，闲聊首字目标（≤5s）直接失守。

## 4. `src/routers/chat.py`：编排（本次改动最集中）

### 4.1 顺序（改前 → 改后）

```
改前：保存用户消息 → _prepare()（预处理 → 判定/检索）→ 生成 → 落库
改后：保存用户消息前先取 last_round_hint → 保存 → detect()
        ├─ chat  → 直接流式直答 → 落库（refs 只写 intent）→ DONE
        └─ knowledge → _prepare()（预处理 → 判定/检索，已带降级）→ 生成 → 落库
```

### 4.2 三个辅助函数

| 函数 | 作用 | 为什么单独抽 |
|---|---|---|
| `_safe_retrieve(queries)` | 包住 `retrieve_queries`，异常 → `([], {kind:"retrieval", why, detail})` | 三处检索调用（增量×2、全量×1）共用同一口径；漏一处就还会 500 |
| `_update_user_refs(msg_id, payload)` | 回填 user 消息 refs | 闲聊与知识两条路都要回填，写法必须一致 |
| `_trim_current(history, question)` | 去掉 history 末尾"本轮问题"那行 | `build_history()` 是在保存本轮问题**之后**调的，history 自带本轮；闲聊直答再塞一次 question 就重复了 |

### 4.3 meta 与审计字段

`meta` 新增 `intent`（含 `label/reason/ms/model/degraded`）与 `retrieval_degraded`；`mode` 多一档 `chat`。
`refs`：知识轮 `{"preprocessed":…, "intent":…}`；闲聊轮 `{"intent":…}`（没有 preprocessed）。**不动表结构**——复用 `chat_messages.references`。

### 4.4 降级的两道网

1. **内层**：`_safe_retrieve` 只兜检索；
2. **外层**：`event_stream()` 里 `_prepare()` 整体 try/except → 构造一个"空资料 + `retrieval_degraded`"的 `prepared`。

为什么两道？实测事故是 `OSError(22, '.env')`，它发生在 `get_vectorstore()`（检索内部）；但 `sufficiency.judge` 也会调模型，预处理也可能崩——外层兜底保证"任何原因都不 500"。
降级时把 `context` 换成 `RETRIEVAL_DEGRADED_NOTE`，让模型**自己说出来**没检索到；同时 `sources=[]`、assistant `refs=None`，**不伪造出处**（裁定 5 的反向约束）。

## 5. `src/services/chat_service.py`：`last_round_hint()`

- 取最近 4 条，找"最后一条 assistant + 最后一条 user"。
- **必须在保存本轮用户消息之前调用**（`chat()` 里就是先 `has_messages` → `last_round_hint` → `save_message`）。晚一步取到的是本轮自己，指代追问就失去上下文。
- 回答只取前 200 字：判定只需要"上一轮在讲什么"，不需要全文。

---

## 6. `src/services/preprocess_audit.py`：审计兼容"没有预处理"的轮次

- 新增 `parse_intent()`（归一化：非法 label → `knowledge`、`ms` 转 int、非 dict 的 `degraded` 丢弃）。
- `build_rounds()` 的轮次里多 `intent` 字段——闲聊轮 `preprocessed=None` 但 `intent` 有值，**不再是"异常数据"**。
- `collect()` 增 `rounds_with_intent`、`chat_rounds`（探针与前端可用）。

**改错会怎样**：只在有 `preprocessed` 时才生成轮次 → 闲聊轮在审计里"消失"，用户点 🔎 会看到"该轮没有预处理记录（01 之前）"，等于把新功能说成历史数据。

## 7. `src/core/config.py`：四个开关

```ini
CHAT_INTENT_ENABLED=True       # false = 跳过判定（回到 01 收官行为）—— 应急回滚
CHAT_INTENT_TIMEOUT=8.0        # 单次判定超时（超时按 knowledge 继续）
CHAT_INTENT_MAX_HISTORY_CHARS=600
CHAT_INTENT_MAX_TOKENS=80
```

`CHAT_INTENT_ENABLED` 的语义是"**完全不判**"，不是"判了但都当知识"——单测锁了"关闭时不调模型"，避免有人以为它还在偷偷花钱。

## 9. 测试：`tests/conftest.py` 是本次的"隐形改动"

- 门禁让**每个 `/api/chat` 用例**都会打一次真模型。新增 autouse 夹具把 `intent.detect` 换成"永远 knowledge"的桩：单测不打网络、不看模型脸色。
- 需要验证门禁的用例，自己 `monkeypatch.setattr(intent_mod, "detect", ...)` 覆盖（autouse 先执行，用例内覆盖生效）。
- `test_intent_gate.py` 里把**真实** `detect` 抓成 `_REAL_DETECT` 来测单元行为——否则会被同一夹具桩掉。

### `tests/test_chat.py` 为什么也改了

原有两个问答用例靠"Agent 调用失败 → 回落假流"才能断言假流文本。网络正常时 Agent 真答了，断言就挂（本次跑到过 1 次失败）。加了确定性夹具（`AGENT_ENABLED=False` + `retrieve_queries` 返回空），用例变快（207s → 37s）且与网络解耦——**断言一条没动**。

## 10. `scripts/probe_intent_e2e.py`：真机探针

- 用一次性账号（`intent_probe_<随机>`）注册后登录，**不碰真实账号、不在脚本里放密码以外的凭证**。
- 覆盖：闲聊/知识/指代追问三问 + 审计 + Redis 缓存隔离检查。
- 为什么单独写脚本而不写进 pytest：它要真模型、真 Chroma、真 Redis，属"真机验证"，跑一次几十秒到几分钟，不适合进单测。

## 11. 三个最容易改错的地方（复盘）

1. **顺序**：`last_round_hint` 必须早于 `save_message`——错一行，指代追问就退化成"第一问 = 闲聊"。
2. **缓存**：闲聊分支只要多写一行 `conv_rag_cache.touch(conv_id)`，后续追问的 `covered` 就会被闲聊污染，症状是"追问答得莫名其妙还很快"。
3. **审计**：把 `intent` 塞进 `preprocessed` 里能省代码，但会让前端 🔎 的空态判断失效（`preprocessed` 变成非空）——按"并列字段"写。

## 12. 思考题（读完之后）

1. 为什么判定失败要偏向 `knowledge`，而检索失败要偏"说清楚没资料"，而不是反过来？
2. 闲聊不写 RAG 缓存，为什么"知识轮"仍然要写？如果闲聊也写，最先出问题的会是哪条链路？
3. `_safe_retrieve` 只兜检索，为什么还要在 `event_stream()` 外层再兜一次？两个兜底各覆盖什么？
4. 如果把 `chat_intent` 的 `max_tokens` 调成 40 会发生什么？（提示：AGNES 审图时 `reasoning_content` 吃满 token 导致 `content` 为空）
