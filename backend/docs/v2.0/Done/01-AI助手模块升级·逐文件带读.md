## 1. `backend/src/core/config.py`（新增 01 配置段）

**在链路里的位置**：全部开关的单一来源。

| 位置 | 内容 | 检查要点 |
|---|---|---|
| `:75` | `RERANKER_DTYPE="fp16"` | fp16/fp32 的**默认档**。改了它，所有没带 `high_precision` 的请求都跟着变 |
| `:76-77` | `RERANKER_BATCH_SIZE=8`、`RAG_HIGH_PRECISION_DEFAULT=False` | 批量 8 是 4.29GB 显存下实测不 OOM 的值；`RAG_HIGH_PRECISION_DEFAULT` 给「以后想默认高精度」留的口子 |
| `:78-80` | `RAG_CONV_CACHE_ENABLED/TTL/CONTEXT_BUDGET_CHARS` | TTL 600s 是**滑动**语义（见 §3 `touch()`）；预算 16,000 字符是本次把 100K~209K 压下来的那个数 |
| `:81-83` | `AGENT_ENABLED`、`AGENT_MAX_TOOL_ROUNDS`、`AGENT_MAX_SPLIT_QUERIES` | 三个回滚/护栏开关：关 Agent 走直连；拆分上限 2 |
| `:84` | `RAG_WARMUP_ON_START=True` | 启动预热开关（裁定 10）。关掉 → 回到「首问自己冷建 175s」 |

**思考题**：为什么 `AGENT_MAX_TOOL_ROUNDS` 写了却不在代码里读？（答：真正的护栏是工具内部计数「每轮 1 次」，配置项是给后续放开多轮留的位；读它反而会和工具内计数打架）

## 2. `backend/src/routers/chat.py`（重写 `chat()`，其余端点不变）

**在链路里的位置**：编排层。一次 `/api/chat` 请求的全部控制流都在 `_prepare()` + `event_stream()` 里。

| 位置 | 内容 | 检查要点 |
|---|---|---|
| `:159-172` | `chat()` 入口 | ① `reranker.set_high_precision(...)` 必须在**检索前**，它影响本轮所有 `rerank()` 调用；② `is_first = not ChatService.has_messages(...)` 必须在 `save_message` **之前**算，否则自己刚写的那条会让「首问」永远为 False；③ 请求阶段用一个 `SessionLocal` 查完即关，生成器内另开（FastAPI 的 `Depends(get_db)` 会随响应关闭） |
| `:60-157` | `_prepare()` | 四条分支：`cached` → 判定；`degraded and not is_first` → 只凭上下文判定；否则 → 全量检索。**顺序不能变**：判定输入是「块摘要」不是全文（否则判定本身就要读 8 万字） |
| `:100-112` | 合并去重 `merged` | 新检索块优先（`new_blocks + cached_blocks`），同 `chunk_id` 只留一份；再用 `format_context()` 统一裁剪 |
| `:175-186` | `event_stream()` 开头 | 预处理结果**回填** user 消息 `refs`：写库失败只记 debug，不打断回答（`update_message_refs` 在 try 里） |
| `:188-205` | meta 帧 | 先发 `{"meta": {...}}` 再发 delta。前端可忽略；排查「为什么这轮慢」全靠它（mode/precision/retrieval_ms/context_chars） |
| `:210-232` | Agent 分支 | Agent 异常 → `except` 里回落 `_stream_direct()`（含 agnes 降级链）。注意回落时**上下文/来源不变**，只是换生成方式 |
| `:160-176` | `_merge_sources()` | 合并「预检索来源」与「Agent 补检来源」，按 `doc+章节` 去重。**refs 必须在生成之后算**：补检发生在流式过程中，早算就会漏掉被引用的文件 |
| `:236-252` | `finally` 落库 | 顺序：`save_message(assistant)` → `put_blocks(本轮新块)` → `touch()`。`touch()` 一定在最后：TTL 从「回答完成」开始计时 |
| `:269-283` | `_stream_direct()` | 直连兜底，用 `safety_qa` 老模板（三占位：context/history/question），保证 `AGENT_ENABLED=false` 时行为等价改造前 |

**思考题**：为什么 `_prepare()` 不在 `chat()` 里同步跑、而是放进生成器？（答：同步跑会让 HTTP 响应头等 6~9s 才返回，浏览器侧看不到「正在连接」；放进生成器后 SSE 立刻建连，首 token 时间的语义才等于「用户真正开始看到字」的时间）

## 3. `backend/src/services/conv_rag_cache.py`（新增）

**在链路里的位置**：会话级子块缓存（Redis）。替代 `md5(question)` 逐字缓存。

| 位置 | 内容 | 检查要点 |
|---|---|---|
| `:46-75` | `normalize_block()` | 关键取舍：**不存 `parent_text`**，只存 `_cropped_block_text()` 切出的窗口（默认 4,000 字符）。存父块 → 单会话 47 万字 |
| `:83-131` | `put_blocks()` | ① 按 `chunk_id` 合并、分数取高（同块二次命中不重复占位）；② 只保留分数最高 `_MAX_BLOCKS=12` 块；③ `queries` 留最近 20 条、`rewrites` 留最近 10 条——防一个长会话把 value 撑大 |
| `:134-142` | `touch()` | Redis `EXPIRE`：**回答完成后**才续期，生成耗时不计入 TTL（改造前 `setex` 在生成前，30s 生成直接吃掉 30s TTL） |
| `:145-170` | `summary()` | 判定器的输入视图：doc#章节 + 每块首 200 字。**判定不该看全文** |
| `:173-183` | `available()` | `PING` 决定走正常模式还是退化模式；`RAG_CONV_CACHE_ENABLED=false` 也返回 False（用它做退化演练） |
| 全文 | 每个方法都 `try/except` | Redis 挂掉时 `get→None / put→False / touch→False`，**不抛异常**。这是「Redis 不可用不拖垮问答」的实现位置 |

**思考题**：`chunk_id` 为什么用「子块文本 md5 前 16 位」而不是 Chroma 的 id？（答：缓存块来自两条路——新检索块（有 Chroma id）与工具补检块；用文本哈希两条路天然对齐，且文本相同即语义相同，去重语义正确）

## 4. `backend/src/ai/query_preprocess.py`（新增）

**在链路里的位置**：所有路径的公共第一步（裁定 7）。

| 位置 | 内容 | 检查要点 |
|---|---|---|
| `:94-140` | `preprocess()` | ① 规则快路径：已是陈述句 + ≤30 字 + 无指代 + 无可剔除项 → 直接返回，省一次 LLM（实测省 2.5~8.4s）；② LLM 路径调 `query_preprocess` 场景，`temperature=0.0` |
| `:23-32` | `_INTERROGATIVES` / `_ANAPHORA` | 快路径的判据表。「那/它/这个」进 LLM 的原因是追问需要靠 `history` 补主语 |
| `:60-70` | `_format_covered()` | 把「已检索摘要」拼成 ≤8 条 `doc#章节：前 120 字`。**只给摘要不给全文**，否则预处理自身就要读几万字 |
| `:76-92` | `_fallback()` | LLM 挂了 → 原话照搜 + 零 LLM 关键词切分（`rag._keyword_split`），并标 `used_llm=False` |
| `:113-135` | 结果校验 | `split=false` 或子查询 ≤1 → **强制收敛成 `[declarative]`**；`split=true` → 截到 `AGENT_MAX_SPLIT_QUERIES=2`。模型说拆 3 条也不会真拆 3 条 |

**思考题**：为什么 `covered_dropped` 只记录、不参与删词？（答：删词是不可逆的信息损失——「剔除已检索项」的正确做法是让检索偏向缺口（判定器给缺口子查询），而不是把用户问题改瘦；记录它是为了可观测与后续分析）

## 5. `backend/src/ai/sufficiency.py`（新增）

**在链路里的位置**：追问路径的闸门（决定「直接答」还是「补检」）。

| 位置 | 内容 | 检查要点 |
|---|---|---|
| `:62-124` | `judge()` | 输入三样：预处理后的检索式、已有材料（块摘要 **或** 退化模式的 `cited_docs`）、会话近况 |
| `:76-84` | `_format_material()` | 正常模式用块摘要；退化模式只有「已引用的 doc#章节」也要能判 |
| `:31-42` | `_conservative()` | 判定失败/异常 → `sufficient=False` + `queries=[question]`：**宁可多查一次，不可答错**；且只查当前问题，不整题重检历史（裁定 6） |
| `:104-112` | 结果校验 | 判「够」→ 清空 `queries`（防止模型一边说够一边还想查）；判「不够」但没给子查询 → 用当前问题兜底；子查询截到 2 条 |

**思考题**：判定用 `temperature=0.0` 对不对？（答：对。这里要的是稳定分类而非创意；不稳定会导致同一问题两次走不同路径，耗时抖动）

## 6. `backend/src/ai/rag.py`（改动最多）

**在链路里的位置**：检索内核 + 冷启动治理。

| 位置 | 内容 | 检查要点 |
|---|---|---|
| `:51-97` | `_load_corpus()` | ① 只读 `include=["documents"]`（`ids` 默认返回）；② 磁盘缓存 `bm25_corpus.pkl`（`count` 校验）；③ 缓存写在**回源之后**，写失败只 warning |
| `:109-123` | `_hydrate_metadata()` | 稀疏命中 ≤30 条，用 id 批量回查 metadata（含 `parent_text`）。这是「不读 2.2GB 又不丢父块语境」的关键一步 |
| `:126-133` | `invalidate_corpus_cache()` | 清 `lru_cache` + 删 pkl。**必须与知识写入同生命周期**（`knowledge.upsert_chunks()` 末尾调用） |
| `:142-152` | `_await_warmup()` | 预热中到达的检索**先等**。为什么必须等：`lru_cache` 不防并发，两线程各建一遍 → 实测 93.9s |
| `:155-206` | `warmup()` | 语料 → BM25 → embedding → 重排，逐步计时进日志；`finally: _warm_event.set()` 保证失败也放行 |
| `:222-233` | `_sparse_search()` | BM25 分数 → Top-30 → `_hydrate_metadata()`。返回体多了 `id` 字段（供回查），`bm25_score` 语义不变 |
| `:252-258` | `_retrieve_candidates()` | 首行 `_await_warmup()`：所有检索路径的唯一入口都经过这里，一处加锁全局生效 |
| `:377-…` | `_multi_query_retrieve()` | 返回值从 2 元组变 3 元组：新增 `score_map`（全局候选索引 → 最高重排分）。用途：把分数一起写进缓存，命中时无需重排。**调用方只有 `hybrid_retrieve`（已同步）与 `retrieve_queries`** |
| `:564-585` | `retrieve_queries()` | 新公共入口：返回**子块级**命中 + `rerank_score`，不拼父块。给 chat 编排层用（要结构化才能算去重/预算） |
| `:588-606` | `_cropped_block_text()` | 「父块中围绕子块的窗口」：`half=(budget-len(child))//2` 向前后各取一半，两端加 `…`。找不到子块（如文本被清洗过）→ 退回父块前 budget 字 |
| `:609-660` | `format_context()` | ① 同一父块只留一次；② 各块均分预算、单块下限 300 字；③ 输出 `[来源: 文档#章节]` + `sources`（字段与改造前一致，A06 引用落库不受影响） |

**思考题**：既然有了 `_cropped_block_text()` 的窗口裁剪，为什么还要 `RAG_CONTEXT_BUDGET_CHARS` 总预算？（答：窗口只管单块，块多时仍会线性膨胀；总预算做的是「块数 × 单块」的上限，两条闸门叠加才能保证 context 稳定在 16K 量级）

## 7. `backend/src/ai/reranker.py`（重写）

**在链路里的位置**：重排（本次最大的耗时项）。

| 位置 | 内容 | 检查要点 |
|---|---|---|
| `:38-44` | `_want_dtype()` | 决策顺序：非 cuda → fp32（CPU 上 fp16 没意义）→ 请求开关 → 配置默认 |
| `:46-78` | `_load()` | **切换精度前先 `del` 旧模型 + `empty_cache()`**：4.29GB 显存放不下两份（fp32 2.27GB + bge-large 1.30GB 就 3.57GB） |
| `:80-89` | `model` 属性 | 双检锁：只有「未加载或精度不符」才重载；并发请求不会来回卸载/重载 |
| `:83-93` | `set_high_precision()` | 只改标志位，不动模型——真正的切换发生在下一次 `model` 访问 |
| `:97-112` | `rerank()` | `batch_size=RERANKER_BATCH_SIZE`；`top_k` 默认 `RAG_TOP_K_RERANK=4` |

## 8. `backend/src/ai/chat_agent.py`（新增）

**在链路里的位置**：生成层（Agent 化）。

| 位置 | 内容 | 检查要点 |
|---|---|---|
| `:26-40` | `_CTX_KEY` + `_current_run_ctx()` | 运行上下文（会话 id / 补检计数 / 新命中块）**随 LangChain `config.configurable` 传**，不用 `contextvars`。原因见下方「已知坑」：Starlette 迭代同步生成器时每次 `next()` 都在线程池的新 context 副本里跑，`contextvars.set/reset` 跨上下文会抛 `different Context`，Agent 整体失败回落直连 |

| `:101-127` | `stream_answer()` | `stream_mode="messages"` 只取 `AIMessageChunk`（工具消息的文本不喂给前端）；每轮把 `{_CTX_KEY: run_ctx}` 塞进 `config` 传给 graph |

| `finally` | 状态行 + **按 DB 重渲染** | ① 写 `#chat-meta` 文案（`MODE_LABEL` 四态 + 精度 + 检索秒数 + 上下文长度 + 来源数 + 退化标记）；② `await openConv(curConvId)` —— 引用标签与点赞踩只在 `renderMsg(m)` 里生成，不重渲染则追问气泡永远是裸文本（真机 bug 已踩） |

**思考题**：为什么元信息不存进 `chat_messages`？（答：要动 schema，且它只对本轮排障有用；要长期留档应该进日志而不是消息表——`logger.info("问答完成 …")` 已经在做这件事）

## 15. 已知坑（本次实现期真踩过的，改这里之前先读）

| 坑 | 现象 | 正确做法 |
|---|---|---|
| **`contextvars` + 同步生成器** | 真机日志：`Agent 生成失败，回落直连 LLM: <Token ...> was created in a different Context`；功能"能用"但其实 Agent 从未生效 | Starlette 用 `iterate_in_threadpool` 迭代**同步**生成器，每次 `next()` 都在线程池的新 context 副本里执行 → `set()` 与 `reset(token)` 跨上下文。运行上下文改走 LangChain `config.configurable`（`ensure_config()` 读），**不要**再引入 `contextvars`。回归用例：`test_run_ctx_comes_from_langchain_config`、`test_chat_agent_does_not_use_contextvars` |
| **把 `metadatas` 写进语料缓存** | `bm25_corpus.pkl` 变成 2.2GB，进程内存飙到 800MB 后 exit 139 | 语料只存 `ids/corpus`（17.8MB）；`parent_text` 用 `_hydrate_metadata()` 只回查命中的 ≤30 条 |
| **预热中提问** | 首问检索 93.9s（两线程各建一遍 BM25/各载一份模型） | `_await_warmup()` 在所有检索入口先等预热结束 |
| **自定义节点挂进回答气泡** | 状态行一闪就没（Playwright 等它内文直接超时） | 回答结束后 `loadConvs()/openConv()` 会用 DB 消息重渲染气泡；常驻信息挂 `#chat-meta`（输入区上方） |
| **业务日志看不到** | 只有 uvicorn 的 access log，`logger.info("问答完成 …")` 不出现 | `main.py` 模块级 `logging.basicConfig(level=INFO)`；uvicorn 只配自己的 logger，root 默认 WARNING |
