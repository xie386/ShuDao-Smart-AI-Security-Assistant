## 一、这一版到底改了什么（一句话版）

旧版：视觉模型一次调用 → 自己写建议 → 生成一张 `boxes.png` 只回给前端看，**不落库、别人看不到、字小到看不见**。
新版：**框能看清（类别色 × 等级深浅）→ 圈好的图存下来全业务可见 → 每条建议都有知识库/网搜依据**。

| 维度 | 旧 | 新 |
|---|---|---|
| 框 | 4 个固定色、4 px 线、20 px 字（4096 图上字高 0.49%） | 类别定色相 + 等级定明度、线宽 12/9/7/6 px、字号 = 图宽/64、白色外描边、填充 25% |
| 标签 | 长文字糊在框上 | 只显示 `#1`，悬停/聚焦才展开「#1 重大 物的不安全状态 基坑临边无防护」 |
| 交互 | 无 | 聚焦其余框淡化到 7%、选中填充 50%、类别筛选、卡片与框双向联动 |
| 建议 | 视觉模型自己编 | 并发 RAG 检索 → 缺口合并一次网搜 → 汇总时**每条必须带依据**，没依据就写「暂无依据」 |
| 图片 | `_boxes.png` 只回前端 | 原图 + 标注图（JPG q90）都落库；列表缩略图、详情可切换 |
| 存储 | 无 | 新表 `hazard_ai_analysis`（坐标 + 建议 + 标注图 URL），`schema.sql` 既有表一字未改 |
| 接口 | 一次性 POST（120s 超时） | SSE 四阶段（`vision → rag → websearch → synthesize`），预算 200s，旧 POST 保留 |

## 三、真机验收（本机实测）

### 3.1 无缺口场景（真实工地照片 1702×1276）

| 项 | 结果 |
|---|---|
| 识别隐患 | 5 条（较大×3 / 一般×1 / 轻微×1） |
| 检索分数 | 0.968 / 0.980 / 0.771 / 0.831 / 0.882 → **无缺口**（阈值 0.65） |
| 建议 | 4 条带知识库依据，如「沿基坑临边连续搭设防护栏杆并设置挡脚板和警示标识…（依据：shd-proc-check-202406·4.基坑支护）」 |
| 无依据 | 第 5 条（管理缺陷·木方散落）输出「暂无依据（知识库暂无该类隐患依据）」——**宁可不写，不编** |
| 标注图 | `1702×1276 → 823 KB`（JPG q90；旧版同图 PNG 约 19.7 MB） |
| 落库 | `POST /api/hazards` 201 → `GET /api/hazards/{id}` 返回 `annotated_url` + `ai_hazards=5`；列表项同样带 `annotated_url` |
| 耗时 | 冷启动整链 65.1s（含 RAG 预热 39s）；温态可复现约 20~25s |

### 3.2 强制缺口场景（`--gap`，阈值抬到 0.999）

| 项 | 结果 |
|---|---|
| 缺口 | 6/6 条 |
| 网搜 | **只发 1 次**合并查询；`ok=True`，来源 `www.jiangyin.gov.cn` / `zjw.sh.gov.cn` |
| 知识文件 | 自动提交贡献 #40（3,025 字，待审核）→ **探针数据已清理**（见 3.4） |
| 建议 | 6/6 条有依据，引用形如 `来源：网络-zjw.sh.gov.cn`，措辞为「可参照…」 |
| 耗时 | 网搜段 **105s**（超预算）→ 见下条改造 |
| 坐标缺失 | 6 条隐患里 2 条模型给不出 `location`（null）→ 标注图只画 4 个框（`annotate count=4`）。这是**模型能力边界**，不是画框 bug；已在卡片上标「未定位（无坐标）」，避免"清单 6 条、图上 4 个框"的困惑 |

### 3.3 由实测逼出来的两处改造

1. **网搜硬超时**：`run_sync` 只约束"采集"（45s），LLM 总结还能再拖 40s，实测 105s。→ `HAZARD_WEB_TIMEOUT=70`，超时放弃本轮、按无依据返回（单测 `test_fill_gap_hard_timeout`）。
2. **引用回落**：模型说"有依据"但章节名写法不一致时，原逻辑会整条丢掉（真机第 5 条检索到 0.88 却显示无依据）。→ 若它引的**文档确实在检索结果里**，回落到 Top1 块；若文档根本不存在（编造），仍判无依据（单测两条）。

### 3.3-b 实现期修掉的两个前端 bug（DOM 截图发现）

| bug | 现象 | 根因 | 修法 |
|---|---|---|---|
| 卡片编号从 #0 开始 | 卡片写 `#0/#1/#2`，图上标签却是 `#1/#2/#3`，对不上 | `hazards.map(hzItemHtml)` 把数组下标（0 基）直接当编号传 | `hazards.map((h,i)=>hzItemHtml(h,i+1))`，并加断言 `card_ids == ["#1","#2","#3"]` |
| 图片加载失败留一条黑边 | 画布还在、但 `<img>` 高度塌成 0，只剩黑色边框条 | 只设了 `img.src`，没处理 `onerror` | `img.onerror` 时隐藏画布（没图就没有叠加的意义） |

> 这两个都是"功能测试全绿、肉眼一看就露"的问题——所以 DOM 截图验证不能省。

## 五、已知限制 / 遗留

1. **SSE 帧到达时间无法用 TestClient 观测**：httpx 的 ASGITransport 会把整个响应缓冲完再返回（探针里所有阶段都打印同一时间戳）。真实 uvicorn + 浏览器是逐帧的；如需量化，用 `curl -N` 观察。
2. **网搜仍是同步阻塞**：单次最长 70s，加上视觉与汇总，最坏端到端约 100~140s，前端超时设 200s。若将来要更快，只能改异步补料（会违背"建议必须有依据"的即时性）。
3. **`/uploads` 仍匿名可读**（裁定 6 保持现状）：知道 URL 即可取图，属既有风险。
4. **`GET /api/hazards/{id}` 无权限校验**（06 之前就有）：本期只做到"全业务可见"，没有收紧可见范围。
5. **结果缓存 10 分钟**：键 = 图片 sha1 + 场景描述，不含模型版本；换模型后可能短时返回旧结果（可清 `hazard:ai:*`）。
6. **D 盘外接 USB SSD 的瞬时失联隐患**未解决（`disk 153`），代码侧未加 I/O 重试（用户已决定先换硬件）。

# 3) 彻底撤销：删表（会丢坐标与标注图索引；uploads 里的图不受影响）

# 4) 前端：把 h-ai-btn 的 consumeHazardStream 换回一次 POST /api/vision/hazard

## 七、验收建议（给用户）

1. **Ctrl+F5** 后进「隐患上报」，上传一张现场图 → 点「AI 识别隐患」，看阶段条是否走 识别中 → 检索知识库 → 汇总；
2. 鼠标悬停任一框：其余框应淡到几乎看不见、悬停框标签展开文字；点卡片看框是否同步高亮；
3. 点类别 chip：非该类框淡化；
4. 上报后进详情：应能切「原图 / 标注图」，且下方「AI 识别明细」每条建议后面都有「（依据：…）」或「（来源：网络-…）」；
5. 列表页每条记录左侧应出现缩略图（标注图优先）；
6. 用管理员账号看别人上报的隐患，确认详情同样能看到标注图（这就是"全业务可视"）。
