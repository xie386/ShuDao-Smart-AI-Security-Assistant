## 裁定 1（2026-10-23）：PPT 产物采用「改名 + 鉴权下载端点」，取消静态公开

| 项 | 内容 |
|---|---|
| **分叉点** | PPT 产物现状是「按主题命名 + 静态目录公开」（`ppt_service.py:153-154`、`main.py:135`）。修覆盖问题不必动鉴权，修越权问题不必动命名，两者要不要一起做？ |
| **可选方案** | **A** 只改名加 `u{uid}_t{tid}_` 前缀（改动最小，静态目录仍公开）；**B** 改名 + 改为鉴权下载端点 `/api/ppt/{id}/download` 并取消静态挂载；**C** 只加鉴权端点、不改命名 |
| **裁定结果** | **B** |
| **依据** | 用户口径（原话）：「B 改名 + 改为鉴权下载端点（/api/ppt/{id}/download 校验归属，取消静态公开）」。支撑证据：ISO-2 实测无 token 可取到 16.2MB 他人 PPT；ISO-1 实测同主题 3 条任务共用同一 `dest`。A 漏越权、C 漏覆盖，只有 B 两项同解 |
| **影响面** | `src/services/ppt_service.py`（产物命名 + 新增 `download_path()`）、`src/routers/ppt.py`（新增下载端点）、`src/main.py`（删除 `/ppt-files` 挂载）、`front/safety/index.html`（下载改带鉴权请求）。不涉及表结构与检索链路 |

## 裁定 2（2026-10-23）：试卷导出文件同批改鉴权，且只留一条取用通道

| 项 | 内容 |
|---|---|
| **分叉点** | 试卷导出文件同时被 `/exam-files/*` 与 `/uploads/exam/*` 两条静态通道暴露（`main.py:123,141`）。是彻底治理，还是因为 paper_id 不可枚举就先放着？ |
| **可选方案** | **A** 一并改鉴权下载端点 + 关掉 `/uploads/exam` 重复通道；**B** 保持现状；**C** 只关重复通道、仍留 `/exam-files` 静态 |
| **裁定结果** | **A** |
| **依据** | 用户口径（原话）：「A 一并改为鉴权下载 + 关掉 /uploads/exam 重复通道（只留一条路）」。证据：ISO-3 实测两条通道均无 token 可下（9660 / 39807 字节）。虽然 paper_id 为 uuid4 hex[:12] 不可枚举，但「同一产物两条无鉴权出口」属设计缺陷，与 PPT 同批治理成本最低 |
| **影响面** | `src/services/exam_export.py`（导出目录与返回路径）、`src/services/exam_service.py`（新增 `download_path()`、`file_url` 语义）、`src/routers/exam.py`（新增下载端点）、`src/main.py`（删 `/exam-files` 挂载 + 封 `/uploads/exam/**`）、前端下载改用带鉴权请求 |

## 裁定 3（2026-10-23）：用户上传的 PPT 模板维持全员共享，不做账号隔离

| 项 | 内容 |
|---|---|
| **分叉点** | `ppt_template_service.list_templates()` 不按 user 过滤，A 上传的模板 B 也能看到并使用（ISO-4）。这是缺陷还是有意设计？ |
| **可选方案** | **A** 维持全员共享（团队模板库）；**B** 按账号隔离（仅本人可见可用） |
| **裁定结果** | **A** |
| **依据** | 用户口径（原话）：「A 维持全员共享（团队模板库，在方案里写明是有意为之）」。项目语义支撑：模板属于企业演示规范类共享资产，与「个人产物」性质不同；隐患图片、知识贡献等真正私有的东西已各自隔离 |
| **影响面** | 不改代码。在 `v2.0规划文档.md` §00 明确写出「模板共享为有意设计」，避免后续被当成缺陷重复上报 |

## 裁定 4（2026-10-23）：历史产物文件不迁移，靠下载端点兼容读取

| 项 | 内容 |
|---|---|
| **分叉点** | 现网已有 3 个 pptx（`ppt_files/`）与 1 套试卷导出（`uploads/exam/`），改造后命名规则与目录都变。是迁移旧文件，还是让旧文件原地不动？ |
| **可选方案** | **A** 保留旧文件与原 `file_path`，仅新生成走新规则，下载端点做兼容解析；**B** 脚本批量重命名 + UPDATE `file_path`；**C** 直接删掉旧演示文件 |
| **裁定结果** | **A** |
| **依据** | 用户口径（原话）：「A 保留旧文件与原 file_path，仅新生成走新命名（不迁移）」。工程依据：现网仅 4 个文件、且均为演示数据；迁移要写 UPDATE 语句动用户数据，收益不抵风险；下载端点按数据库 `file_path` 定位文件，天然兼容老路径 |
| **影响面** | 无需数据迁移脚本；下载端点需实现「先按新目录、再按旧 `uploads/exam/`」两段解析；旧静态 URL 改造后失效，但旧记录仍可通过新端点下载 |

## 裁定 5（2026-10-23）：下载鉴权的 token 用「fetch + Blob」，不用 `?token=` query

| 项 | 内容 |
|---|---|
| **分叉点** | 产物改鉴权下载后，前端 `<a href>` / `<a download>` 无法携带 `Authorization` 头。token 怎么传给下载请求？ |
| **可选方案** | **A** fetch + Blob（`api()` 自动带 header，前端约 20 行）；**B** `?token=` query 参数（前端 2 行，但 token 进访问日志/浏览器历史/Referer）；**C** 后端先上、前端下载暂不可用 |
| **裁定结果** | **A** |
| **依据** | 用户在方案评审阶段的两条口径：① 开工口令为「先开工完成 00 大点（进入实现期）」，未对 `research/00` §八 R7 的三条候选另行改判；② 该项目为组内迭代但仍按生产标准处理账号数据，token 不应落 URL。安全收益（B 会留下日志痕迹）远大于 18 行前端工作量 |
| **影响面** | `front/safety/index.html`：`dlPpt()`（`:1634`）与 `exportExam()`（`:1863`）改 Blob 下载；服务端无需改动 |

## 裁定 6（2026-10-23）：历史 `/uploads/exam/**` 用中间件封 403，不迁移文件

| 项 | 内容 |
|---|---|
| **分叉点** | 试卷导出目录搬到 `exam_files/` 后，历史文件仍在 `uploads/exam/`，且被 `/uploads` 静态暴露。是封通道、搬文件，还是放任？ |
| **可选方案** | **A** 中间件对 `/uploads/exam/**` 返 403（不迁移）；**B** 搬 3 个历史文件并 UPDATE `file_path`（与裁定 4「不迁移」冲突）；**C** 放任（不满足裁定 2「只留一条通道」） |
| **裁定结果** | **A** |
| **依据** | 与裁定 2、裁定 4 一致：用户要求「只留一条通道」且「历史产物不迁移」。A 是唯一同时满足两者且不动用户数据的做法；老记录改由下载端点的两段兼容解析读取（实测 200，见 `../Done/00-账号隔离性前置检查·实现记录.md` §3.3） |
| **影响面** | `src/main.py:105-114` 新增中间件（仅拦 `/uploads/exam/` 前缀，不影响隐患图片与头像）；`src/services/exam_service.py:135-151` 双根白名单解析 |
