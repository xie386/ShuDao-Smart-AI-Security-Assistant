## 裁定 1（2026-11-05）：框色以**类别**为主维度，**等级**用同色深浅区分

| 项 | 内容 |
|---|---|
| **分叉** | ① 等级色（重大红/较大橙/一般黄/轻微灰）；② 类别色（4 类）；③ 类别色 + 等级深浅；④ 等级色 + 类别纹理。 |
| **裁定** | **③**。4 个类别固定色相，同类别内 4 个等级按 **HSL 明度梯度**（重大最深 → 轻微最浅，S=0.62，L=38%/46%/55%/64%），边框色 = 类别色 × 等级明度；叠加白色 1~2 px 外描边保证深/浅背景都可见。 |
| **色板（唯一事实源，前后端共用）** | 人的不安全行为（H212）：`#245C9C/#2C70BE/#4587D3/#6A9FDC`<br>物的不安全状态（H32）：`#9C6424/#BE7A2C/#D39045/#DCA66A`<br>环境的不安全因素（H145）：`#249C56/#2CBE69/#45D380/#6ADC99`<br>管理缺陷（H268）：`#5C249C/#702CBE/#8745D3/#9F6ADC`<br>（顺序：重大 / 较大 / 一般 / 轻微） |
| **依据** | 用户 2026-11-05：「不同类别不同色，同类别不同等级按照同颜色深浅程度区分」；类别是"隐患性质"，等级是"严重度"，两个维度必须同时可读，但 4×4=16 色无法逐色记忆，用「色相定位类别 + 明度定位等级」把认知负担压到两个一维判断。 |
| **代价** | 同一张图上若只有"重大/较大"，颜色接近（仅明度差）；用**标签文字 + 边框粗细**（重大 12px / 较大 9px / 一般 7px / 轻微 6px）补强。 |

## 裁定 2（2026-11-05）：聚焦单条时，其余框**淡化到 6~8%**（不隐藏）

| 项 | 内容 |
|---|---|
| **分叉** | ① 完全隐藏；② 淡化到 6~8%；③ 不变只加粗选中。 |
| **裁定** | **②**：选中框填充 50%、描边加粗到 14px、标签常显；其余框 `fill-opacity=0.06`、`stroke-opacity=0.25`、标签隐藏。 |
| **依据** | 用户拍板「淡化到 6~8%」。保留轮廓可维持"这张图上共有几处隐患"的空间感，隐藏会让画面跳变、失去上下文。 |
| **代价** | 深色背景上 6% 几乎等于不可见——但此时用户已聚焦单条，可接受。 |

## 裁定 3（2026-11-05）：标签**默认只显示序号**，悬停/聚焦才展开文字

| 项 | 内容 |
|---|---|
| **裁定** | 全显示态：每个框只画一个小序号角标（`#1`~`#n`，圆角矩形 + 类别色底）；鼠标悬停某框或聚焦某条时，该框展开完整标签「类别 · 等级 · 隐患名」。 |
| **依据** | 用户拍板「只留序号、悬停或聚焦时才展开文字」。4096 px 图上 4~8 个框若都常显文字，标签互相遮挡、且大面积覆盖现场细节（原型实测：杂草带与木板的标签在 1500 px 预览下会压住目标）。 |
| **补充约束** | 序号角标贴框左上角内侧（不越界）；展开标签自动内收，右侧/下侧空间不足时翻转到框内。 |

## 裁定 4（2026-11-05）：**上报前前端 SVG 渲染；上报后保存标注图**

| 项 | 内容 |
|---|---|
| **分叉** | ① 只前端渲染（不存图）；② 只后端烘焙（前端只显示结果图）；③ 前端渲染预览 + 上报后保存（后端烘焙落盘）。 |
| **裁定** | **③**：识别结果页用前端 **SVG 叠加**（可筛选/聚焦/零请求）；用户点「提交上报」时，把当前 `boxes_json` + 样式参数一起提交，由**后端烘焙**成 `_boxes.jpg` 并入库；详情页优先渲染可交互 SVG（有坐标时），缺坐标时退回静态标注图。 |
| **依据** | 用户拍板「在用户上报前前端渲染，上报后将有前端渲染的画圈后图片保存」。前端渲染保证交互；后端烘焙保证导出/打印/消息卡片有一份稳定图片，且不受浏览器渲染差异影响。 |
| **实现约束** | ① 前后端共用一份样式配置（类别色板、等级明度、透明度、字号规则），禁止两处各写一份；② 烘焙只允许用 `boxes_json` 里的坐标，不得二次调用视觉模型；③ 图片改 **JPG q90**（实测 19.7 MB → 2.5 MB）。 |

## 裁定 8（2026-11-05）：采用 **B 混合编排**，外层包装为「隐患识别 Agent」

| 项 | 内容 |
|---|---|
| **分叉** | ① A 全 Agent（LLM 自主决定查几次、改查询）；② **B 混合编排**；③ C 只注入检索结果。 |
| **裁定** | **②**。管线固定为：视觉识别（确定性）→ 每条隐患构造 1 条检索式 → **并发 RAG** → 缺口判定 → 缺口合并为 1 次网搜 → 一次 LLM 汇总（每条建议 + 引用）→ 返回结构化 JSON。对外仍称"隐患识别 Agent"，工具集为 `search_kb` / `report_knowledge_gap`。 |
| **依据** | 用户拍板「按照 B 混合编排」。实测：温态单查询 1~2.7s，4 条并发 ≈ 3s；步骤本身是确定的（先看图、再逐条查、再汇总），把"查几次"交给 LLM 只会带来抖动（同图两次结果不一致）。 |
| **代价** | 不是"LLM 自主循环"，Agent 味靠工具与补料闭环体现；文档与答辩需讲清这一点。 |

## 裁定 9（2026-11-05）：知识库缺口 → **同步网搜**写建议，引用标「网络-网址」，并提交知识文件审核

| 项 | 内容 |
|---|---|
| **分叉** | ① 异步网搜（先出建议、后台补）；② **同步网搜**（等结果再写建议）。 |
| **裁定** | **②**。某条隐患 `Top1 < 0.65` 或 0 命中 → 判定缺口 → **把所有缺口条目合并成 1 次**网搜（`agent_scout.run_sync`，预算 60s：采集 45s + 总结 15s）→ 用返回的知识片段写该条建议 → 引用格式 **`（来源：网络-<主机名>）`**（如 `（来源：网络-www.hunan.gov.cn）`）→ 同一次调用里把总结写成知识文件**提交管理员审核**（`≥1000 字`才提交，与 04 一致）。 |
| **依据** | 用户拍板「知识库有缺口通过网搜结果写建议，标注来源:网络-网址，然后再写知识文件提交审核」。异步会让"建议"先于证据产生，正是前几轮"假上报"的成因。 |
| **代价（必须写进 UI）** | 有缺口的识别会明显变慢：视觉 10~30s + RAG 3s + 网搜 45~60s + 汇总 8s → **总时延可达 60~110s**。前端超时必须从 120s 放宽到 **200s**，并显示阶段文案（"识别中 → 补充资料中 → 汇总中"）。 |
| **失败降级** | 网搜失败/超时 → 该条不出建议，显示「暂无依据（网搜未成，未提交）」；不得编造条款号。 |

## 裁定 10（2026-11-05）：建议**必须带引用**，无依据就不写

| 项 | 内容 |
|---|---|
| **裁定** | 每条「建议」必须带且只带一种引用：<br>· 库内命中：`（依据：<doc>·<chapter>）`<br>· 网搜命中：`（来源：网络-<host>）`<br>· 两者皆无：**不写建议正文**，改显示「暂无依据（已提交补充）」，并在 `grounded=false` 标记 |
| **依据** | 用户要求"通过网搜结果写建议"——即建议必须有证据来源；视觉模型自己编的建议容易给出无法核对的数值/条款（与 01 大点"不编造"口径一致）。 |
| **输出契约** | `hazards[i]` 增 `suggestion / refs[] / grounded / gap_note`；`refs` 元素 `{kind:"kb"|"web", doc?, chapter?, host?, score?}`。 |
| **前端** | 建议行末渲染引用小字；`grounded=false` 时整条建议区显示黄色提示条（与"未审核"样式区分）。 |

## 裁定 11（2026-11-05）：识别接口改 **SSE 分阶段推送**，原 POST 保留兼容

| 项 | 内容 |
|---|---|
| **分叉** | ① 保持一次性 POST（前端 200s 超时、单状态）；② **改 SSE 分阶段**；③ 先 POST、SSE 后置。 |
| **裁定** | **②**。新增 `POST /api/vision/hazard/stream`（SSE），原 `POST /api/vision/hazard` **保留**（脚本/测试/兼容用）。前端切到 SSE。 |
| **事件协议** | `data:{"stage":"vision","msg":"正在识别现场隐患…"}` → `{"stage":"rag","queries":[...],"hits":[{"index":1,"top":"…","score":0.9}]}` → `{"stage":"websearch","query":"…","note":"知识库缺 2 条，正在联网补充"}`（无缺口则跳过）→ `{"stage":"synthesize"}` → `{"result":{image_url, image_width, image_height, boxes_url?, analysis:{hazards:[…]}}}` → `data:[DONE]` |
| **预算** | 整体 ≤ **200s**：vision 60s（模型自身 180s 上限，但超 60s 主动降级）→ RAG 并发 8s/条 → websearch 60s → synthesize 25s；任一阶段超时按阶段降级，不整单失败 |
| **降级** | vision 超时/失败 → `stage=vision` 后直接 `result.analysis.detected=false` + `error` 字段；RAG 全超时 → 全部 `grounded=false`；网搜超时 → 缺口条 `gap_note="网搜未成"` |
| **取消** | 前端 `AbortController`；服务端检测到断连即中止后续阶段；**识别流不写库**（落库仍在上报时，见裁定 5） |
| **兼容/回归** | 旧 POST 行为保持不变（返回同样的 JSON，只是内部也走 B 编排）；`tests` 覆盖两条路径 |
| **前端** | 用 `fetch + ReadableStream`（与聊天页同一套写法，EventSource 不支持 POST+multipart）；进度条按 4 阶段推进；超时 200s；阶段文案："识别中 → 检索知识 → 补充资料 → 汇总" |

> 其余两项（同图 10 分钟结果缓存、缺口合并为 1 次网搜）按方案默认执行，不再单列。

## 裁定 12（2026-11-05）：缺口网搜加**外层硬超时 70s**，超时按「无依据」返回

| 项 | 内容 |
|---|---|
| **背景** | 实测：`agent_scout.run_sync` 的 60s 预算只约束"采集"（45s），LLM 总结还能再拖 40s → 真机一次网搜 **105s**，整单 184s，已逼近前端 200s 上限。 |
| **裁定** | `hazard_agent.fill_gap()` 用独立线程 + `future.result(timeout=HAZARD_WEB_TIMEOUT=70)`，**超时就放弃本轮**（该条建议标「暂无依据（联网补充超时）」），识别继续往下走，不整单失败。被放弃的采集线程自行结束（其贡献提交不影响本次响应）。 |
| **依据** | 网搜是"锦上添花"，不是识别的前置条件；让一次慢网搜拖垮整次上报，与 04 大点"补料不能影响主链路"的口径一致。 |
| **测试** | `test_fill_gap_hard_timeout`（假 `_web_search` 睡 1.5s，限 0.3s → 必须返回 `ok=False` 且 note 含"超时"）。 |
