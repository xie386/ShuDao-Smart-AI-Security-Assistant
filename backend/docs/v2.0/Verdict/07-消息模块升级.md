# 大点 07 · 消息模块升级 —— 裁定

> 2026-11-05。依据：`research/07-消息模块升级.md`（15 处缺陷）+ 用户 2026-11-05 两轮拍板。
> 本文件只写"定了什么、为什么"；实现细节在 `v2.0规划文档.md` 的 07 ③ 段。

---

## 裁定 1：形态——**Redis 管消息，MySQL 管记录**，模块改名「消息与记录」

| 项 | 内容 |
|---|---|
| **分叉** | A 最小修补（Redis 内做全套）／B Redis 增强（hash+set 已读）／**C MySQL 落库**／D 完整站内信。 |
| **裁定** | **C**，但按用户口径拆成两半：**Redis 仍是消息主通道**（短期、会自动消失），**新建 1 张 MySQL 表存"记录"**（已闭环隐患 + 贡献结果，长期可翻阅）。前端菜单与页面标题改为「**消息与记录**」，页内两个 tab：消息 / 记录。 |
| **依据** | 用户拍板「做到 C」「继续以 redis 为主，建立一个新的 mysql 表用于记录已经闭环的隐患」。Redis 做短期通道的好处是"消息会自己过期"，不需要清理策略；缺点（重启即丢）恰好被"记录在 MySQL"补上。 |

---

## 裁定 2：Redis 数据结构换成 **HASH + ZSET**，条目级过期

| 项 | 内容 |
|---|---|
| **现状问题** | 单个 list 无法给"某一条"设 TTL、无法按 `hazard_id+type` 精准删除、无法存已读状态。 |
| **裁定** | 每用户两键：`shudao:notify:<uid>`（HASH `msg_id → json`）、`shudao:notify:z:<uid>`（ZSET `msg_id → created_ts`）。消息体字段：`id / type / message / hazard_id / contrib_id / created_at / expire_at / read / status`。 |
| **过期** | `expire_at` 为时间戳或 `null`（null = 不自动过期，靠业务删除）。**读的时候惰性清理**（GET 先剔过期、顺手 HDEL/ZREM），push 时也顺手清一批；不依赖 Redis 7.4 的 `HEXPIRE`（外部 Redis 可能是 5.x）。 |
| **兼容** | 旧 `list` 键写一次性迁移脚本（`scripts/migrate_07_notify.py`，默认 dry-run）：`LRANGE → HSET/ZADD`，原键改名 `…:legacy` 保留一天。 |

---

## 裁定 3：消息类型 · 收件人 · 生命周期（用户口径原文落地）

| 类型 | 收件人 | Redis 保留 | 删除时机 |
|---|---|---|---|
| **接收上报** `report` | 全部 admin | 不限期 | 该隐患「最终处理=已闭环」→ **删** |
| **整改反馈** `rectify` | 全部 admin | 不限期 | 同上 → **删** |
| **整改任务** `assign`（派单） | 被派单责任人 | 不限期 | 同上 → **删**（用户拍板 A1：保留该消息） |
| **验收结果·驳回** `accept`（status=rejected） | 被派单的 safety_officer | 不限期，**允许堆积** | 该隐患验收**通过**时，删掉此前所有驳回 |
| **验收结果·通过** `accept`（status=passed） | 被派单的 safety_officer | **1 天** | 到期自动清 |
| **最终处理** `final` | 上报人（任意角色）+ 全部 admin | **1 天** | 到期自动清 |
| **知识贡献** `kb_contrib` | 全部 admin + 贡献者本人（Agent 不发） | **1 天** | 到期自动清（通过/驳回都发） |

**两条推论（写死在方案里，避免实现时跑偏）：**

1. **"最终处理"只在验收通过（已闭环）时发**；驳回不是最终结果，不发"最终处理"，只发「验收结果·驳回」给责任人（用户口径：驳回堆积在 Redis，等通过）。
2. **admin 不再收「验收结果」**（旧代码会全量广播给 109 admin + 47 sfo）。admin 想知道某隐患被驳回，只能进详情看时间线。

---

## 裁定 4：闭环（验收通过）一次性动作

| 步骤 | 内容 |
|---|---|
| ① 删消息 | 该隐患的 `report / rectify / assign` 从**所有收件人**的消息里删除；责任人处该隐患的所有 `accept(rejected)` 删除 |
| ② 发消息 | 责任人：`accept(status=passed)`，1 天；上报人 + 全部 admin：`final`，1 天 |
| ③ 写记录 | 写入 `message_records(kind='hazard_closed', ref_id=hazard_id)`，**幂等**（UNIQUE 约束，重复验收不重复写） |
| ④ 失败隔离 | 记录写入失败只记日志，不影响验收结果；消息删除失败同样只记日志（30s 轮询会再对齐） |

---

## 裁定 5：记录表 `message_records`（1 张表，`kind` 区分两类记录）

```sql
CREATE TABLE message_records (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  kind          ENUM('hazard_closed','kb_contrib') NOT NULL,
  ref_id        INT NOT NULL,              -- hazard_id / contribution_id
  user_id       INT NULL,                  -- 上报人 / 贡献者（可见性过滤用）
  title         VARCHAR(200) NOT NULL,
  summary       VARCHAR(500) NULL,
  status        VARCHAR(24) NULL,          -- 已闭环 / 已入库 / 已驳回
  payload_json  MEDIUMTEXT NOT NULL,       -- 全量快照
  created_at    DATETIME NOT NULL DEFAULT NOW(),
  UNIQUE KEY uk_kind_ref (kind, ref_id),
  KEY ix_records_kind_time (kind, created_at),
  KEY ix_records_user (user_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

- **不动** `schema.sql` 既有表；迁移脚本 `scripts/migrate_07_records.py`（幂等，dry-run + `--apply`）。
- 一类一条记录：同一隐患被驳回多次再通过，**只写一条**，`payload_json` 里带驳回次数与全过程。

## 裁定 6：记录内容——**全量快照**，不是标题

`payload_json` 至少含：

```
{ hazard: {id,title,description,level,hazard_type,location,reporter_id,assignee_id,image_urls},
  timeline: [{action,operator_id,note,created_at}...],        // 上报/派单/每次驳回/整改/通过
  rectify: {measures, images, at},
  accept: {approved, note, at, reject_count},
  ai: {hazards:[...], annotated_url} | null }                 // 06 的 hazard_ai_analysis（有则带）
```

贡献记录为 `{contrib:{id,title,doc_type,source_kind,size}, review:{status,note,by,at,chunk_count}}`。

**依据**：用户要"记录"能翻阅复核；只存标题无法复核，也失去与 `hazard_timeline` 对账的意义。

## 裁定 7：记录可见范围

| kind | admin | safety_officer | employee | 其他 |
|---|---|---|---|---|
| `hazard_closed` | 全部 | **全部**（含不是自己做的，用户明确） | **仅自己上报的**（用户拍板 C） | 同 employee |
| `kb_contrib` | 全部 | 仅自己贡献的 | 仅自己贡献的 | 仅自己贡献的 |

- 服务端强制过滤（不靠前端藏按钮）；`GET /api/records` 与 `GET /api/records/{id}` 都校验。
- Agent 贡献（`source_kind=agent`）**照常写记录**供 admin 查阅，但**不给 Agent 发消息**（Agent 没有可读消息的界面）。

## 裁定 8：**引入已读**（B2），角标 = 未读数

| 项 | 内容 |
|---|---|
| **裁定** | 消息体带 `read` 字段；进「消息」tab 时前端自动把**当前列出的消息**标已读（`POST /api/notifications/read`，body `{ids:[...]}` 或 `{all:true}`）；角标显示**未读数**，随标记递减，不再把总条数当未读。 |
| **为何** | 现状 `unread=LLEN` 是假未读（S1-2），用户已拍板要真已读。 |
| **例外** | 「验收结果·驳回」允许堆积且进页面即被标已读——用户仍能在列表看到（灰显），闭环时一并删除。 |

---

## 裁定 9：实时性——**30s 轮询**，不做 WebSocket/SSE

- 前端 `setInterval` 30s 拉 `/api/notifications/count`（轻量：只回未读数 + 最新 1 条摘要），页面不可见时暂停（`visibilitychange`），回到页面立即刷一次；
- 在「消息」tab 上时，30s 顺带刷新列表；在「记录」tab 不轮询。

**依据**：用户拍板「30s 轮询」；现有 SSE 只用于聊天/PPT 长任务，消息用轮询足够且不占连接。

---

## 裁定 10：不做历史回填、不做站外通知

- 190 条历史隐患**不回填**（用户拍板 5）；记录从上线后的闭环事件开始积累；
- 不做邮件/短信/企业微信（用户拍板 6）；
- 仍然保留「清空我的消息」（`DELETE /api/notifications`），只清当前用户。

## 裁定 11：接口清单（定稿）

| 接口 | 说明 |
|---|---|
| `GET /api/notifications?limit=1..100` | 列表（新→旧），字段：`id/type/message/hazard_id/contrib_id/created_at/expire_at/read/status`；`unread` 为真未读数；`total` 改为**真实总数**（不再是截断长度） |
| `GET /api/notifications/count` | 轻量角标：`{unread, latest:{message,type,created_at}}` |
| `POST /api/notifications/read` | `{ids:[...]}` 或 `{all:true}` → 标已读，返回 `{unread}` |
| `DELETE /api/notifications` | 清空我的消息（保留） |
| `GET /api/records?kind=&page=&page_size=&q=` | 分页 + 关键词（标题/摘要），服务端按裁定 7 过滤 |
| `GET /api/records/{id}` | 详情（`payload_json` 解析后返回） |

## 裁定 12：保留的取舍与已知副作用（实现记录里要写清）

1. admin 不再收到「验收结果」，驳回情况要去隐患详情时间线看；
2. 驳回消息只给责任人，管理员在闭环前看不到"被驳回"的提醒；
3. 消息在 Redis，**后端重启仍会丢当天的短期消息**（`final / accept-pass / kb_contrib`）——这是"Redis 为主"的代价，记录表不受影响；若要彻底不丢，只能把消息也落库（超出本期口径）。
4. 记录写入放在验收事务**之后**（先提交隐患状态再写记录），避免记录失败回滚验收；幂等由唯一键保证。
