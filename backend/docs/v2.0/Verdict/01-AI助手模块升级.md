## 裁定 1（2026-10-23）：本大点范围收窄为「AI 助手回答提速」，全量评测与标注重建另立大点

| 项 | 内容 |
|---|---|
| **分叉点** | 01 原本会把「改检索链路」和「重跑全量评测（ALL@10 ≥ 0.80 红线）」绑在一起验收。但 Agent 化与问题预处理一旦落地，**一次问答可能包含多轮补检**，旧的单轮 100 题标注与「检索命中」口径不再等价，重跑得先重建标注。是先重建评测，还是先做提速？ |
| **可选方案** | **A** 先做提速，评测与标注重建另立大点（本轮只做分段耗时 + 抽样人工核对）；**B** 先重建多轮标注与评测脚本，再做提速；**C** 两者并行 |
| **裁定结果** | **A** |
| **依据** | 用户口径（原话）：「全量测评先放着，随着 Agent 化和各种预处理，评判标注和考察目标都要调整，01 专注 AI 助手回答提速方面的升级」。支撑：调研已把提速的主要来源量化清楚（热态检索 42~155s，其中重排 39.7~56s；context 100K~209K 字符），不依赖全量评测即可验证收益 |
| **影响面** | 规划文档 §01 ③ §3.5 改为「单测 + 分段打点 + 真机 + 5 题抽样」；`eval_qa.py` / `golden_qa.jsonl` 本轮不动；评测与标注重建留待后续大点 |

## 裁定 2（2026-10-23）：AI 助手本轮**正式 Agent 化**（R2 路线）

| 项 | 内容 |
|---|---|
| **分叉点** | 草案 1 认为现架构「不是严格 Agent，更像连接 API 的工作流」，建议正式 Agent 化；但 Agent 每轮多一次 LLM 往返，与「提速」目标存在张力。是只做缓存与预处理（R1），还是同批 Agent 化（R2），或拆成两个大点（R3）？ |
| **可选方案** | **A** R1：不上 Agent；**B** R2：`create_agent` + 检索工具 + 中间件承载缓存/判定；**C** R3：先 R1，Agent 化另立大点 |
| **裁定结果** | **B（R2）** |
| **依据** | 用户口径（原话）：「确定 Agent 化」。技术可行性已实测：`langchain 1.3.4` + `langgraph 1.2.4` 已装，`langchain.agents.create_agent` 可用（返回 `CompiledStateGraph`，支持 `checkpointer`/`middleware`），`MemorySaver` 可用，`stream_mode="messages"` 可接到现有 SSE；LLM 热态调用约 1.88s，多一轮在可接受范围 |
| **影响面** | 新增 `src/ai/chat_agent.py`；`chat.py` 编排改为「Agent 优先、直连 LLM 兜底」；`AGENT_ENABLED` 开关；`MemorySaver` 只在单进程有效（部署侧标注约束）；`langgraph-checkpoint-redis` **不引入** |

## 裁定 3（2026-10-23）：缓存粒度由父块改为**子块**

| 项 | 内容 |
|---|---|
| **分叉点** | 草案 Q4 原定「拟父块」缓存。但实测父块 `parent_text` p50 = **117,312 字符**（≈整篇文档），原样缓存会在每轮把十几万字塞回模型，既顶爆上下文又拖慢生成。缓存父块还是子块？ |
| **可选方案** | **A** 父块原样；**B** 父块截断到 N 字；**C** 子块缓存（命中后按需回取父块并裁剪） |
| **裁定结果** | **C（子块）** |
| **依据** | 用户口径（原话）：「一开始缓存父块的本意是降低问题被分成多问题分别提问的频率（多次提问意味多倍耗时），但既然草案 4(0) 的一半已经存在且父块体量过大，拟改为子块缓存」。数据支撑：子块 300~800 字符（实测抽样 751~800），缓存体量可控；命中后可直接跳过重排（重排是 39.7~56s 的唯一来源） |
| **影响面** | `conv_rag_cache` 的 value 结构为子块级（`child_text` + `rerank_score` + `parent_ref`）；上下文装配新增预算裁剪（`RAG_CONTEXT_BUDGET_CHARS=16000`）；父块只在生成前按命中子块所属文档取一次并裁剪 |

## 裁定 4（2026-10-23）：重排默认 **fp16**，前端提供「高精度检索」开关切 fp32

| 项 | 内容 |
|---|---|
| **分叉点** | 重排是唯一瓶颈（fp32 显存打满、n=30 要 36~56s）。可选：直接改 fp16（省 11.5 倍但牺牲极小的数值精度）、保持 fp32 但接受慢、或让用户自己选。 |
| **可选方案** | **A** 全部改 fp16，不提供选择；**B** 保持 fp32；**C** 默认 fp16 + 前端「高精度」开关按请求切 fp32；**D** 降候选数/换轻模型 |
| **裁定结果** | **C** |
| **依据** | 用户口径（原话）：「f32 要变成用户可选项，即默认 f16，用户可以为了提高准确性在前端打开『高精度』检索开关」。实测支撑（research §5.5.4）：同一批 30 个真实子块，fp32 36.40s vs fp16 3.16s；**top-4 顺序/集合/全量排序完全一致**，最大分差 0.0016；fp16 连跑 3 次 3.21/3.06/3.06s（抖动 1.05x，fp32 时是 2x）；fp16 显存 2.45GB（device_free 0.73GB）vs fp32 3.57GB（device_free 0.00GB）。D 被否：触碰指标红线 |
| **影响面** | `config.py` 增 `RERANKER_DTYPE`/`RERANKER_BATCH_SIZE`；`reranker.py` 支持按请求切换精度（切换需卸载重载，加锁）；`schemas/chat.py` 增 `high_precision`；`front/safety/index.html` 增开关（localStorage）；SSE 追加 meta 帧显示精度与耗时 |

## 裁定 5（2026-10-23）：预处理结果复用 `chat_messages.refs` 承载，不改表结构

| 项 | 内容 |
|---|---|
| **分叉点** | 草案 Q5 要求「history 存用户原话和预处理后的样子」。承载方式有三条：给 `chat_messages` 加列（动 `schema.sql`，触碰「表结构唯一权威」铁律）、复用现有 `refs` 字段（user 行目前为空）、或只写日志不落库。 |
| **可选方案** | **A** 加列；**B** 复用 `refs` JSON；**C** 只写日志 |
| **裁定结果** | **B** |
| **依据** | 继承 v1.0 铁律「schema.sql 唯一权威、代码不得擅自改表」，且本大点定位是「提速」，不值得为可追溯性引入迁移；user 行的 `refs` 字段本就闲置，写入 `{"preprocessed": {...}}` 零成本，且 `build_history` 可直接读出来拼「原话（检索式：…）」 |
| **影响面** | `chat_service.save_message` 支持 user 行写 refs；`build_history` 拼接格式变化；不动 `database/schema.sql`、不动前端引用解析（前端只读 assistant 行的 refs） |

## 裁定 6（2026-10-23）：Redis 不可用时走「上下文回顾 + 缺口补检」，**不是**整题全量重检

| 项 | 内容 |
|---|---|
| **分叉点** | 方案初稿把 Redis 不可用的退化写成「退回每问全量检索」。用户指出这与草案 5(2) 不符：草案要求「后续追问先上下文信息判断是否需要更多信息，需要的话把需要的信息进行检索，而不是整体重新检索」——Redis 挂了也应保留「只补缺口」的行为。 |
| **可选方案** | **A** 退回每问全量检索（初稿，最省事但违背草案；首问之外的追问也会变慢）；**B** 退化时只凭会话上下文（最近 3 轮问答 + 上轮已引用来源）判断缺口，只补缺失部分；**C** 退化时不做判定，直接生成（最省时但可能答不全） |
| **裁定结果** | **B** |
| **依据** | 用户口径（原话）：「草案提到了不是完整检索，是只回顾上下文总结缺失信息（redis 存活时回顾上下文和 redis 内检索块总结缺失信息）」。可行性：`chat_messages.refs` 已存每轮答案的引用来源（v1.0 就在用），从库里就能重建「已检索/已引用过什么」，不依赖 Redis；判定器输入换成 `context_digest()`（最近 3 轮问答摘要 + 上轮 `doc#chapter`）即可复用同一个判定 prompt。C 被否：缺少「缺什么」的判断，容易答不全 |
| **影响面** | 规划文档 §01 ③ 的数据流新增「Redis 不可用」分支；`sufficiency.py` 支持两套输入（缓存块摘要 / `context_digest`）；`chat_service` 新增 `context_digest()`（只读 DB）；验证项 7 的通过条件改为「退化模式下只做缺口增量检索」 |

## 裁定 7（2026-10-23）：问题预处理（陈述句化 / 专业化 / 拆分 / 剔除已检索）在**所有路径必做**

| 项 | 内容 |
|---|---|
| **分叉点** | 方案初稿的数据流把预处理画在「无缓存」与「Redis 不可用」两个分支下面，读起来像「有 Redis 就走缓存、不用预处理」。用户指出：这三类处理与 Redis 是否可用无关，任何一条路径都要做。 |
| **可选方案** | **A** 维持初稿（预处理归入分支）；**B** 预处理提为公共步骤，所有路径先做全覆盖预处理，分支只决定「检索来源与判定输入」；**C** 只对首问做预处理，追问跳过（省 LLM 调用但追问质量下降） |
| **裁定结果** | **B** |
| **依据** | 用户口径（原话）：「不管有没有 redis 服务，(陈述句化、专业化、拆分) 三个都要有，不是 redis 服务有就不用做」。设计依据：追问同样常是口语/疑问句（如「那高度呢？」），若跳过预处理，改写与检索都会失真；且「剔除已检索项」在无 Redis 时同样可做——`chat_messages.refs` 里就有上轮答案引用过的 `doc#chapter` |
| **影响面** | 规划文档 §01 ③ §3.2 数据流把预处理提为公共步骤（并移除分支内的预处理描述）；§3.3 (4) 改为「四类动作每次都跑全套 + 三处输入来源（Redis 块摘要 / DB refs 二选一，逻辑不分支）」；§3.5 验证项 7 增加「退化模式四类动作照做」 |

## 裁定 8（2026-10-23）：动作 c) 多主题拆分改为 **Agent 可选行为**，判据「同实体不拆、不同实体才拆」

| 项 | 内容 |
|---|---|
| **分叉点** | 方案初稿把「多主题拆分」与陈述句化、专业化一样列为每次必做。但拆分等于多发一次检索，**时长近乎翻倍**，与「提速」目标直接冲突；而很多问题其实是同一实体的两个方面（合成一条检索式即可覆盖）。 |
| **可选方案** | **A** 每次必拆（初稿）；**B** 一律不拆（省时但复合问题答不全）；**C** 由 Agent 按判据决定是否拆，并限制条数；**D** 规则判定（按「和/与/、」切分） |
| **裁定结果** | **C** |
| **依据** | 用户口径（原话）：「拆分行为本身就是多次询问，会使时长翻倍，故不是每次必做，而是让 Agent 进行判断……同一实体的两个方面不必拆，不同实体需要拆」。D 被否：规则无法区分「同一实体两方面」与「不同实体」（如「安全带选型 + 报废标准」按连词会被误拆）。判据落地：预处理只给 `split` 建议，Agent 复核后决定；上限 2 条子查询 |
| **影响面** | 规划文档 §01 ③ §3.2 数据流把 c) 标为可选并写明判据；§3.3 (4) 动作表改为「a/b/d 必做、c 可选」并新增判据对照表；§3.3 (7) Agent 的 `retrieve_more` 支持多子查询但 `system_prompt` 写死判据；§3.5 新增验证项 8（三组对照） |

## 裁定 9（2026-10-23，实现期）：Agent **不挂 checkpointer**，多轮上下文由 DB `build_history()` 每轮注入

| 项 | 内容 |
|---|---|
| **分叉点** | 裁定 2 曾写「Agent 状态用 `MemorySaver`（单进程）」。进入实现后与「上下文预算」目标发生冲突：Agent 自带记忆 + 每轮再注入历史 = 双份上下文；且 `MemorySaver` 是进程内内存，重启即丢、多 worker 各自一份，而 MySQL 里的 `chat_messages` 才是唯一事实来源。 |
| **可选方案** | **A** `create_agent(checkpointer=MemorySaver(), thread_id=会话ID)`，不再注入历史；**B** 不挂 checkpointer（无状态），每轮把「最近 5 轮 + 本轮资料」拼成 user 消息；**C** 引入 `langgraph-checkpoint-redis` 走 Redis 持久化 |
| **裁定结果** | **B** |
| **依据** | ① 历史已在 MySQL，B 不引入第二份状态，重启/多 worker 行为一致；② A 的上下文无法按 `RAG_CONTEXT_BUDGET_CHARS` 裁剪，长会话必然膨胀，与「把 100K~209K 字符压到 16K」的正题相反；③ C 需新增依赖并再引入一个存储故障面（Redis 已有一条降级路径），收益仅是省掉一次 DB 读。B 的代价是每轮多一次 `build_history` 查询（实测 ms 级）。 |
| **影响面** | `chat_agent.py` 不传 checkpointer；`stream_answer` 只做「流式 token」一件事；多轮语义靠 `chat_service.build_history()`（user 行带预处理检索式，便于模型对齐）与 `safety_agent_user` 模板。已在 `Done/01-…·实现记录.md` §三 验证多轮追问连续性（第 2 轮检索式与第 1 轮明显不同且回答承接上文）。 |

## 裁定 10（2026-10-23，实现期）：冷启动治理 —— 语料只读 `documents` + 磁盘缓存 + 启动预热 + 检索等待预热

| 项 | 内容 |
|---|---|
| **分点** | 调研期只测到「BM25 预热 178s」，实现期拆开量到真因：`col.get(include=["documents","metadatas"])` 会连同每个子块的 `parent_text`（p50 ≈ 117K 字符）一起拉进内存，**17,797 块 ≈ 2.2GB / 159.8s**，还会写出 2.2GB pickle（实测已产生并删除）。BM25 建索引另需 17~18s。首问预算 60s 被这两项吃光。 |
| **可选方案** | **A** 原样保留（首问 ≥175s，超预算）；**B** 只把慢活挪到启动线程预热（首问仍可能撞上预热）；**C** B + 语料只读 `documents`、metadata 按 id 回查 + 磁盘缓存 `ids/corpus`（17.8MB）+ 检索端「预热未完成则等待」 |
| **裁定结果** | **C** |
| **依据** | ① 只读 `documents` 后磁盘缓存 2.2GB → **17.8MB**，语料加载 159.8s → **5.8~8.0s**（缓存命中）；② metadata（含 `parent_text`）改由 `_hydrate_metadata()` 只回查稀疏命中的 ≤30 条，检索链路口径不变；③ 预热中提问若不等待，`lru_cache` 不防并发 → 两个线程各建一遍索引，实测把首问检索从 13.4s 拖到 **93.9s**；加 `_await_warmup()` 后同一场景降到 **34.5s**（= 预热剩余时间 + 检索）；④ 语料变更由 `upsert_chunks` 主动 `invalidate_corpus_cache()`，另有块数校验兜底，不存在「知识更新后检索命中旧语料」。 |
| **影响面** | `rag.py`：`_load_corpus()/_get_bm25()/_hydrate_metadata()/invalidate_corpus_cache()/warmup()/_await_warmup()`；`knowledge.upsert_chunks()` 末尾失效缓存；`main.py` lifespan 起 `rag-warmup` 线程；新增配置 `RAG_WARMUP_ON_START`。副作用：`chroma/` 同级新增 `bm25_corpus.pkl`（17.8MB，可随时删除，删除后下次启动重建）。 |
