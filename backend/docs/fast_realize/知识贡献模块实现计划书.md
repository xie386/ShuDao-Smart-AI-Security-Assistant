# 知识贡献（贡献知识）模块实现计划书

> 状态：规划中 ｜ 阶段：优化丰富期（D1–D5 完成，考试工坊 + RAG 优化已交付） ｜ 落点：backend + front/safety
> 关联模块：隐患上报（H01–H06）、消息通知（H08）、RAG 知识库（safety_kb）、子智能体（考试工坊 exam_agent 同范式）

---

## 一、业务目标

让**全员**（employee / safety_officer / admin）向施工安全知识库**贡献新知识**，**管理员人工审核通过后才真正写入向量库**——实现「不重建知识库、增量追加」。

复用已有 RAG 技术栈的 `knowledge.upsert_chunks()`（内容哈希稳定 ID 增量 upsert，重跑覆盖去重），达到「**向量库不重建即可追加**」的核心诉求。

### 1.1 为什么要做「审核后才入向量库」
向量库一旦写入错误/无关内容，会污染 RAG 检索质量（错误知识被召回喂给问答 LLM）。因此贡献内容**必须经 admin 审核**，且由**子智能体预筛「是否确属施工安全领域」**辅助管理员决策。

### 1.2 框架套用「隐患上报」
| 隐患上报 H0x | 知识贡献 K0x | 说明 |
|---|---|---|
| H01 上报 `待处理` | **K01 贡献提交** `待审核` | 全员可提交 |
| H04 派单→`处理中` | （无对应，贡献无需派单） | — |
| H05 整改→`待验收` | （无对应） | — |
| H06 验收 `已闭环/已驳回` | **K06 审核** `已入库/已驳回` | 仅 admin |
| H03 时间线 | **K03 进度时间线** | 上传者看进度 |
| H08 消息联动 | **H08 消息联动** | 上传者收进度、admin 收待审通知 |

**结论**：知识贡献 = 隐患上报的「提交 → 审核闭环」双态精简版，复用其 timeline + 消息联动套路。

## 二、技术方案

### 2.1 可行性结论（已调研）
当前 RAG 技术栈**完全支持增量追加、不重建**：
- 向量库：Chroma 1.5.9 持久化 `safety_kb`（cosine + HNSW），`chroma/` 持久化目录
- 写入入口：`src/ai/knowledge.upsert_chunks(chunks)` —— 接收 chunk 列表，稳定 ID upsert
- 分块：`SPLITTERS` 四类（laws/cases/plans/procedures）结构感知分块，**用户输入单段文本选定 doc_type 即可复用**
- 嵌入：`embedding_model.embed_documents()` 本地 bge-large-zh（lazy）
- 检索侧：`hybrid_retrieve` 只读引用，追加后自动可见，**零改动**

→ 知识贡献审核通过 = 把单条内容的分块结果调一次 `upsert_chunks` 即可。

### 2.2 子智能体（辅助审核）
- 新建 `src/ai/knowledge_review_agent.py`，**完全照考试工坊 exam_agent 范式**：
  - `from src.ai.llm_client import llm_client`（LangChain ChatOpenAI，DeepSeek 主 / agnes 自动降级）
  - `from src.ai.prompts import load_prompts, render`
  - prompt 新增 `prompts.yml` 的 `knowledge_review`（判定：是否施工安全领域 / 是否重复/无关 / 一句话理由 + 建议通过/驳回）
- 在管理员打开审核界面时**自动调用**，返回预筛结论，**仅作参考、不代替管理员决策**

### 2.3 不重建的保证
- 复用 `upsert_chunks` 稳定 ID：同一文本重审通过不会重复写
- **绝不调用** `build_from_dir`（全量扫描）——只用单条 `upsert_chunks`，HNSW 索引原地增量

## 四、后端接口（src/routers/knowledge_contrib.py）

| # | 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|---|
| K01 | POST | `/api/knowledge-contrib` | 全员 | 提交贡献：`status=待审核` + 写 timeline（提交）+ 通知**全部 admin**（待审） |
| K02 | GET | `/api/knowledge-contrib` | 全员 | 列表：普通用户 `only_mine`；admin 看全部/按 status 筛（待审核优先） |
| K03 | GET | `/api/knowledge-contrib/{id}` | 本人或 admin | 详情（含 timeline） |
| K04 | POST | `/api/knowledge-contrib/{id}/review` | **仅 admin** | 审核：通过 → `upsert_chunks` 入向量库 + `status=已入库` + chunk_count 回填；驳回 → `status=已驳回` + review_note |
| K05 | POST | `/api/knowledge-contrib/{id}/review-preview` | **仅 admin** | 子智能体预筛：调用 `knowledge_review_agent`，返回 `{in_scope, suggestion, reason}`（不写库） |

> 复用 `get_current_user` + `require_roles("admin")`；service 层强制状态机（待审核→已入库/已驳回）。

### 4.1 审核通过写向量库（核心）
`src/services/knowledge_contrib_service.py::review()`：
```python
# 1. 取贡献内容，用对应分块器分块
splitter = SPLITTERS[contrib.doc_type]
chunks = splitter(contrib.content, doc=f"contrib_{contrib.id}", source="user_contrib")
# 2. 增量 upsert（不重建！）
n = upsert_chunks(chunks)
contrib.status = "已入库"
contrib.chunk_count = n
# 3. 写 timeline + 通知上传者「已入库」
```
> 分块器 `doc=` 用 `contrib_{id}` 保证稳定 ID 不与官方源冲突（隔离命名空间）。

### 4.2 消息联动（H08 复用）
- **K01 提交**：通知全部 admin `【知识待审】用户 #x 贡献：{title}（贡献 #id），请审核`（msg_type=kb_contrib）
- **K04 通过**：通知上传者 `【知识已入库】您的贡献 {title}（#id）已通过审核并入知识库`（msg_type=kb_contrib, contrib_id）
- **K04 驳回**：通知上传者 `【知识被驳回】{title}（#id）：{review_note}`（msg_type=kb_contrib, contrib_id）
- 前端消息列表按 `type=kb_contrib` 渲染，点击跳 `#/kb-contrib/{id}`

## 八、风险与注意

| 项 | 处理 |
|---|---|
| 污染风险 | 审核通过才 `upsert`；`doc=` 用 `contrib_{id}` 命名空间隔离，重审不重复 |
| 审核误放行 | 子智能体仅辅助，最终决策在 admin（K04 必填 approved） |
| 大模型无关内容 | 子智能体判定 `in_scope`，但管理员可否决 |
| Redis 未启动 | 消息推送已优雅降级（notification_service 现状），不阻塞主流程 |
| 与 RAG 优化并行 | 仅新增 `upsert_chunks` 调用方，**不改** knowledge.py/rag.py/embeddings.py |
