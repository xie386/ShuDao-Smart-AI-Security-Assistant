# 版本文档规范（本项目适配版）

> **为什么有这份文件**：往期项目反复栽在三件**编排**问题上（不是能力问题）——
>
> | 事故形态 | 具体长什么样 | 代价 |
> |---|---|---|
> | 文档编排与职责先后混乱 | 调研、方案、裁定、实现记录混在同一份文档里，读者分不清「哪句是当时的试探」「哪句是定论」 | 实现期照一句被否掉的结论去做，返工 |
> | 裁决记录未计或延迟 | 裁定散落在对话与各文档里，「待拍板」「未决」到处是 | 同一件事被重复裁定、重复验证；事后说不清当时为什么这么定 |
> | 规划与实现脱节 | 规划文档没写清「这个议题来自哪份调研的哪个方案」 | 实现时无据可依，回头翻信息堆砌的调研文件，越翻越乱 |
>
> **适配说明**：本文件按蜀道项目（FastAPI + 单文件前端）的实际结构改写自 deep_search_pro 的同名规范；新增一节「与上游规范的差异」写明哪些规定不照搬。

---

## 〇、三条硬规矩

1. **四类分家**：每个**整数版本**目录（本项目当前为 `backend/docs/v2.0/`）下，文档按 **规划文档 / `research` / `Verdict` / `Done`** 四类存放。**一份文档只承担一类职责**，不许一份文档里既有调研又有定论。
2. **决策字眼只有一处**：实现分叉的裁定**只写在 `Verdict/`**。**任何其他文档不得出现「待裁决 / 待拍板 / 未决」字样**；凡是「选型 / 取舍 / 为何这么定」这类表述，都只在 `Verdict/` 写。要引用裁定就写「见 `Verdict/NN-….md` 第 n 条」。
3. **实现期只读两份**：规划文档的对应大点 + `Verdict/`。**调研文件不许在实现期通读**（见 §六）。

## 一、目录结构

```text
backend/docs/
├── README.md                    # 文档体系索引 + 全树导航
├── v1.0/                        # 老版本归档：存放各种文档、不再逐一维护，内部杂乱属正常
└── v2.0/                        # ★ 按四类编排（自 v2.0 起）
    ├── v2.0规划文档.md          # ★ 唯一权威：目录表（进度真值）+ 每个大点四段式
    ├── research/NN-<大点名>.md   # 调研期产物（信息堆砌，可天马行空）
    ├── Verdict/NN-<大点名>.md    # 实现分叉的裁定记录（唯一裁决落点）
    ├── Done/NN-<大点名>·实现记录.md
    ├── Done/NN-<大点名>·逐文件带读.md
    ├── backups/                 # 改用户数据前的只读快照（不入库，版本提交后即删）
    └── 交接文档.md              # 版本冷启动入口（例外：不分进四类）
```

- **编号 `<NN>`** = 该大点在规划文档里的序号（`00` / `01` / `02` …）。**四类文件共用同一编号与同名**，一眼对上「规划里的一大点 ↔ 四个文件」，不另建对照表。
- 本项目大点编号**从 `00` 起**（v2.0 的第一个大点即 00）——这是本项目口径，与上游项目把 `00` 留给「版本级裁定」的做法不同。
- 四类目录**只在整数版本目录下建**。小数版本（将来若出现 `v2.5` 这类）不建四类，仍按「问题 → 方案 → 结果」单篇办。

## 二、`vn.0规划文档.md`（每个版本的唯一权威）

**内容 = 目录表 + 每个「已经过讨论、敲定实现方案」的议题**，一个新功能点（或一项工程改造）一大点。**工程类议题同样是大点**，不因为它不改产品行为就降格（v2.0 的 00 号大点就是账号隔离性工程）。

两条准入：
- **方案没敲定的不进规划文档**（它还在 `research/` 里躺着）；
- **外部来源**（文档、接口说明、参考实现）要**指到出处**（URL 或项目内路径），别只写「据调研」。

### 目录表 = 进度唯一真值

规划文档开头的目录表必须能让「这一版有哪些大点、各自到哪一步」一眼看完：一行摘要 + 阶段 + 指向 `research` / `Verdict` / `Done`。**README 与交接文档都不承载进度。**

### 每个大点的四段式（缺一段不算完整）

| 段 | 写什么 | 判据（写好没有） |
|---|---|---|
| **① 应对什么问题** | 现象 + **证据** | 证据可复现：数字、日志、库/代码位置（`path:line`）。写不出证据说明还在调研阶段 |
| **② 功能** | 做成什么样（用户视角） | 能一句话说清「做完之后，用户/系统多了什么」 |
| **③ 实现功能的技术方案** | 怎么落 + **来源标注** | 来源 = 「`research/NN-xxx.md` 的 §X」；外部来源补 URL。要写到「换个会话照着能开工」的粒度 |
| **④ 实际实现的文档索引** | 指向 `Done/` 的两篇 | 未开工就写「未开始」；开工后填实测结果 |

### 「占位段」（已立项但方案未敲定）

允许为**已立项、但方案仍在调研**的大点在规划文档占一段。格式：

- 标题下**立刻**写状态：`> 状态：方案未敲定（调研中，见 research/NN-xxx.md）`；
- **只写 ① ②**，③ ④ 一律写「未开始」，不得编造方案或文档索引；
- 该大点**不得**进 `Done/`；方案敲定后先补齐 ③ 段（含来源标注）再开工。

## 三、六类文档的角色表

| 记录类型 | 角色 | 不许写什么 |
|---|---|---|
| `Verdict/NN-*.md` | **决策类字眼的唯一出口**：所有「选型 / 取舍 / 为何这么定」 | —（它就是权威） |
| `vn.0规划文档.md` | **方案唯一权威**：只写详细方案规划（③ 要写到换会话能开工） | 裁定结论、实现过程 |
| `Done/NN-*·实现记录.md` | **只记实现过程**：问题 → 做法 → 结果 + 可复跑数字 + 偏差/事故 | 决策口径 |
| `Done/NN-*·逐文件带读.md` | 逐行检查：文件清单 + 关键行号 + 链路位置 + 思考题 | 决策口径 |
| `docs/<版本>/README.md` | 整个版本做完后写的、**面向非开发用户**的新版本功能介绍（进行中可留骨架） | 进度表 / 索引表 / 决策 |
| `交接文档.md` | 版本**冷启动入口**：当下状态 + 下一步 + 纪律与指向 | 进度真值、决策正文 |
| `research/NN-*.md` | 调研期信息（多方向、含废案）；实现期只许定点查 | 定论口吻 |
| `docs/README.md` | 文档体系索引 + 全树导航 | — |
| `backups/` | 改用户数据前只读快照；该版本 git 提交完成后即删除 | — |

### 大点的生命周期（六阶段）

| 阶段 | 状态写法 | 产物 | 硬约束 |
|---|---|---|---|
| 1. 占位（待调研） | 目录表「待调研」 | 规划文档占位段（只写 ①②）+ `research/NN-*.md` 骨架 | ③④ 写「未开始」；不得进 `Done/` |
| 2. 调研 | 「调研中」 | **只在 `research/NN-*.md` 里写**（信息堆砌、多方向、含废案） | 不动代码、不改数据；取证只做只读探测 |
| 3. 定方案 | 「方案已定」 | 规划文档 ③ 段补齐（含来源标注）+ `Verdict/NN-*.md` 记方案级裁定 | ③ 段不补齐 = 不许开工 |
| 4. 实现 | 「实现中」 | 代码/夹具；**中途的实现分叉逐条落 `Verdict/`**（当场问、当场记） | 裁定不进任何其他文档 |
| 5. bug 修复 | 「修 bug 中」 | 先脚本自测（单测/离线自检），再真机客户端测试（浏览器点一遍） | **两步都不许跳**；结果都记进本阶段记录 |
| 6. 记录 | 「已完成」 | `Done/` 两篇 + 规划文档 ④ 段指向它们 | 实测数字要能复跑；偏差与事故如实写 |

- **阶段只前进不跳跃**：调研期写方案 = 越级；实现期回头通读 `research/` = 污染。
- **阶段推进由用户口令决定**：助手不得以「调研已充分」为由自行补 ③ 段或开工。
- **调研期用户的选择要留档**：当场逐字记进 `research/NN-*.md`，到阶段 3 再转正为 `Verdict/` 的裁定。
- **回退**：实现中发现方案不成立 → 回阶段 3 改 ③ 段，并在 `Verdict/` 追加「推翻/修订第 n 条」及理由。

## 四、`research/`（调研期产物）

- 每个大点一个 md，命名 `NN-<大点名>.md`。
- **可以天马行空**：信息堆砌、多方向考察、试错记录、被否掉的路线、外部资料摘录——不追求可读，追求**信息不丢**。
- 最终只有一个结果写进规划文档对应大点；research 里可以有十条路线，规划文档里只有那一条。
- 读者是调研期与方案决定期的你，**不是实现期**。

---

## 五、`Verdict/`（裁决的唯一落点）

每个大点一个 md，按时间**追加**条目；**旧条目不删、不改语义**（要改就在下面追加「修订 + 理由」）。

每条裁定至少写全六项：

| 项 | 内容 |
|---|---|
| 日期 | `YYYY-MM-DD` |
| 分叉点 | 一句话说清在纠结什么（含被否掉的那条路） |
| 可选方案 | A / B / C 各自代价 |
| **裁定结果** | 定了哪个 |
| **依据** | 实测数字、代码事实、或用户口径（原话里的取舍原则） |
| 影响面 | 改了哪些文件、影响了哪些指标/行为 |

三条纪律：**当场问、当场记**；**别处置疑**（其他文档不出现「待裁决」字样）；**同一条不重复裁定**（要推翻就新追加一条并写明推翻第 n 条）。

---

## 六、`Done/`（实现记录 + 逐文件带读）

每个大点**两篇**，别揉成一篇：

| 文件 | 写什么 | 读者 |
|---|---|---|
| `NN-<大点名>·实现记录.md` | **问题 → 方案 → 结果**：改了什么、关键落点、踩坑、与方案的偏差（含理由）、**实测数字（可复跑）**、待跑清单 | 想知道「改了什么、为什么」的人 |
| `NN-<大点名>·逐文件带读.md` | **逐文件带读**：文件清单 + 关键定义行号 + 在链路里的位置 + 逐行检查要点 + 思考题 | 想逐行检查实现的人 |

- 写了数字就要能复跑（写了「8/8 通过」必须给出跑出 8/8 的命令），否则等于没写。
- **如实记偏差与事故**：现象 / 证据 / 根因 / 验证四段写清，别只写「已修复」。

---

## 七、阅读纪律（防上下文污染）

- `research/` 只在调研期与方案决定期读。
- **实现期不要通读 `research/`**：只在核对「这个方案的依据」时定点看一眼那一节。
- 理由：research 里混着被否掉的路线与试探性结论，通读会把它当现行方案，比不读更危险。
- 实现期的权威只有两份：**规划文档对应大点 + `Verdict/`**。两者没写到的，才回去查 research，并顺手把缺的那条补进规划文档。

---

## 八、引用计数同步

凡在文档里写**条数 / 个数 / 计数**：

1. 只写在**该数的权威处**（裁定条数 → `Verdict/`；测试项数 → `Done/` 实现记录 + 复跑命令），他处一律不重复数字、改写为「见 `Verdict/NN-….md`」；
2. 若确需引用，**引用前重新数一遍**（`grep -c` 或跑一遍命令），不许凭记忆；
3. 大点收官巡检时列为检查项。

## 九、与上游规范的差异（本项目不照搬的部分）

| 上游（deep_search_pro） | 本项目口径 | 原因 |
|---|---|---|
| `Verdict/00-*.md` 固定留给「版本级选题与范围」 | 大点编号从 `00` 起，`Verdict/00` 就是大点 00 的裁定 | 用户 2026-10-23 口径：「现在还是 00 大点，不是 01」 |
| 五阶段（占位→调研→定方案→实现→记录，bug 修复合入实现） | **六阶段**，bug 修复单列（实现→bug 修复→记录） | 用户 2026-10-23 明确要求六阶段，且强调「每阶段等我口令」 |
| `tests/` 按 `unit/harness/testclient/live/debug` 分类 | 本项目 `tests/` 为扁平 `test_<模块>.py`，不强制分类 | 现有 10 个测试文件即此结构，重构成本大于收益 |
| 上游目录（`agent/` `api/` `tools/` `user_data/` 等） | 本项目为 `backend/src/{core,ai,models,routers,services,schemas,utils}` + `front/` + `database/` + `deploy/` | 见《文件存放规则（本项目适配版）》§二 |
